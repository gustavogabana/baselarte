O que é uma skill e o que ela fazWhat a skill is and what it does

Uma skill é uma pasta com um arquivo SKILL.md: um cabeçalho YAML (nome e descrição) e, abaixo, instruções em Markdown. Ela ensina ao agente um procedimento repetível (como revisar um PR, como escrever requisitos, como fazer um release) e só entra no contexto quando a tarefa pede. O formato é um padrão aberto, o Agent Skills, e a mesma pasta funciona no Claude Code, no Codex, no opencode e no Hermes (cada um acrescenta extras, veja onde ficam).A skill is a folder with a SKILL.md file: a YAML header (name and description) and, below it, instructions in Markdown. It teaches the agent a repeatable procedure (how to review a PR, how to write requirements, how to cut a release) and only enters the context when the task calls for it. The format is an open standard, Agent Skills, and the same folder works in Claude Code, Codex, opencode and Hermes (each adds extras, see where they live).

O truque é a divulgação progressiva: no início o agente lê só o nome e a descrição de cada skill (cerca de 100 tokens por skill, segundo a especificação). Se a tarefa casa com a descrição, ele carrega o corpo do SKILL.md. Arquivos de apoio só são lidos se o corpo mandar. Assim você pode ter dezenas de skills instaladas sem encher o contexto.The trick is progressive disclosure: at the start the agent reads only the name and description of each skill (about 100 tokens per skill, per the specification). If the task matches the description, it loads the SKILL.md body. Supporting files are read only if the body says so. That way you can have dozens of skills installed without filling the context.

O que uma boa skill faz, e o que não fazWhat a good skill does, and what it does not

  • Traz o que o agente não sabe: as convenções do seu projeto, os passos na ordem certa, as armadilhas (“a tabela users usa exclusão lógica”). Não explica o que o agente já sabe, como o que é um PDF ou um SQL injection.Brings what the agent does not know: your project's conventions, the steps in the right order, the traps (“the users table uses soft deletes”). It does not explain what the agent already knows, like what a PDF or a SQL injection is.
  • Fixa o formato da saída com um modelo (template): o agente segue estruturas concretas melhor do que descrições em prosa.Fixes the output format with a template: the agent follows concrete structures better than prose descriptions.
  • Entrega scripts quando um passo precisa ser idêntico a cada vez. O script roda e só a saída gasta contexto.Ships scripts when a step must be identical every time. The script runs and only its output costs context.
  • Não é um sandbox nem uma permissão. A skill roda com o acesso que o agente já tem; ela é instrução, e instrução pode ser ignorada ou enganada. O que precisa valer sempre vai em hook, permissão ou rede (veja segurança).It is not a sandbox or a permission. The skill runs with the access the agent already has; it is instruction, and instruction can be ignored or tricked. What must always hold goes in a hook, a permission or the network (see security).
Quando vale criar uma. A documentação do Claude Code dá o critério: quando você cola as mesmas instruções no chat de novo e de novo, ou quando uma seção do CLAUDE.md virou um procedimento em vez de um fato. A especificação acrescenta o teste inverso: se o agente já faz a tarefa bem sem a skill, ela não está agregando valor.When one is worth creating. The Claude Code documentation gives the criterion: when you paste the same instructions into chat again and again, or when a CLAUDE.md section has become a procedure rather than a fact. The specification adds the opposite test: if the agent already does the task well without the skill, it is not adding value.

Como criar uma skill, passo a passoHow to create a skill, step by step

  1. Faça a tarefa uma vez, com o agente, sem skill. Dê o contexto, corrija os desvios, diga as preferências. Depois olhe: quais passos funcionaram, quais correções você fez, que formato de entrada e saída apareceu. É isso que vira a skill. As boas práticas oficiais alertam: pedir a um modelo uma skill “do nada” gera procedimentos genéricos (“siga as boas práticas”); o valor está no que é seu.Do the task once, with the agent, with no skill. Give context, correct the drift, state preferences. Then look at it: which steps worked, which corrections you made, what input and output format showed up. That is what becomes the skill. The official best practices warn: asking a model for a skill “out of thin air” yields generic procedures (“follow best practices”); the value is in what is yours.
  2. Crie a pasta e o arquivo. O nome da pasta é o nome da skill, e o arquivo chama-se SKILL.md exatamente assim, em maiúsculas.Create the folder and the file. The folder name is the skill name, and the file is called SKILL.md exactly like that, in capitals.
  3. Escreva a descrição. É o campo mais importante (veja regras): o que a skill faz e quando usá-la, com as palavras que o usuário usaria.Write the description. It is the most important field (see rules): what the skill does and when to use it, with the words the user would use.
  4. Escreva o corpo como um procedimento: passos numerados, uma seção de armadilhas (gotchas), o modelo de saída. Curto: tudo que está lá fica no contexto enquanto a skill estiver ativa.Write the body as a procedure: numbered steps, a gotchas section, the output template. Keep it short: everything in it stays in context while the skill is active.
  5. Mova o que é longo ou raro para arquivos de apoio (references/, assets/) e diga no corpo quando ler cada um. Ponha em scripts/ o que precisa ser determinístico.Move what is long or rare into supporting files (references/, assets/) and say in the body when to read each one. Put in scripts/ what must be deterministic.
  6. Valide e teste (veja o laboratório): o formato com um linter, e o disparo com perguntas reais.Validate and test (see the lab): the format with a linter, and the triggering with real prompts.

Exemplo completo: uma skill de revisão de código. Estrutura:A complete example: a code review skill. Structure:

reviewing-code/
├── SKILL.md                      # obrigatório: metadados + procedimento
├── scripts/changed-files.sh      # roda, não é lido: lista os arquivos alterados
└── references/security-checklist.md   # só é lido se a mudança tocar em segurança
---
name: reviewing-code
description: Reviews a code change (a diff, branch or pull request) and reports findings ranked by severity. Use when the user asks to review code, a PR or a diff, or says "look over my changes", even if they never say "review".
---

# Reviewing code

## Steps

1. Get the change: run `scripts/changed-files.sh` and read every listed file in full, not only the diff lines.
2. Check in this order: correctness bugs, security, tests, readability.
   - If the change touches authentication, input parsing, SQL, file paths or secrets, read `references/security-checklist.md` first.
3. Report with the template below. Do not edit files unless the user asks.

## Gotchas

- Lockfiles, `dist/` and generated code are not reviewed; say they were skipped.
- A missing test is a finding only if the changed behaviour is observable. Do not demand tests for renames.
- Never mark something "critical" without naming the input that triggers it.

## Output template

```markdown
## Summary
[one sentence: what the change does and your verdict]

## Findings
- **[critical|major|minor] file:line** — what is wrong, the input that triggers it, a suggested fix

## Not reviewed
[files skipped and why]
```
  • A descrição diz o que faz (“revisa uma mudança e reporta por severidade”) e quando usar, inclusive quando o usuário não diz a palavra “review” (“olha as minhas mudanças”).The description says what it does (“reviews a change and reports by severity”) and when to use it, including when the user does not say the word “review” (“look over my changes”).
  • Os passos dão uma ordem (bugs, segurança, testes, legibilidade) e um gatilho para o arquivo de apoio: “se a mudança toca autenticação, SQL, arquivos ou segredos, leia references/security-checklist.md”. É melhor do que um genérico “veja references/”.The steps give an order (bugs, security, tests, readability) and a trigger for the supporting file: “if the change touches authentication, SQL, files or secrets, read references/security-checklist.md”. That beats a generic “see references/”.
  • As armadilhas são correções concretas (“lockfiles não se revisam”, “nunca marque como crítico sem dizer a entrada que dispara”). Sempre que você precisar corrigir o agente numa revisão, acrescente a correção aqui: é o jeito mais direto de melhorar uma skill.The gotchas are concrete corrections (“lockfiles are not reviewed”, “never mark critical without naming the triggering input”). Whenever you have to correct the agent in a review, add the correction here: it is the most direct way to improve a skill.
  • O modelo de saída garante que toda revisão tenha o mesmo formato.The output template guarantees every review has the same format.

Quando dividir uma skill em duas (ou juntar)When to split a skill in two (or merge)

A especificação compara a escolha ao desenho de uma função: uma skill deve ser uma unidade coerente de trabalho que se combina bem com as outras. Estreita demais, e várias skills precisam carregar para uma só tarefa, com custo de contexto e instruções que se contradizem. Larga demais, e fica difícil de ativar com precisão (o exemplo oficial: uma skill que consulta um banco e formata o resultado é uma unidade; se ela também faz administração do banco, está tentando fazer demais).The specification compares the choice to function design: a skill should be a coherent unit of work that composes well with the others. Too narrow, and several skills must load for a single task, costing context and giving contradicting instructions. Too broad, and it becomes hard to activate precisely (the official example: a skill that queries a database and formats the result is one unit; if it also does database administration, it is trying to do too much).

# Writing functional requirements

1. Ask at most five clarifying questions, only about things that change the behaviour (who, trigger, data, failure case, limits). If the user already answered, skip them.
2. Write each requirement as one observable behaviour, using the template in `assets/requirement-template.md`.
3. Give every requirement acceptance criteria in Given / When / Then form.
4. End with an "Open questions" list. Do not guess answers to them.
5. Do not propose a design, a database schema or code.

## Gotchas

- "Fast", "easy" and "secure" are not requirements until they have a number or a test.
- One requirement, one behaviour: split any requirement that contains "and".

Segurança, somente leitura. Os campos opcionais license, compatibility e allowed-tools da especificação deixam o limite explícito, e o corpo repete a regra em palavras, porque allowed-tools tem suporte variável entre agentes:Security, read only. The specification's optional license, compatibility and allowed-tools fields make the limit explicit, and the body repeats the rule in words, because allowed-tools has varying support across agents:

description: Audits code or configuration for security weaknesses and reports them without changing anything. Use when the user asks for a security review, threat check, or whether something is safe to expose, or touches authentication, secrets, uploads or user input.
license: MIT
compatibility: Read-only. Needs only file reading and search; no network access.

---

# Reviewing security

Report only. Never edit files, run the application or contact the network.

1. List the entry points (routes, handlers, CLI arguments, files read) and the data each one trusts.
2. For each, check: input validation, authentication and authorisation, secrets handling, injection (SQL, shell, path), and error messages.
3. Rank findings by exploitability: name the exact input or request that triggers each one. A finding without a trigger is a "note", not a finding.
4. End with what you could not check.

Note que ela repete a restrição no texto (“Report only. Never edit files…”). É um cinto e suspensório: o campo pede ao agente que restrinja as ferramentas, e o texto diz ao modelo o que fazer mesmo onde o campo não é respeitado. Nenhum dos dois é uma garantia (veja segurança).Note that it repeats the restriction in the text (“Report only. Never edit files…”). It is belt and braces: the field asks the agent to restrict tools, and the text tells the model what to do even where the field is not honoured. Neither is a guarantee (see security).

Este linter (só biblioteca padrão e PyYAML) confere o que a especificação exige: nome, descrição, tamanhos, links de apoio.This linter (standard library and PyYAML only) checks what the specification requires: name, description, sizes, supporting links.

#!/usr/bin/env python3
"""Minimal Agent Skills linter (follows agentskills.io/specification). Not the official skills-ref."""
import re, sys, pathlib
import yaml

SPEC_FIELDS = {"name", "description", "license", "compatibility", "metadata", "allowed-tools"}

def lint(d):
    errors, warns = [], []
    f = d / "SKILL.md"
    if not f.is_file():
        return [f"{d}: SKILL.md not found (name it exactly SKILL.md)"], []
    text = f.read_text()
    m = re.match(r"---\n(.*?)\n---\n(.*)", text, re.S)
    if not m:
        return [f"{f}: frontmatter must start on line 1 between --- markers"], []
    try:
        fm = yaml.safe_load(m.group(1)) or {}
    except yaml.YAMLError as e:
        return [f"{f}: invalid YAML: {e}"], []
    body = m.group(2)
    name, desc = fm.get("name"), fm.get("description")
    if not isinstance(name, str) or not re.fullmatch(r"[a-z0-9]+(-[a-z0-9]+)*", name) or len(name) > 64:
        errors.append(f"name {name!r}: 1-64 chars, lowercase letters/digits, single hyphens, no leading/trailing hyphen")
    elif name != d.name:
        errors.append(f"name {name!r} must match the folder name {d.name!r}")
    if not isinstance(desc, str) or not desc.strip():
        errors.append("description: required and non-empty")
    elif len(desc) > 1024:
        errors.append(f"description: {len(desc)} chars, max 1024")
    if "compatibility" in fm and not (isinstance(fm["compatibility"], str) and 1 <= len(fm["compatibility"]) <= 500):
        errors.append("compatibility: 1-500 chars")
    if "metadata" in fm and not (isinstance(fm["metadata"], dict) and all(isinstance(k, str) and isinstance(v, str) for k, v in fm["metadata"].items())):
        errors.append("metadata: must map strings to strings")
    for k in fm.keys() - SPEC_FIELDS:
        warns.append(f"field '{k}' is not in the open spec (fine if one agent uses it, ignored or rejected by others)")
    if isinstance(desc, str) and not re.search(r"\b(use when|use this|when the user|use only when)\b", desc, re.I):
        warns.append("description: no 'use when ...' trigger found (heuristic)")
    if len(text.splitlines()) > 500:
        warns.append(f"SKILL.md has {len(text.splitlines())} lines: keep under 500 (move detail to references/)")
    for link in re.findall(r"\]\(([^)#]+)\)", body):
        if not link.startswith(("http", "mailto")) and not (d / link).exists():
            errors.append(f"link to '{link}' does not exist")
    return errors, warns

bad = 0
for p in sys.argv[1:]:
    d = pathlib.Path(p).resolve()
    errs, warns = lint(d)
    print(f"{'FAIL' if errs else 'ok  '} {d.name}")
    for e in errs: print(f"   error: {e}")
    for w in warns: print(f"   warn:  {w}")
    bad += bool(errs)
sys.exit(1 if bad else 0)

Atividade 3: testar o disparo (roteiro, não executada)Activity 3: test triggering (script, not run)

Uma skill só ajuda se for ativada. A orientação oficial é montar cerca de 20 perguntas reais, metade que devem disparar a skill e metade que não devem, e rodar cada uma algumas vezes (o modelo não é determinístico). [
  { "query": "can you look over my changes on the feat/login branch before I open the PR?", "should_trigger": true },
