Web apps, protected end to end.

From HTTPS and security headers to stateful sessions, stateless JWTs, CSRF, injection — and the new frontier of AI agent security.

HTTP e HTTPS: a baseHTTP and HTTPS: the base

Onde esta nota se encaixa: é a etapa 1 da trilha de cibersegurança para quem programa (segurança de aplicações, o ponto de partida recomendado para um dev). Para ver as mesmas falhas do lado de quem ataca, siga para a nota de red team; as bases de rede estão na nota de segurança e redes.Where this note fits: it is stage 1 of the cybersecurity path for developers (application security, the recommended starting point for a developer). To see the same flaws from the attacker's side, go on to the red team note; the network fundamentals are in the security and networking note.

Esta nota é o lado de dentro da muralha: como proteger a aplicação web que você constrói, não como atacar a de outra pessoa (isso fica na nota de Red Team). O fio condutor é simples: HTTP é um protocolo de texto, sem memória entre uma requisição e a próxima; tudo que chamamos de "segurança de app web" é uma camada de proteções em cima dessa base simples — cifrar o transporte, autenticar quem está do outro lado, lembrar quem é quem entre requisições, e desconfiar de qualquer dado que entra.This note is the inside of the wall: how to protect the web app you build, not how to attack someone else's (that is the Red Team note). The thread running through it is simple: HTTP is a text protocol with no memory between one request and the next; everything we call "web app security" is a layer of protections on top of that simple base — encrypting the transport, authenticating who is on the other side, remembering who is who between requests, and distrusting any data that comes in.

HTTP e HTTPS: a mesma coisa, uma delas cifradaHTTP and HTTPS: the same thing, one of them encrypted

HTTP descreve o que é trocado (método, cabeçalhos, corpo); HTTPS é HTTP rodando dentro de uma conexão TLS, que cifra e autentica o transporte. A nota de segurança e redes já mostrou isso na prática: uma captura de pacotes da porta 80 mostra a requisição em texto puro; da porta 443, só ruído. TLS resolve três problemas de uma vez:HTTP describes what is exchanged (method, headers, body); HTTPS is HTTP running inside a TLS connection, which encrypts and authenticates the transport. The security and networking note already showed this in practice: a packet capture of port 80 shows the request in plain text; of port 443, just noise. TLS solves three problems at once:

ConfidencialidadeConfidentialityninguém no meio do caminho lê o conteúdo (cookies, senhas, tokens)nobody along the way can read the content (cookies, passwords, tokens)
IntegridadeIntegrityninguém no meio do caminho altera o conteúdo sem ser percebidonobody along the way can alter the content undetected
AutenticidadeAuthenticityo certificado prova que você está falando com o servidor certo, não um impostor (o "s" de HTTPS)the certificate proves you are talking to the right server, not an impostor (the "s" in HTTPS)
HTTPS protege o transporte. Ele não impede SQL injection, não impede XSS, não valida nada que o usuário digita. É a base, não a proteção inteira — o resto desta nota cobre o que vem depois do TLS.HTTPS protects the transport. It does not prevent SQL injection, does not prevent XSS, does not validate anything the user types. It is the foundation, not the whole protection — the rest of this note covers what comes after TLS.

Cabeçalhos de segurança: do básico ao seu próprioSecurity headers: from the basics to your own

O navegador obedece a instruções que o SERVIDOR manda em cabeçalhos HTTP de resposta. Um punhado deles fecha a maior parte das portas de ataque mais comuns, de graça, sem mudar uma linha de lógica de negócio.The browser obeys instructions the SERVER sends in HTTP response headers. A handful of them close most of the common attack doors, for free, without changing a line of business logic.

CORS: a exceção controlada à regra de mesma origemCORS: the controlled exception to same-origin

Por padrão, o navegador bloqueia JavaScript de um site lendo a resposta de outro (a same-origin policy). Access-Control-Allow-Origin e companhia são o jeito do SERVIDOR abrir uma exceção explícita para origens específicas. Access-Control-Allow-Origin: * é seguro para uma API pública e sem cookies; para uma API autenticada, liste as origens exatas e use Access-Control-Allow-Credentials: true só quando precisar enviar cookies entre origens.By default, the browser blocks JavaScript from one site reading another site's response (the same-origin policy). Access-Control-Allow-Origin and friends are how the SERVER opens an explicit exception for specific origins. Access-Control-Allow-Origin: * is fine for a public, cookie-free API; for an authenticated API, list exact origins and use Access-Control-Allow-Credentials: true only when you need to send cookies cross-origin.

Como um cabeçalho funciona (e por que o navegador obedece)How a header works (and why the browser obeys)

Toda resposta HTTP tem três partes: a linha de status, os cabeçalhos (pares Nome: valor, um por linha) e o corpo. Os cabeçalhos de segurança são instruções que o servidor escreve nessa área e que o navegador escolhe cumprir: ele não pergunta se faz sentido, só aplica. Por isso eles protegem tão bem — e por isso só protegem quem usa um navegador moderno (um curl ou um atacante com script próprio ignora todos).Every HTTP response has three parts: the status line, the headers (Name: value pairs, one per line) and the body. Security headers are instructions the server writes in that area and the browser chooses to follow: it does not ask whether they make sense, it just applies them. That is why they protect so well — and why they only protect people on a modern browser (a curl or an attacker with their own script ignores all of them).

HTTP/2 200
content-type: text/html; charset=utf-8
strict-transport-security: max-age=63072000; includeSubDomains
content-security-policy: default-src 'self'; frame-ancestors 'none'
x-content-type-options: nosniff
referrer-policy: strict-origin-when-cross-origin

<!doctype html>...

Três lugares podem escrever esses cabeçalhos, e vale escolher um só como dono de cada um para não duplicar nem se contradizer: (1) o código da aplicação (middleware), que enxerga a requisição e pode variar por rota ou gerar um valor por resposta, como um nonce; (2) o proxy reverso (Nginx, Caddy), bom para o que vale para o site inteiro; (3) a CDN/edge (Cloudflare, CloudFront), que cobre também arquivos estáticos. Cabeçalhos devem ir em todas as respostas — inclusive erros 404/500 e arquivos estáticos.Three places can write these headers, and it pays to pick one owner for each so they neither duplicate nor contradict: (1) the application code (middleware), which sees the request and can vary per route or generate a per-response value such as a nonce; (2) the reverse proxy (Nginx, Caddy), good for what applies to the whole site; (3) the CDN/edge (Cloudflare, CloudFront), which also covers static files. Headers belong on every response — including 404/500 errors and static files.

HSTS: como não se trancar para foraHSTS: how not to lock yourself out

O Strict-Transport-Security faz o navegador lembrar, por max-age segundos, que aquele domínio só fala HTTPS. includeSubDomains estende a regra a todos os subdomínios, e preload pede para entrar numa lista embutida nos navegadores, valendo até na primeira visita. O risco é real: se um subdomínio ainda só tem HTTP, ele some para quem já recebeu o cabeçalho, e desfazer preload leva meses. O caminho seguro é subir aos poucos: max-age=300 (5 min) → um dia → um mês → dois anos, só avançando quando nada quebrou.The Strict-Transport-Security header makes the browser remember, for max-age seconds, that the domain only speaks HTTPS. includeSubDomains extends the rule to every subdomain, and preload asks to join a list built into browsers, effective even on the first visit. The risk is real: if a subdomain is still HTTP-only, it disappears for anyone who already received the header, and undoing preload takes months. The safe path is to ramp up: max-age=300 (5 min) → one day → one month → two years, advancing only when nothing broke.

CSP passo a passoCSP step by step

A Content Security Policy é uma lista de diretivas separadas por ;, cada uma dizendo de onde um tipo de recurso pode vir. Se algo não está na lista, o navegador bloqueia — então, mesmo que um atacante consiga injetar um <script> na página (XSS), ele não roda.The Content Security Policy is a list of directives separated by ;, each saying where a type of resource may come from. If something is not on the list, the browser blocks it — so even if an attacker manages to inject a <script> into the page (XSS), it does not run.

DiretivaDirectivePara que serveWhat it is for
default-srcreserva: vale para toda diretiva de recurso que você não definiufallback: applies to every resource directive you did not define
script-srcde onde scripts podem vir — a diretiva anti-XSS principalwhere scripts may come from — the main anti-XSS directive
object-src 'none'bloqueia <object> e <embed> (plugins)blocks <object> and <embed> (plugins)
base-uri 'none'impede que um <base> injetado redirecione links relativosstops an injected <base> from redirecting relative links
frame-ancestorsquem pode colocar sua página num iframe; substitui o X-Frame-Options (anti-clickjacking)who may put your page in an iframe; replaces X-Frame-Options (anti-clickjacking)
form-actionpara onde formulários podem enviar dadoswhere forms may submit data
report-toendpoint que recebe os relatórios de violaçãoendpoint that receives violation reports

Listar domínios permitidos ("allowlist") é frágil: basta um domínio da lista hospedar um script qualquer para furar a regra. A forma moderna, chamada CSP estrita, usa um nonce (valor aleatório gerado a cada resposta, repetido no cabeçalho e no atributo nonce das tags permitidas) ou um hash do conteúdo do script. O atacante não consegue adivinhar o nonce, então o script injetado dele não roda. 'strict-dynamic' estende a confiança de um script com nonce aos scripts que ele carrega.Listing allowed domains (an "allowlist") is fragile: one listed domain hosting any script is enough to bypass the rule. The modern way, called a strict CSP, uses a nonce (a random value generated per response, repeated in the header and in the nonce attribute of the permitted tags) or a hash of the script content. The attacker cannot guess the nonce, so their injected script does not run. 'strict-dynamic' extends trust from a nonce-tagged script to the scripts it loads.

Content-Security-Policy:
  script-src 'nonce-R4nd0m...' 'strict-dynamic';
  object-src 'none';
  base-uri 'none';
  frame-ancestors 'none'

<script nonce="R4nd0m...">/* roda */</script>
<script>/* injetado pelo atacante: bloqueado */</script>
Adote em duas etapas. Primeiro envie a política como Content-Security-Policy-Report-Only: nada é bloqueado, mas o navegador relata cada violação (declare o destino com Reporting-Endpoints e report-to). Quando os relatórios ficarem limpos, troque o nome do cabeçalho para Content-Security-Policy e passe a aplicar. E lembre: a CSP complementa a validação e o escape de saída, não os substitui.Adopt it in two stages. First send the policy as Content-Security-Policy-Report-Only: nothing is blocked, but the browser reports each violation (declare the destination with Reporting-Endpoints and report-to). When the reports are clean, rename the header to Content-Security-Policy and start enforcing. And remember: CSP complements input validation and output escaping, it does not replace them.

Criando o seu próprio cabeçalho (middleware)Creating your own header (middleware)

"Criar um cabeçalho" tem dois sentidos. O primeiro, e mais comum: escrever o seu próprio middleware que aplica o conjunto de segurança em toda resposta (é isso que o helmet faz por baixo). O segundo: inventar um cabeçalho seu, como um identificador de requisição. Os dois cabem no mesmo código:"Creating a header" has two meanings. The first, and most common: writing your own middleware that applies the security set to every response (that is what helmet does under the hood). The second: inventing a header of your own, such as a request identifier. Both fit in the same code:

// security-headers.js — middleware para Express
const crypto = require('node:crypto');

module.exports = function securityHeaders(req, res, next) {
  // 1) valor por resposta: nonce da CSP, exposto às views
  const nonce = crypto.randomBytes(16).toString('base64');
  res.locals.cspNonce = nonce;

  // 2) o conjunto de segurança
  res.set({
    'Strict-Transport-Security': 'max-age=63072000; includeSubDomains',
    'Content-Security-Policy': [
      "default-src 'self'",
      `script-src 'nonce-${nonce}' 'strict-dynamic'`,
      "object-src 'none'",
      "base-uri 'none'",
      "frame-ancestors 'none'",
    ].join('; '),
    'X-Content-Type-Options': 'nosniff',
    'Referrer-Policy': 'strict-origin-when-cross-origin',
    'Permissions-Policy': 'camera=(), microphone=(), geolocation=()',
    'Cross-Origin-Opener-Policy': 'same-origin',
  });

  // 3) um cabeçalho SEU: id de correlação para achar a requisição nos logs
  const id = req.get('X-Request-Id') || crypto.randomUUID();
  res.set('X-Request-Id', id);

  next();
};

// app.js
const express = require('express');
const app = express();
app.disable('x-powered-by');          // remove o cabeçalho que entrega o framework
app.use(require('./security-headers'));

Regras para um cabeçalho que você inventa:Rules for a header you invent:

  • Nome: palavras separadas por hífen, sem diferenciar maiúsculas de minúsculas. O prefixo X- foi desencorajado pela RFC 6648; para um cabeçalho novo, prefira um nome descritivo (ex.: Request-Id) ou um prefixo da sua empresa.Name: hyphen-separated words, case-insensitive. The X- prefix was deprecated by RFC 6648; for a new header prefer a descriptive name (e.g. Request-Id) or a company prefix.
  • Nunca coloque segredo ou dado pessoal num valor: cabeçalhos vão para logs, proxies e CDNs.Never put a secret or personal data in a value: headers end up in logs, proxies and CDNs.
  • Entre origens (CORS): para o JavaScript de outro site enviar seu cabeçalho, o servidor precisa listá-lo em Access-Control-Allow-Headers; para ler o cabeçalho da resposta, em Access-Control-Expose-Headers.Across origins (CORS): for another site's JavaScript to send your header, the server must list it in Access-Control-Allow-Headers; to read a response header, in Access-Control-Expose-Headers.
  • Valide o que entra: um cabeçalho de requisição é entrada do usuário como qualquer outra — nunca o repita na resposta sem validar (risco de injeção de cabeçalho/CRLF).Validate what comes in: a request header is user input like any other — never echo it into a response without validating it (header/CRLF injection risk).

Em Next.js: next.config.js e proxy.tsIn Next.js: next.config.js and proxy.ts

No Next.js, cabeçalhos fixos vão na chave headers() do next.config.js; cabeçalhos por requisição (como o nonce da CSP) vão no proxy.ts (o antigo middleware.ts). A documentação oficial recomenda este formato:In Next.js, fixed headers go in the headers() key of next.config.js; per-request headers (such as the CSP nonce) go in proxy.ts (the former middleware.ts). The official docs recommend this shape:

// next.config.js — cabeçalhos fixos
module.exports = {
  poweredByHeader: false,   // tira o X-Powered-By: Next.js
  async headers() {
    return [
      {
        source: '/(.*)',
        headers: [
          { key: 'Strict-Transport-Security', value: 'max-age=63072000; includeSubDomains' },
          { key: 'X-Content-Type-Options', value: 'nosniff' },
          { key: 'Referrer-Policy', value: 'strict-origin-when-cross-origin' },
          { key: 'Permissions-Policy', value: 'camera=(), microphone=(), geolocation=()' },
        ],
      },
    ];
  },
};
// proxy.ts — nonce novo a cada requisição
import { NextRequest, NextResponse } from 'next/server';

export function proxy(request: NextRequest) {
  const nonce = Buffer.from(crypto.randomUUID()).toString('base64');
  const isDev = process.env.NODE_ENV === 'development';
  const csp = `
    default-src 'self';
    script-src 'self' 'nonce-${nonce}' 'strict-dynamic'${isDev ? " 'unsafe-eval'" : ''};
    style-src 'self' 'nonce-${nonce}';
    img-src 'self' blob: data:;
    object-src 'none';
    base-uri 'self';
    form-action 'self';
    frame-ancestors 'none';
    upgrade-insecure-requests;
  `.replace(/\s{2,}/g, ' ').trim();

  const requestHeaders = new Headers(request.headers);
  requestHeaders.set('x-nonce', nonce);
  requestHeaders.set('Content-Security-Policy', csp);

  const response = NextResponse.next({ request: { headers: requestHeaders } });
  response.headers.set('Content-Security-Policy', csp);
  return response;
}
Nonce exige renderização dinâmica: o HTML é gerado a cada requisição, então páginas estáticas, ISR e cache de CDN deixam de valer, e o Partial Prerendering é incompatível. Se precisa manter geração estática, a alternativa (experimental, só App Router) é a CSP com hashes via Subresource Integrity (experimental.sri). Em desenvolvimento o React precisa de 'unsafe-eval'; em produção, não.A nonce requires dynamic rendering: the HTML is generated on every request, so static pages, ISR and CDN caching stop applying, and Partial Prerendering is incompatible. If you need to keep static generation, the alternative (experimental, App Router only) is a hash-based CSP through Subresource Integrity (experimental.sri). In development React needs 'unsafe-eval'; in production it does not.

Em Nginx (proxy reverso)In Nginx (reverse proxy)

server {
  listen 443 ssl;
  server_tokens off;                      # esconde a versão do Nginx
  add_header Strict-Transport-Security "max-age=63072000; includeSubDomains" always;
  add_header X-Content-Type-Options "nosniff" always;
  add_header Referrer-Policy "strict-origin-when-cross-origin" always;
  add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;
  proxy_hide_header X-Powered-By;         # remove o que o app vazou
}

O always é o detalhe que mais se esquece: sem ele o Nginx só adiciona o cabeçalho em respostas 2xx/3xx, e as páginas de erro ficam sem proteção. Outra pegadinha: um add_header declarado dentro de um location substitui os do bloco pai, em vez de somá-los.The always is the detail most often forgotten: without it Nginx only adds the header on 2xx/3xx responses, and error pages go unprotected. Another gotcha: an add_header declared inside a location replaces the parent block's, instead of adding to them.

Cookies: os três atributos que importamCookies: the three attributes that matter

Um cookie é um pedacinho de texto que o servidor pede ao navegador para guardar e devolver em toda requisição futura ao mesmo site. É o mecanismo mais comum para "lembrar" quem está logado — e, mal configurado, uma das formas mais fáceis de vazar uma sessão inteira.A cookie is a small piece of text the server asks the browser to store and send back on every future request to the same site. It is the most common mechanism to "remember" who is logged in — and, misconfigured, one of the easiest ways to leak a whole session.

Fixação de sessãoSession fixation

Um ataque simples: o atacante planta um ID de sessão conhecido na vítima (por um link, ou porque o site aceita qualquer ID enviado) e espera ela fazer login — se o site mantém o MESMO ID depois do login, o atacante agora está "logado" também. A defesa: sempre gerar um ID de sessão novo no momento do login (e de novo em qualquer mudança de privilégio), nunca aceitar um ID de sessão que já veio do cliente antes de autenticar.A simple attack: the attacker plants a known session ID on the victim (via a link, or because the site accepts any submitted ID) and waits for them to log in — if the site keeps the SAME ID after login, the attacker is now "logged in" too. The defence: always generate a new session ID at the moment of login (and again on any privilege change), never accept a session ID that arrived from the client before authenticating.

Autenticação stateful: sessões no servidorStateful authentication: server-side sessions

Autenticação stateful (com estado): o servidor guarda, num banco ou cache (Redis é o padrão de mercado), um registro de cada sessão ativa. O cookie carrega só um ID opaco e aleatório — o resto da informação (quem é o usuário, quando expira) fica no servidor.Stateful authentication: the server keeps, in a database or cache (Redis is the market standard), a record of each active session. The cookie carries only an opaque, random ID — the rest of the information (who the user is, when it expires) lives on the server.

Autenticação stateless: JWT, access e refreshStateless authentication: JWT, access and refresh

Autenticação stateless (sem estado): em vez de um ID opaco, o servidor assina um token que carrega os dados nele mesmo — tipicamente um JWT (JSON Web Token). Qualquer servidor que conheça a chave de assinatura pode validar o token sozinho, sem consultar banco nenhum. É o modelo padrão para APIs e microsserviços, e para SPAs que falam com uma API separada.Stateless authentication: instead of an opaque ID, the server signs a token that carries the data inside itself — typically a JWT (JSON Web Token). Any server that knows the signing key can validate the token on its own, with no database lookup. It is the standard model for APIs and microservices, and for SPAs talking to a separate API.

Rotação de refresh token e detecção de reusoRefresh token rotation and reuse detection

A cada uso, o refresh token é TROCADO por um novo, e o antigo é invalidado. Se o antigo aparecer de novo (alguém tentando reusar um token roubado, ou uma cópia antiga), isso significa que ele vazou — a resposta correta é revogar a CADEIA inteira daquele token, derrubando a sessão.On every use, the refresh token is SWAPPED for a new one, and the old one is invalidated. If the old one shows up again (someone trying to reuse a stolen token, or an old copy), that means it leaked — the correct response is to revoke the WHOLE chain for that token, killing the session.

# pseudocódigo do endpoint de refresh
POST /refresh  (cookie: refresh_token=rt_antigo)
  1. valida assinatura e expiração de rt_antigo
  2. rt_antigo já foi usado antes (está na lista de "já trocados")?
       SIM -> REUSO DETECTADO: revoga toda a família de tokens desse usuário, força novo login
       NÃO -> gera access_token novo (minutos) + refresh_token novo (dias)
              marca rt_antigo como "já trocado", responde com os dois
Diferente do modelo stateful, revogar um JWT antes do tempo é difícil por definição — ele é válido até expirar, mesmo que o usuário troque a senha. Por isso: access tokens CURTOS (minutos) e, se precisar revogar de verdade e na hora, uma lista de bloqueio (denylist) consultada nas rotas sensíveis, ou volte para sessões stateful nelas.Unlike the stateful model, revoking a JWT early is hard by definition — it is valid until it expires, even if the user changes their password. Hence: SHORT access tokens (minutes) and, if you need to revoke immediately for real, a denylist checked on sensitive routes, or fall back to stateful sessions there.

CSRF: o pedido que você não pediuCSRF: the request you did not ask for

SQL injection e XSS: o lado de quem constróiSQL injection and XSS: the builder's side

Confiar em qualquer dado que entra de fora é a raiz da maioria das falhas de aplicação web. As duas mais comuns já apareceram na nota de Red Team do ponto de vista de quem ataca; aqui é o lado de quem constrói.Trusting any data that comes in from outside is the root of most web application flaws. The two most common ones already showed up in the Red Team note from the attacker's side; here is the builder's side.

SQL injection: nunca monte SQL colando textoSQL injection: never build SQL by pasting text

-- NUNCA: concatena a entrada direto na consulta
const query = `SELECT * FROM usuarios WHERE email = '${emailDoFormulario}'`;

-- SEMPRE: consulta parametrizada — a entrada é um VALOR, nunca parte do comando
SELECT * FROM usuarios WHERE email = $1;   -- Postgres (driver node-postgres, por exemplo)

Veja a nota de Postgres para os comandos e a seção de exploração da nota de Red Team para como essa falha é usada do outro lado. ORMs (Prisma, SQLAlchemy, ActiveRecord) fazem isso por padrão — o risco real aparece quando alguém usa SQL "cru" dentro do ORM para um caso especial e esquece de parametrizar.See the Postgres note for commands and the Red Team note's exploitation section for how this flaw is used from the other side. ORMs (Prisma, SQLAlchemy, ActiveRecord) do this by default — the real risk shows up when someone drops down to "raw" SQL inside the ORM for a special case and forgets to parameterise.

XSS: escapar saída, não só validar entradaXSS: escape output, not just validate input

Frameworks modernos (React, Vue, Angular) escapam a saída por padrão quando você usa a sintaxe normal de template — o perigo mora nas "válvulas de escape" que pulam essa proteção de propósito.Modern frameworks (React, Vue, Angular) escape output by default when you use their normal template syntax — the danger lives in the "escape hatches" that skip that protection on purpose.

// React: ESCAPADO automaticamente, seguro mesmo se bio vier de um usuário
<p>{usuario.bio}</p>

// React: a válvula de escape — NUNCA com texto de usuário sem sanitizar antes
<div dangerouslySetInnerHTML={{ __html: usuario.bio }} />

Se você realmente precisa renderizar HTML vindo do usuário (um editor rich-text, por exemplo), sanitize com uma biblioteca testada para isso (como DOMPurify) — nunca confie em regex caseira para "limpar" HTML.If you genuinely need to render user-supplied HTML (a rich-text editor, for example), sanitise it with a battle-tested library (like DOMPurify) — never trust a homemade regex to "clean" HTML.

Uma checklist curtaA short checklist

  • Toda consulta com dado externo é parametrizada; nenhum SQL é montado por concatenação de string.Every query with external data is parameterised; no SQL is built by string concatenation.
  • Toda saída em HTML usa a escapagem padrão do framework; dangerouslySetInnerHTML/v-html/|safe só com conteúdo sanitizado.All HTML output uses the framework's default escaping; dangerouslySetInnerHTML/v-html/|safe only with sanitised content.
  • Validação de entrada acontece no SERVIDOR, mesmo que também exista no navegador (o navegador é só conforto para o usuário, não é segurança).Input validation happens on the SERVER, even if it also exists in the browser (the browser is just user convenience, not security).
  • Um WAF e um Content-Security-Policy são camadas extras, nunca a única defesa.A WAF and a Content-Security-Policy are extra layers, never the only defence.

A nova fronteira: segurança de agentes de IAThe new frontier: AI agent security

Tudo até aqui assume que quem fala com a sua aplicação é um navegador controlado por uma pessoa. A nova peça é um agente de IA: um modelo de linguagem que lê conteúdo, decide, e age — chama APIs, roda código, lê e-mails, usa ferramentas via protocolos como o MCP (Model Context Protocol). Isso muda o modelo de ameaça: o "usuário" que manda instruções pode agora ser um texto que o próprio agente leu em algum lugar.Everything so far assumes whoever talks to your application is a browser controlled by a person. The new piece is an AI agent: a language model that reads content, decides, and acts — calls APIs, runs code, reads emails, uses tools through protocols like MCP (Model Context Protocol). This changes the threat model: the "user" issuing instructions can now be a piece of text the agent itself read somewhere.

O que o HTTPS protege, e o que ele NÃO protege?What does HTTPS protect, and what does it NOT protect?Protege o transporte (confidencialidade, integridade, autenticidade); não protege contra SQL injection, XSS ou entrada não validada.It protects the transport (confidentiality, integrity, authenticity); it does not protect against SQL injection, XSS or unvalidated input.
Qual cabeçalho é a defesa mais forte do navegador contra XSS?Which header is the browser's strongest defence against XSS?Content-Security-Policy.Content-Security-Policy.
Por que SameSite=None num cookie de autenticação é um sinal de alerta?Why is SameSite=None on an authentication cookie a red flag?Porque o cookie passa a viajar em requisições de QUALQUER origem, abrindo a porta para CSRF.Because the cookie starts travelling on requests from ANY origin, opening the door to CSRF.
Qual a diferença central entre revogar uma sessão stateful e um JWT?What is the key difference between revoking a stateful session and a JWT?Sessão: apagar uma linha no servidor. JWT: válido até expirar, a menos que haja uma denylist.Session: delete a row on the server. JWT: valid until it expires, unless there is a denylist.
Por que o access token deveria ter vida curta?Why should the access token be short-lived?Porque não dá para revogá-lo antes da hora; uma vida curta limita o estrago de um vazamento.Because it cannot be revoked early; a short life limits the damage of a leak.
O que diferencia prompt injection direta de indireta?What tells direct and indirect prompt injection apart?Direta: o usuário escreve a instrução maliciosa. Indireta: ela está escondida em algo que o agente lê (e-mail, página, ferramenta).Direct: the user types the malicious instruction. Indirect: it is hidden in something the agent reads (email, page, tool).
Por que um bom RAG não resolve prompt injection?Why doesn't a good RAG fix prompt injection?Porque aterra o modelo em dados melhores, mas não o protege de instruções hostis escondidas nesses mesmos dados.Because it grounds the model in better data, but does not protect it from hostile instructions hidden in that same data.
