CI/CD

Deploy from GitHub to AWS, without stored keys.

A push to develop or main deploys to the matching AWS environment, using OpenID Connect instead of long-lived access keys.

Como funcionaHow it works

Em vez de guardar chaves de acesso da AWS nos secrets do GitHub, o GitHub Actions emite um token OIDC de curta duração para cada execução. A AWS confia no GitHub como provedor de identidade e troca esse token por credenciais temporárias de uma role IAM.Instead of storing AWS access keys in GitHub secrets, GitHub Actions issues a short-lived OIDC token for each run. AWS trusts GitHub as an identity provider and exchanges that token for temporary credentials of an IAM role.

  1. O job pede um token ao GitHub (precisa de id-token: write).The job asks GitHub for a token (it needs id-token: write).
  2. A action aws-actions/configure-aws-credentials envia o token à AWS (sts:AssumeRoleWithWebIdentity).The aws-actions/configure-aws-credentials action sends the token to AWS (sts:AssumeRoleWithWebIdentity).
  3. A AWS confere a trust policy da role: emissor, audiência (aud) e quem está pedindo (sub).AWS checks the role’s trust policy: issuer, audience (aud) and who is asking (sub).
  4. Se bater, devolve credenciais temporárias (por padrão, 1 hora) que os passos seguintes usam.If it matches, AWS returns temporary credentials (1 hour by default) that the following steps use.

Não há segredo para vazar nem para rotacionar. O controle de quem pode fazer deploy passa a morar na trust policy.There is no secret to leak or rotate. Control over who can deploy now lives in the trust policy.

O desenhoThe layout

  • Branch develop → ambiente develop na AWS.Branch develop → develop environment on AWS.
  • Branch main → ambiente production na AWS.Branch main → production environment on AWS.
  • Um GitHub Environment por ambiente, cada um com sua role IAM e suas variáveis.One GitHub Environment per environment, each with its own IAM role and variables.

O exemplo faz deploy de uma imagem Docker no Amazon ECR e atualiza um serviço do Amazon ECS, o mesmo caminho das notas de AWS. Se o seu destino for outro (S3, EC2, Lambda), as etapas 1 a 3 não mudam; só as permissões da role e os passos de deploy do workflow.The example deploys a Docker image to Amazon ECR and updates an Amazon ECS service, the same path as the AWS notes. If your target is something else (S3, EC2, Lambda), steps 1 to 3 stay the same; only the role’s permissions and the workflow’s deploy steps change.

Se develop e produção ficam em contas AWS diferentes, repita as etapas 1 e 2 em cada conta: o provedor OIDC usado na trust policy precisa estar na mesma conta da role.If develop and production live in different AWS accounts, repeat steps 1 and 2 in each account: the OIDC provider used in a trust policy must be in the same account as the role.

1. Provedor OIDC na AWS1. OIDC provider in AWS

O provedor diz à AWS “confio nos tokens emitidos pelo GitHub Actions”. Ele vive dentro de cada conta, então esta etapa é feita duas vezes: uma na conta dev e outra na prod. Uma conta só precisa dele uma vez, não importa quantos repositórios ou roles use.The provider tells AWS “I trust tokens issued by GitHub Actions”. It lives inside each account, so this step is done twice: once in the dev account and once in prod. An account needs it only once, no matter how many repositories or roles use it.

  1. Entre na conta (portal do Identity Center, escolha a conta dev e a role de administrador). Abra IAM → Identity providers → Add provider.Sign in to the account (Identity Center portal, pick the dev account and the administrator role). Open IAM → Identity providers → Add provider.
  2. Em Provider type, escolha OpenID Connect.Under Provider type, choose OpenID Connect.
  3. Provider URL · https://token.actions.githubusercontent.com
  4. Audience · sts.amazonaws.com
  5. Clique em Add provider. Confirme que apareceu na lista, com o ARN arn:aws:iam::<ID_CONTA>:oidc-provider/token.actions.githubusercontent.com.Click Add provider. Confirm it appears in the list, with the ARN arn:aws:iam::<ACCOUNT_ID>:oidc-provider/token.actions.githubusercontent.com.
  6. Troque para a conta prod e repita os passos 1 a 5.Switch to the prod account and repeat steps 1 to 5.

Pela CLI, o comando é o abaixo (confira na referência da CLI se ele pede a lista de thumbprints na sua versão).From the CLI, the command is the one below (check the CLI reference for whether your version asks for a thumbprint list).

for P in dev prod; do
    aws iam create-open-id-connect-provider \
      --url https://token.actions.githubusercontent.com \
      --client-id-list sts.amazonaws.com \
      --profile $P
  done

Se o comando falhar com “EntityAlreadyExists”, o provedor já existe naquela conta e não há nada a fazer.If the command fails with “EntityAlreadyExists”, the provider already exists in that account and there is nothing to do.

Sobre thumbprints: a AWS valida o certificado do endpoint do provedor com a sua biblioteca de autoridades raiz confiáveis, e só recorre aos thumbprints cadastrados se o certificado não for assinado por uma delas.About thumbprints: AWS verifies the provider endpoint’s certificate with its library of trusted root CAs, and only falls back to the configured thumbprints if the certificate is not signed by one of them.

2. Roles IAM e trust policy2. IAM roles and trust policy

Crie uma role por ambiente (por exemplo github-deploy-develop e github-deploy-production). A trust policy diz quem pode assumir a role. A condição em sub é obrigatória: sem ela, qualquer repositório do GitHub poderia pedir acesso.Create one role per environment (for example github-deploy-develop and github-deploy-production). The trust policy says who may assume the role. The sub condition is required: without it, any repository on GitHub could ask for access.

{
    "Version": "2012-10-17",
    "Statement": [
      {
        "Effect": "Allow",
        "Principal": {
          "Federated": "arn:aws:iam::<ACCOUNT_ID>:oidc-provider/token.actions.githubusercontent.com"
        },
        "Action": "sts:AssumeRoleWithWebIdentity",
        "Condition": {
          "StringEquals": {
            "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
            "token.actions.githubusercontent.com:sub": "repo:<ORG>/<REPO>:environment:develop"
          }
        }
      }
    ]
  }

Na role de produção, troque o final do sub por environment:production.On the production role, change the end of sub to environment:production.

Como o sub é montadoHow sub is built

Quando o jobWhen the jobsub
referencia um environmentreferences an environmentrepo:ORG/REPO:environment:NAME
roda de uma branch (sem environment)runs from a branch (no environment)repo:ORG/REPO:ref:refs/heads/BRANCH
roda por pull request (sem environment)runs for a pull request (no environment)repo:ORG/REPO:pull_request
roda de uma tag (sem environment)runs from a tag (no environment)repo:ORG/REPO:ref:refs/tags/TAG
Quando o job referencia um environment, o sub usa a forma environment:NAME e não mais a da branch. Por isso a trust policy acima usa environment:develop, e não ref:refs/heads/develop.When a job references an environment, sub uses the environment:NAME form, not the branch form. That is why the trust policy above uses environment:develop rather than ref:refs/heads/develop.
Repositórios criados depois de 15/07/2026, ou que optaram por isso, usam o formato imutável com IDs do dono e do repositório. Nesse caso uma trust policy só com nomes falha com “Not authorized to perform sts:AssumeRoleWithWebIdentity”. O valor passa a ser, por exemplo: repo:<ORG>@<ORG_ID>/<REPO>@<REPO_ID>:environment:develop.Repositories created after July 15, 2026, or that opted in, use the immutable format with the owner and repository IDs. In that case a name-only trust policy fails with “Not authorized to perform sts:AssumeRoleWithWebIdentity”. The value becomes, for example: repo:<ORG>@<ORG_ID>/<REPO>@<REPO_ID>:environment:develop.

3. Environments no GitHub3. GitHub Environments

Um Environment é a “porta” entre o repositório e uma role da AWS: é nele que ficam as variáveis daquele ambiente e as regras de quem pode fazer deploy. Passo a passo no repositório:An Environment is the “door” between the repository and an AWS role: it holds that environment’s variables and the rules about who may deploy. Step by step in the repository:

  1. Settings → Environments → New environment, nome develop (exatamente igual ao usado no sub da trust policy), Configure environment.Settings → Environments → New environment, name develop (exactly the same as used in the trust policy’s sub), Configure environment.
  2. Em Deployment branches and tags, escolha Selected branches and tags → Add deployment branch or tag rule → develop.Under Deployment branches and tags, choose Selected branches and tags → Add deployment branch or tag rule → develop.
  3. Em Environment variables → Add variable, crie as cinco variáveis abaixo com os valores da conta dev.Under Environment variables → Add variable, create the five variables below with the dev account values.
  4. Volte e crie o environment production: branch permitida main, Required reviewers marcado com quem aprova, e as mesmas cinco variáveis com os valores da conta prod.Go back and create the production environment: allowed branch main, Required reviewers checked with who approves, and the same five variables with the prod account values.

Os nomes das variáveis são iguais nos dois ambientes; o que muda é o valor. É isso que faz o mesmo workflow mandar o develop para uma conta e o main para outra.The variable names are the same in both environments; the value is what changes. That is what makes the same workflow send develop to one account and main to another.

  • Deployment branches. Em develop, permita só a branch develop; em production, só a main. É o que impede outra branch de obter acesso à role.Deployment branches. On develop, allow only the develop branch; on production, only main. This is what stops another branch from reaching the role.
  • Required reviewers em production (até 6 pessoas ou times; basta uma aprovação), se quiser aprovação manual antes do deploy.Required reviewers on production (up to 6 people or teams; one approval is enough), if you want manual approval before deploying.
  • Variables por ambiente: AWS_ROLE_ARN, AWS_REGION, ECR_REPOSITORY, ECS_CLUSTER, ECS_SERVICE. Ficam disponíveis só para jobs que usam o environment, pelo contexto vars.Variables per environment: AWS_ROLE_ARN, AWS_REGION, ECR_REPOSITORY, ECS_CLUSTER, ECS_SERVICE. They are available only to jobs that use the environment, through the vars context.
O ARN de uma role não é segredo, então variáveis bastam: não há chave nenhuma para guardar.A role ARN is not a secret, so variables are enough: there is no key to store.

A AWS recomenda proteger environments usados em políticas OIDC com regras de proteção, como a restrição de branches e tags de deploy.AWS recommends protecting environments used in OIDC policies with protection rules, such as deployment branch and tag restrictions.

4. Secrets: onde ficam e por quê4. Secrets: where they live and why

Pergunta frequente: “a senha do banco vai nos secrets do GitHub ou na AWS?”. Depende de quem precisa ler o valor. Separe três tipos de informação:A common question: “does the database password go in GitHub secrets or in AWS?”. It depends on who needs to read the value. Separate three kinds of information:

O que éWhat it isOnde guardarWhere to keep itPor quêWhy
Credencial da AWS para o deployAWS credential for the deployEm lugar nenhumNowhere (OIDC)O token é emitido por execução e expira. Não existe chave para vazar nem para rotacionar.The token is issued per run and expires. There is no key to leak or rotate.
ARN da role, região, nomes de ECR/cluster/serviçoRole ARN, Region, ECR/cluster/service namesGitHub · Environment variablesNão são segredo e mudam por ambiente. Em variável você consegue ver e conferir o valor.They are not secret and change per environment. In a variable you can see and check the value.
Senha do banco, chaves de API, tokens que a aplicação usa ao rodarDatabase password, API keys, tokens the application uses at runtimeAWS · Secrets Manager (ou SSM Parameter Store SecureString), na conta de cada ambiente(or SSM Parameter Store SecureString), in each environment’s accountQuem lê é o ECS, na hora de iniciar o container, não o pipeline. Veja abaixo.The reader is ECS, when it starts the container, not the pipeline. See below.
Token de terceiro que só o CI usa (registry privado de pacotes, scanner, etc.)Third-party token used only by CI (private package registry, scanner, etc.)GitHub · Environment secrets (ou do repositório)(or repository)A AWS não precisa dele. Só o workflow o lê, então é lá que ele deve ficar.AWS does not need it. Only the workflow reads it, so that is where it belongs.

Por que o segredo da aplicação fica na AWS e não no GitHubWhy the application secret lives in AWS, not GitHub

  • Quem lê é o runtime. A aplicação precisa do valor sempre que uma task sobe: no deploy, mas também em autoscaling, reinício ou troca de host, quando o GitHub não está envolvido. Se o valor só existe nos secrets do GitHub, você teria de reimplantar para qualquer task nova.The reader is the runtime. The application needs the value whenever a task starts: at deploy, but also on autoscaling, restarts or host replacement, when GitHub is not involved. If the value exists only in GitHub secrets, you would have to redeploy for every new task.
  • O pipeline nunca vê o valor. Com o segredo na AWS, o workflow só carrega o ARN dele. Quem tem permissão de rodar workflows (ou uma action de terceiros comprometida) não consegue lê-lo. Segredos do GitHub chegam ao runner como variáveis do job; a documentação avisa que o mascaramento nos logs não é garantido e que valores transformados podem escapar.The pipeline never sees the value. With the secret in AWS, the workflow carries only its ARN. Anyone who can run workflows (or a compromised third-party action) cannot read it. GitHub secrets reach the runner as job variables; the docs warn that log masking is not guaranteed and that transformed values can slip through.
  • Um valor por ambiente, na conta dele. O segredo de prod existe só na conta prod, e o IAM dessa conta decide quem lê. Um desenvolvedor com acesso à dev nunca alcança a senha de produção. O CloudTrail registra cada leitura.One value per environment, in its own account. The prod secret exists only in the prod account, and that account’s IAM decides who reads it. A developer with dev access never reaches the production password. CloudTrail logs every read.
  • Rotação e criptografia nativas. O Secrets Manager rotaciona segredos e criptografa com o KMS. Os secrets do GitHub são criptografados antes de chegar ao GitHub (libsodium), mas ele é um cofre para o CI, sem rotação automática.Native rotation and encryption. Secrets Manager rotates secrets and encrypts them with KMS. GitHub secrets are encrypted before reaching GitHub (libsodium), but it is a vault for CI, with no automatic rotation.
Regra prática: se a aplicação lê, o segredo fica na AWS. Se só o CI lê, fica no GitHub. Se ninguém precisa ler (credencial de deploy), use OIDC e não guarde nada.Rule of thumb: if the application reads it, the secret lives in AWS. If only CI reads it, it lives in GitHub. If nobody needs to read it (deploy credential), use OIDC and store nothing.

Ligando o segredo ao serviço, passo a passoWiring the secret to the service, step by step

  1. Criar o segredo em cada conta, com valores diferentes. Leia o valor de um arquivo ou de um prompt, para não ficar no histórico do shell:Create the secret in each account, with different values. Read the value from a file or a prompt, so it does not stay in shell history: 
    aws secretsmanager create-secret --name meu-app/develop/db \
      --secret-string file://db-develop.json --profile dev
  # db-develop.json: {"username":"app","password":"..."}  (delete the file afterwards)
  2. Dar permissão de leitura à task execution role (não à role de deploy). É ela que o ECS usa para buscar o segredo ao iniciar o container. Acrescente à role, em cada conta, uma política como esta (kms:Decrypt só se o segredo usar uma chave KMS própria):Give read permission to the task execution role (not to the deploy role). It is what ECS uses to fetch the secret when starting the container. Add a policy like this to the role, in each account (kms:Decrypt only if the secret uses a customer managed KMS key): 
    {
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Allow",
      "Action": "secretsmanager:GetSecretValue",
      "Resource": "arn:aws:secretsmanager:<REGION>:<ACCOUNT_ID>:secret:meu-app/develop/db-*"
    }]
  }
  3. Referenciar o segredo no .aws/task-definition.json, em containerDefinitions[].secrets. O ECS injeta o valor como variável de ambiente; o sufixo :password:: escolhe uma chave do JSON:Reference the secret in .aws/task-definition.json, under containerDefinitions[].secrets. ECS injects the value as an environment variable; the :password:: suffix picks one key of the JSON: 
    "secrets": [
    {
      "name": "DB_PASSWORD",
      "valueFrom": "arn:aws:secretsmanager:<REGION>:<ACCOUNT_ID>:secret:meu-app/develop/db-AbCdEf:password::"
    }
  ]
  4. Cuidado com o arquivo único. O task-definition.json é o mesmo nos dois ambientes, mas o ARN do segredo tem o ID da conta e o nome do ambiente. Duas saídas: manter um arquivo por ambiente (.aws/task-definition.develop.json e .production.json) ou nomear o segredo igual nas duas contas e montar o ARN com o ID da conta da variável. O exemplo do workflow usa um arquivo só; adapte o caminho se escolher um por ambiente.Watch out for the single file. task-definition.json is the same in both environments, but the secret ARN contains the account ID and the environment name. Two ways out: keep one file per environment (.aws/task-definition.develop.json and .production.json) or name the secret the same in both accounts and build the ARN with the account ID from a variable. The workflow example uses a single file; adapt the path if you choose one per environment.
  5. Deploy. O workflow não muda. A role de deploy só precisa do iam:PassRole sobre a execution role (já está na política da etapa 2) e não precisa de nenhuma permissão no Secrets Manager.Deploy. The workflow does not change. The deploy role only needs iam:PassRole on the execution role (already in the step 2 policy) and needs no Secrets Manager permission.
O ECS busca o valor quando o container inicia. Se você atualizar ou rotacionar o segredo depois, as tasks em execução não recebem o valor novo: é preciso subir tasks novas (por exemplo, um novo deploy ou “Force new deployment” no serviço). Além disso, a aplicação, os logs e as ferramentas de depuração do container enxergam as variáveis de ambiente.ECS fetches the value when the container starts. If you update or rotate the secret later, running tasks do not get the new value: new tasks must be launched (for example a new deploy or “Force new deployment” on the service). Also, the application, logs and debugging tools in the container can see the environment variables.

Quando você usa secrets do GitHubWhen you do use GitHub secrets

  • Crie pela interface (Settings → Secrets and variables → Actions, ou dentro do environment) ou pela CLI: gh secret set NOME --env develop (sem --env, vai para o repositório). O valor não pode ser lido de volta depois.Create them in the UI (Settings → Secrets and variables → Actions, or inside the environment) or from the CLI: gh secret set NAME --env develop (without --env it goes to the repository).   • Prefira environment secrets a repository secrets: só chegam a jobs que usam aquele environment e respeitam as regras dele (branch permitida, revisores).Prefer environment secrets over repository secrets: they only reach jobs that use that environment and respect its rules (allowed branch, reviewers).
  • O workflow só lê um secret que você cita de forma explícita (${{ secrets.NOME }}). Passe-o por env: ou with:, nunca escrito direto no comando.A workflow only reads a secret you cite explicitly (${{ secrets.NAME }}). Pass it through env: or with:, never written directly in the command.
  • Secrets não são passados a workflows disparados de forks (exceto o GITHUB_TOKEN), nem a jobs do Dependabot, nem automaticamente a reusable workflows.Secrets are not passed to workflows triggered from forks (except GITHUB_TOKEN), nor to Dependabot jobs, nor automatically to reusable workflows.

Do push ao ambiente: o caminho completoFrom push to environment: the full path

  1. Você trabalha numa branch de feature e abre um pull request para develop. Quando o PR é mergeado, o GitHub registra um push em develop e isso dispara o workflow.You work on a feature branch and open a pull request to develop. When the PR is merged, GitHub records a push to develop and that triggers the workflow.
  2. O job declara environment: develop (a expressão olha o nome da branch). O GitHub confere as regras do environment: a branch é permitida?The job declares environment: develop (the expression looks at the branch name). GitHub checks the environment’s rules: is the branch allowed?
  3. O job recebe o token OIDC com sub = repo:ORG/REPO:environment:develop e a configure-aws-credentials o troca por credenciais da role da conta dev (vars.AWS_ROLE_ARN daquele environment).The job receives the OIDC token with sub = repo:ORG/REPO:environment:develop and configure-aws-credentials exchanges it for credentials of the dev account role (that environment’s vars.AWS_ROLE_ARN).
  4. Build, push para o ECR da conta dev, atualização do serviço ECS da conta dev.Build, push to the dev account’s ECR, update of the dev account’s ECS service.
  5. Depois de validar em dev, você abre um PR de develop para main. Ao mergear, o mesmo fluxo roda com environment: production: o job espera a aprovação dos revisores e então usa a role da conta prod.After validating in dev, you open a PR from develop to main. On merge the same flow runs with environment: production: the job waits for the reviewers’ approval and then uses the prod account role.
Complemento recomendado: proteja develop e main com uma regra de branch (Settings → Rules → Rulesets) que exija pull request e a passagem dos testes. Assim ninguém dá push direto e todo deploy passa por revisão. Crie um workflow de testes separado, disparado por pull_request, sem environment: ele não consegue assumir as roles de deploy, porque o sub de um PR (repo:ORG/REPO:pull_request) não bate com nenhuma trust policy.Recommended addition: protect develop and main with a branch rule (Settings → Rules → Rulesets) requiring a pull request and passing tests. That way nobody pushes directly and every deploy goes through review. Create a separate tests workflow triggered by pull_request, without an environment: it cannot assume the deploy roles, because a PR’s sub (repo:ORG/REPO:pull_request) matches no trust policy.

Um único arquivo atende os dois ambientes: o nome do environment sai do nome da branch. Arquivos no repositório:One file serves both environments: the environment name comes from the branch name. Files in the repository:

.github/workflows/deploy.yml
  .aws/task-definition.json     # aws ecs register-task-definition --generate-cli-skeleton
name: Deploy

  on:
    push:
      branches:
        - develop
        - main

  # One deploy at a time per branch; a newer push waits for the running one.
  concurrency:
    group: deploy-${{ github.ref_name }}
    cancel-in-progress: false

  permissions:
    id-token: write   # lets the job request the OIDC token
    contents: read    # actions/checkout

  jobs:
    deploy:
      runs-on: ubuntu-latest
      environment: ${{ github.ref_name == 'main' && 'production' || 'develop' }}
      env:
        AWS_REGION: ${{ vars.AWS_REGION }}
        ECR_REPOSITORY: ${{ vars.ECR_REPOSITORY }}
        ECS_CLUSTER: ${{ vars.ECS_CLUSTER }}
        ECS_SERVICE: ${{ vars.ECS_SERVICE }}
        ECS_TASK_DEFINITION: .aws/task-definition.json
        CONTAINER_NAME: app
      steps:
        - uses: actions/checkout@v6

        - name: Configure AWS credentials (OIDC)
          uses: aws-actions/configure-aws-credentials@v6
          with:
            role-to-assume: ${{ vars.AWS_ROLE_ARN }}
            role-session-name: gh-${{ github.run_id }}
            aws-region: ${{ env.AWS_REGION }}

        - name: Log in to Amazon ECR
          id: login-ecr
          uses: aws-actions/amazon-ecr-login@v2

        - name: Build and push the image
          id: build-image
          env:
            REGISTRY: ${{ steps.login-ecr.outputs.registry }}
            IMAGE_TAG: ${{ github.sha }}
          run: |
            docker build -t "$REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG" .
            docker push "$REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG"
            echo "image=$REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG" >> "$GITHUB_OUTPUT"

        - name: Render the task definition
          id: render
          uses: aws-actions/amazon-ecs-render-task-definition@v1
          with:
            task-definition: ${{ env.ECS_TASK_DEFINITION }}
            container-name: ${{ env.CONTAINER_NAME }}
            image: ${{ steps.build-image.outputs.image }}

        - name: Deploy to Amazon ECS
          uses: aws-actions/amazon-ecs-deploy-task-definition@v2
          with:
            task-definition: ${{ steps.render.outputs.task-definition }}
            service: ${{ env.ECS_SERVICE }}
            cluster: ${{ env.ECS_CLUSTER }}
            wait-for-service-stability: true
  • permissions: id-token: write permite pedir o token OIDC e não dá acesso de escrita a nenhum recurso; contents: read é para o checkout.permissions: id-token: write lets the job request the OIDC token and grants no write access to any resource; contents: read is for the checkout.
  • concurrency faz dois pushes na mesma branch não implantarem ao mesmo tempo.concurrency keeps two pushes to the same branch from deploying at the same time.
  • A imagem é marcada com o SHA do commit, então cada deploy é rastreável e reversível.The image is tagged with the commit SHA, so each deploy is traceable and reversible.
  • role-session-name com o ID da execução faz o CloudTrail mostrar qual execução do workflow fez cada chamada.role-session-name with the run ID makes CloudTrail show which workflow run made each call.
  • wait-for-service-stability: true faz o job esperar o serviço estabilizar; se o deploy falhar, o job falha.wait-for-service-stability: true makes the job wait for the service to stabilise; if the deploy fails, the job fails.
Estas actions não são certificadas pelo GitHub. A documentação do GitHub recomenda fixar actions por SHA de commit; os exemplos usam tags (@v6, @v2, @v1) por legibilidade. Em produção, fixe por SHA.These actions are not certified by GitHub. GitHub’s docs recommend pinning actions to a commit SHA; the examples use tags (@v6, @v2, @v1) for readability. In production, pin to a SHA.

Cuidados e problemas comunsSafety and common problems

  • “Credentials could not be loaded” ou “Could not assume role”. Falta permissions: id-token: write no workflow ou o AWS_ROLE_ARN está vazio: confira se o job usa o environment que contém a variável (variáveis de environment só existem para jobs que o declaram).“Credentials could not be loaded” or “Could not assume role”. The workflow lacks permissions: id-token: write or AWS_ROLE_ARN is empty: check that the job uses the environment that holds the variable (environment variables exist only for jobs that declare it).
  • Deploy de dev caiu na conta errada. Confira o ARN em AWS_ROLE_ARN de cada environment: o ID da conta no ARN é o que decide o destino. Os dois environments com ARNs trocados é o erro mais caro desta configuração.A dev deploy landed in the wrong account. Check the ARN in each environment’s AWS_ROLE_ARN: the account ID in the ARN decides the destination. Swapped ARNs between the two environments is the costliest mistake in this setup.
  • AccessDenied em iam:PassRole ou ecs:RegisterTaskDefinition. A política da role de deploy não cobre os ARNs das roles de task da mesma conta (os ARNs têm o ID da conta).AccessDenied on iam:PassRole or ecs:RegisterTaskDefinition. The deploy role’s policy does not cover the task role ARNs of the same account (the ARNs contain the account ID).
  • A task não sobe com “ResourceInitializationError ... unable to pull secrets”. A task execution role não tem secretsmanager:GetSecretValue sobre o segredo (ou o ARN no valueFrom está errado). Não é a role de deploy que precisa dessa permissão.The task fails with “ResourceInitializationError ... unable to pull secrets”. The task execution role lacks secretsmanager:GetSecretValue on the secret (or the ARN in valueFrom is wrong). It is not the deploy role that needs this permission.
  • “Not authorized to perform sts:AssumeRoleWithWebIdentity”. O sub da trust policy não bate com o do token: confira se o job referencia o environment, o nome exato dele e o formato imutável.“Not authorized to perform sts:AssumeRoleWithWebIdentity”. The trust policy’s sub does not match the token’s: check that the job references the environment, its exact name, and the immutable format.
  • Nunca use só curinga no sub. O IAM rejeita uma trust policy do GitHub sem a condição, ou com valor que seja só *.Never use only a wildcard in sub. IAM rejects a GitHub trust policy without the condition, or whose value is only *.
  • Evite ForAllValues: em statements Allow: pode liberar acesso quando a claim está ausente ou escrita errada. Use StringEquals ou StringLike.Avoid ForAllValues: in Allow statements: it can grant access when a claim is absent or misspelled. Use StringEquals or StringLike.
  • Cuidado com gatilhos pull_request_target. Jobs do Dependabot têm event_name igual a dynamic; se a trust policy deve valer só para Actions, restrinja os eventos esperados.Be careful with pull_request_target triggers. Dependabot jobs have event_name set to dynamic; if the trust policy should cover only Actions, restrict the expected events.
  • A AWS não suporta claims OIDC personalizadas; o GitHub permite personalizar o formato do sub, mas crie antes a condição correspondente na AWS.AWS does not support custom OIDC claims; GitHub lets you customise the sub format, but create the matching condition in AWS first.
  • A sessão dura 1 hora por padrão (role-duration-seconds, de 15 min a 12 h). Deploys longos precisam de uma duração maior.The session lasts 1 hour by default (role-duration-seconds, from 15 min to 12 h). Long deploys need a longer duration.
