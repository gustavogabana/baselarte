O fluxo completoThe full flow

O objetivo: depois de um commit chegar em develop ou main, o GitHub constrói uma imagem Docker com a configuração daquele ambiente, guarda a imagem no repositório de imagens (Amazon ECR) da conta AWS correta e troca o container em execução pelo novo. Ninguém entra em servidor, ninguém guarda chave de acesso.The goal: once a commit lands on develop or main, GitHub builds a Docker image with that environment’s configuration, stores it in the image registry (Amazon ECR) of the right AWS account and swaps the running container for the new one. Nobody logs in to a server, nobody stores an access key.

  1. Push. O merge de um PR em develop (ou main) registra um evento push e dispara o workflow.Push. Merging a PR into develop (or main) records a push event and triggers the workflow.
  2. Build. O job escolhe o environment pelo nome da branch e constrói a imagem passando como --build-arg as variáveis desse environment.Build. The job picks the environment from the branch name and builds the image passing that environment’s variables as --build-arg.
  3. Credenciais. O GitHub emite um token OIDC; a AWS o troca por credenciais temporárias da role da conta do ambiente (etapas 1 a 3).Credentials. GitHub issues an OIDC token; AWS exchanges it for temporary credentials of the environment account’s role (steps 1 to 3).
  4. Registro. A imagem sobe para o ECR da mesma conta, com o SHA do commit como tag.Registry. The image is pushed to the ECR of the same account, tagged with the commit SHA.
  5. Troca. O workflow registra uma task definition nova apontando para a imagem nova e manda o serviço ECS usá-la. O ECS sobe o container novo, espera ele ficar saudável e para o antigo.Swap. The workflow registers a new task definition pointing to the new image and tells the ECS service to use it. ECS starts the new container, waits for it to be healthy and stops the old one.
  6. Verificação. O job espera o serviço estabilizar. Se a versão nova não ficar saudável, o job falha e o ECS pode desfazer sozinho.Check. The job waits for the service to stabilise. If the new version does not become healthy, the job fails and ECS can roll back on its own.
E o “parar e excluir o container atual”? No ECS você não roda docker stop e docker rm. O serviço faz a troca (rolling update): a documentação diz que o scheduler “substitui as tasks em execução por tasks novas”. A task antiga é parada e o container dela é descartado junto. Se você usa Docker puro numa EC2, o mesmo passo é manual: veja a alternativa com EC2 (etapa 10).And “stop and delete the current container”? On ECS you do not run docker stop and docker rm. The service does the swap (a rolling update): the docs say the scheduler “replaces the currently running tasks with new tasks”. The old task is stopped and its container is discarded with it. If you run plain Docker on an EC2 instance, the same step is manual: see the EC2 alternative (step 10).

Como o OIDC funcionaHow OIDC works

Em vez de guardar chaves de acesso da AWS nos secrets do GitHub, o GitHub Actions emite um token OIDC de curta duração para cada execução. A AWS confia no GitHub como provedor de identidade e troca esse token por credenciais temporárias de uma role IAM.Instead of storing AWS access keys in GitHub secrets, GitHub Actions issues a short-lived OIDC token for each run. AWS trusts GitHub as an identity provider and exchanges that token for temporary credentials of an IAM role.

  1. O job pede um token ao GitHub (precisa de id-token: write).The job asks GitHub for a token (it needs id-token: write).
  2. A action aws-actions/configure-aws-credentials envia o token à AWS (sts:AssumeRoleWithWebIdentity).The aws-actions/configure-aws-credentials action sends the token to AWS (sts:AssumeRoleWithWebIdentity).
  3. A AWS confere a trust policy da role: emissor, audiência (aud) e quem está pedindo (sub).AWS checks the role’s trust policy: issuer, audience (aud) and who is asking (sub).
  4. Se bater, devolve credenciais temporárias (por padrão, 1 hora) que os passos seguintes usam.If it matches, AWS returns temporary credentials (1 hour by default) that the following steps use.

Não há segredo para vazar nem para rotacionar. O controle de quem pode fazer deploy passa a morar na trust policy.There is no secret to leak or rotate. Control over who can deploy now lives in the trust policy.

O que é um identity provider OIDCWhat an OIDC identity provider is

Um identity provider (IdP, provedor de identidade) é um serviço que sabe provar quem é alguém e que outros sistemas aceitam como testemunha. Você já usou vários: ao clicar em “Entrar com Google”, o Google é o IdP e o site que você abriu confia na palavra dele em vez de pedir uma senha nova. OIDC (OpenID Connect) é o protocolo padrão dessa conversa: o IdP entrega um token assinado (um JWT) dizendo “este sujeito é fulano, emitido por mim, para tal destino”, e quem recebe só precisa conferir a assinatura.An identity provider (IdP) is a service that can prove who someone is and that other systems accept as a witness. You have used plenty: when you click “Sign in with Google”, Google is the IdP and the site you opened trusts its word instead of asking for a new password. OIDC (OpenID Connect) is the standard protocol for that conversation: the IdP hands over a signed token (a JWT) saying “this subject is so-and-so, issued by me, for this destination”, and the receiver only has to check the signature.

Aqui o “fulano” não é uma pessoa, é uma execução do GitHub Actions. O GitHub faz o papel de IdP para os seus workflows: a cada job ele assina um token com a identidade daquela execução (repositório, branch, environment, workflow). A AWS faz o papel de quem recebe e precisa decidir se acredita.Here the “someone” is not a person, it is a GitHub Actions run. GitHub plays the IdP for your workflows: for each job it signs a token carrying that run’s identity (repository, branch, environment, workflow). AWS plays the receiver that has to decide whether to believe it.

Então o que é o “provedor OIDC” que criamos na AWS?So what is the “OIDC provider” we create in AWS?

It is a trust list, similar to the browser’s list of certificate authorities: without the entry, STS rejects any GitHub token, even one with a perfect signature, because it has no reason to believe it.

O registro guarda só duas coisas públicas, a URL do emissor e a audiência. Não há chave, senha nem segredo.   • Agora: nada de valioso é guardado. O token dura minutos, serve só para a audiência sts.amazonaws.com e as credenciais que a AWS devolve expiram em cerca de 1 hora. 7. Como o ECS troca o container7. How ECS swaps the container

Com 1 task desejada, o padrão (100/200) sobe a nova antes de parar a antiga: sem indisponibilidade, desde que a nova passe no health check. With 0/100 ECS is forced to stop the old one first: the literal equivalent of “stop, delete and create again”, at the cost of a window offline.

A documentação avisa: ao definir esses percentuais, garanta que o scheduler consiga parar ou iniciar pelo menos uma task. The deploy role’s policy does not cover the task role ARNs of the same account (the ARNs contain the account ID).
