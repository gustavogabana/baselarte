CI/CD

From push to running container: build, ECR and replace.

A push to develop or main builds a Docker image with that environment’s settings, stores it in ECR and replaces the running container in the matching AWS account.

O fluxo completoThe full flow

O objetivo: depois de um commit chegar em develop ou main, o GitHub constrói uma imagem Docker com a configuração daquele ambiente, guarda a imagem no repositório de imagens (Amazon ECR) da conta AWS correta e troca o container em execução pelo novo. Ninguém entra em servidor, ninguém guarda chave de acesso.The goal: once a commit lands on develop or main, GitHub builds a Docker image with that environment’s configuration, stores it in the image registry (Amazon ECR) of the right AWS account and swaps the running container for the new one. Nobody logs in to a server, nobody stores an access key.

  1. Push. O merge de um PR em develop (ou main) registra um evento push e dispara o workflow.Push. Merging a PR into develop (or main) records a push event and triggers the workflow.
  2. Build. O job escolhe o environment pelo nome da branch e constrói a imagem passando como --build-arg as variáveis desse environment.Build. The job picks the environment from the branch name and builds the image passing that environment’s variables as --build-arg.
  3. Credenciais. O GitHub emite um token OIDC; a AWS o troca por credenciais temporárias da role da conta do ambiente (nota de OIDC).Credentials. GitHub issues an OIDC token; AWS exchanges it for temporary credentials of the environment account’s role (OIDC note).
  4. Registro. A imagem sobe para o ECR da mesma conta, com o SHA do commit como tag.Registry. The image is pushed to the ECR of the same account, tagged with the commit SHA.
  5. Troca. O workflow registra uma task definition nova apontando para a imagem nova e manda o serviço ECS usá-la. O ECS sobe o container novo, espera ele ficar saudável e para o antigo.Swap. The workflow registers a new task definition pointing to the new image and tells the ECS service to use it. ECS starts the new container, waits for it to be healthy and stops the old one.
  6. Verificação. O job espera o serviço estabilizar. Se a versão nova não ficar saudável, o job falha e o ECS pode desfazer sozinho.Check. The job waits for the service to stabilise. If the new version does not become healthy, the job fails and ECS can roll back on its own.
E o “parar e excluir o container atual”? No ECS você não roda docker stop e docker rm. O serviço faz a troca (rolling update): a documentação diz que o scheduler “substitui as tasks em execução por tasks novas”. A task antiga é parada e o container dela é descartado junto. Se você usa Docker puro numa EC2, o mesmo passo é manual: veja a alternativa com EC2.And “stop and delete the current container”? On ECS you do not run docker stop and docker rm. The service does the swap (a rolling update): the docs say the scheduler “replaces the currently running tasks with new tasks”. The old task is stopped and its container is discarded with it. If you run plain Docker on an EC2 instance, the same step is manual: see the EC2 alternative.

  • main → conta prod. O environment production pode exigir um revisor antes de o job continuar.main → prod account. The production environment can require a reviewer before the job continues.
  • Mais ambientes? Nada mais muda.More environments? Nothing else changes.

Segredo no build é vazamento. Valores de ARG e ENV ficam gravados nos metadados e nas camadas da imagem, e qualquer pessoa com permissão de baixá-la os lê (por exemplo com docker history). Para a senha do banco, use o caminho de runtime da tabela.A secret at build time is a leak. 2. O repositório de imagens (ECR)2. The image registry (ECR)

Cada conta tem o seu repositório ECR, com o mesmo nome nas duas. O workflow envia a imagem para o repositório da conta em que a role foi assumida, então dev e prod nunca compartilham imagens.Each account has its own ECR repository, with the same name in both. 3. Como o ECS troca o container3. How ECS swaps the container

É aqui que o container antigo é parado e descartado. O comportamento é controlado por dois números do serviço, descritos na documentação do ECS:This is where the old container is stopped and discarded. The behaviour is controlled by two numbers on the service, described in the ECS documentation:

  • minimumHealthyPercent é o limite inferior de tasks saudáveis durante a troca, em % do número desejado (arredondado para cima).minimumHealthyPercent is the lower limit of healthy tasks during the swap, as a % of the desired count (rounded up).
  • maximumPercent é o limite superior de tasks em execução durante a troca (arredondado para baixo).maximumPercent is the upper limit of running tasks during the swap (rounded down).

Com 1 task desejada, o padrão (100/200) sobe a nova antes de parar a antiga: sem indisponibilidade, desde que a nova passe no health check. Com 0/100 o ECS é forçado a parar a antiga antes: é o equivalente literal de “parar, excluir e criar de novo”, ao custo de uma janela fora do ar.With 1 desired task, the default (100/200) starts the new one before stopping the old one: no downtime, as long as the new one passes the health check. With 0/100 ECS is forced to stop the old one first: the literal equivalent of “stop, delete and create again”, at the cost of a window offline.

A documentação avisa: ao definir esses percentuais, garanta que o scheduler consiga parar ou iniciar pelo menos uma task. Com 1 task desejada, 100/100 trava o deploy (nem sobe a nova, nem para a antiga) e o serviço registra um evento de erro.The docs warn: when you set these percentages, make sure the scheduler can stop or start at least one task. With 1 desired task, 100/100 stalls the deploy (it can neither start the new one nor stop the old one) and the service logs an error event.

Configurar, passo a passoConfiguring, step by step

  1. No console: ECS → Clusters → seu cluster → seu serviço → Update service, seção de opções de deployment.In the console: ECS → Clusters → your cluster → your service → Update service, deployment options section.
  2. Defina Minimum healthy percent e Maximum percent conforme o desenho acima (a primeira opção é a recomendada).Set Minimum healthy percent and Maximum percent as drawn above (the first option is the recommended one).
  3. Ative o deployment circuit breaker com rollback: se as tasks novas não conseguirem iniciar, o ECS marca o deploy como falho e volta para a revisão anterior. A documentação o indica para parar um deploy quando as tasks não sobem.Turn on the deployment circuit breaker with rollback: if the new tasks cannot start, ECS marks the deploy as failed and returns to the previous revision. The docs recommend it for stopping a deployment when tasks cannot start.
  4. Repita no serviço da outra conta (em prod, mantenha o padrão 100/200 para não ter janela fora do ar).Repeat on the other account’s service (in prod, keep the default 100/200 to avoid an offline window).
aws ecs update-service --cluster meu-cluster --service meu-servico \
  --deployment-configuration "minimumHealthyPercent=100,maximumPercent=200,deploymentCircuitBreaker={enable=true,rollback=true}" \
  --profile dev

O health check decide quando a antiga pode pararThe health check decides when the old one may stop

O ECS só considera a task nova saudável se o container passar no health check. Defina um na task definition (o comando depende do que existe na imagem; este exemplo usa wget, presente na imagem Alpine):ECS only treats the new task as healthy if the container passes its health check. Define one in the task definition (the command depends on what the image contains; this example uses wget, present in the Alpine image):

"healthCheck": {
  "command": ["CMD-SHELL", "wget -qO- http://localhost:3000/health || exit 1"],
  "interval": 15,
  "timeout": 5,
  "retries": 3,
  "startPeriod": 20
}

Se o serviço está atrás de um load balancer, o health check do target group também vale. Sem nenhum health check, o ECS só sabe que o processo iniciou, não que a aplicação responde.If the service is behind a load balancer, the target group’s health check counts too. With no health check, ECS only knows the process started, not that the application responds.

5. O workflow completo5. The full workflow

Um único arquivo atende os dois ambientes. É o workflow da nota de OIDC com duas diferenças: as --build-arg vindas das variáveis do environment e a checagem de “imagem já existe”.One file serves both environments. It is the OIDC note’s workflow with two differences: the --build-args coming from the environment variables and the “image already exists” check.

.github/workflows/deploy.yml
Dockerfile
.aws/task-definition.json     # container named "app"
name: Build and deploy

on:
  push:
    branches:
      - develop
      - main

# One deploy at a time per branch; a newer push waits for the running one.
concurrency:
  group: deploy-${{ github.ref_name }}
  cancel-in-progress: false

permissions:
  id-token: write   # lets the job request the OIDC token
  contents: read    # actions/checkout

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: ${{ github.ref_name == 'main' && 'production' || 'develop' }}
    env:
      AWS_REGION: ${{ vars.AWS_REGION }}
      ECR_REPOSITORY: ${{ vars.ECR_REPOSITORY }}
      ECS_CLUSTER: ${{ vars.ECS_CLUSTER }}
      ECS_SERVICE: ${{ vars.ECS_SERVICE }}
      ECS_TASK_DEFINITION: .aws/task-definition.json
      CONTAINER_NAME: app
    steps:
      - uses: actions/checkout@v6

      - name: Configure AWS credentials (OIDC)
        uses: aws-actions/configure-aws-credentials@v6
        with:
          role-to-assume: ${{ vars.AWS_ROLE_ARN }}
          role-session-name: gh-${{ github.run_id }}
          aws-region: ${{ env.AWS_REGION }}

      - name: Log in to Amazon ECR
        id: login-ecr
        uses: aws-actions/amazon-ecr-login@v2

      - name: Build and push the image
        id: build-image
        env:
          REGISTRY: ${{ steps.login-ecr.outputs.registry }}
          IMAGE_TAG: ${{ github.sha }}
          APP_ENV: ${{ vars.APP_ENV }}
          PUBLIC_API_URL: ${{ vars.PUBLIC_API_URL }}
        run: |
          IMAGE="$REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG"
          if aws ecr describe-images --repository-name "$ECR_REPOSITORY" \
               --image-ids imageTag="$IMAGE_TAG" > /dev/null 2>&1; then
            echo "Image $IMAGE_TAG already in ECR, skipping build"
          else
            docker build \
              --build-arg APP_ENV="$APP_ENV" \
              --build-arg PUBLIC_API_URL="$PUBLIC_API_URL" \
              -t "$IMAGE" .
            docker push "$IMAGE"
          fi
          echo "image=$IMAGE" >> "$GITHUB_OUTPUT"

      - name: Render the task definition
        id: render
        uses: aws-actions/amazon-ecs-render-task-definition@v1
        with:
          task-definition: ${{ env.ECS_TASK_DEFINITION }}
          container-name: ${{ env.CONTAINER_NAME }}
          image: ${{ steps.build-image.outputs.image }}

      - name: Deploy to Amazon ECS (replaces the running container)
        uses: aws-actions/amazon-ecs-deploy-task-definition@v2
        with:
          task-definition: ${{ steps.render.outputs.task-definition }}
          service: ${{ env.ECS_SERVICE }}
          cluster: ${{ env.ECS_CLUSTER }}
          wait-for-service-stability: true

O que cada parte fazWhat each part does

  • on.push.branches. Só develop e main disparam. Uma branch de feature não faz deploy.on.push.branches. Only develop and main trigger. A feature branch does not deploy.
  • environment:. A expressão escolhe production para main e develop para o resto. É isso que seleciona as variáveis (vars.*), a role e as regras de aprovação.environment:. The expression picks production for main and develop otherwise. It is what selects the variables (vars.*), the role and the approval rules.
  • Build. As variáveis do environment viram --build-arg. A imagem nasce com os valores do ambiente certo.Build. The environment’s variables become --build-arg. The image is born with the right environment’s values.
  • Checagem de existência. Com tags imutáveis, enviar de novo a mesma tag dá erro. Se você reexecutar um job do mesmo commit, o workflow pula o build e reaproveita a imagem. Consequência: se mudar uma variável do environment e reexecutar o mesmo commit, a imagem não é refeita; faça um commit novo.Existence check. With immutable tags, pushing the same tag again is an error. If you re-run a job for the same commit, the workflow skips the build and reuses the image. Consequence: if you change an environment variable and re-run the same commit, the image is not rebuilt; make a new commit.
  • Render + deploy. A primeira ação grava a imagem nova na task definition; a segunda registra a revisão e atualiza o serviço. A partir daí, o ECS faz a troca descrita na etapa 3.Render + deploy. The first action writes the new image into the task definition; the second registers the revision and updates the service. From there ECS does the swap described in step 3.
  • wait-for-service-stability. O job só termina quando o serviço estabiliza. Se a versão nova não ficar saudável, o job falha e você vê no GitHub.wait-for-service-stability. The job finishes only when the service stabilises. If the new version does not become healthy, the job fails and you see it on GitHub.
As actions não são certificadas pelo GitHub e os exemplos usam tags (@v6, @v2, @v1) por legibilidade. Em produção, fixe por SHA de commit, como recomenda a documentação do GitHub.These actions are not certified by GitHub and the examples use tags (@v6, @v2, @v1) for readability. In production, pin to a commit SHA, as GitHub’s docs recommend.

7. Alternativa: Docker puro numa EC27. Alternative: plain Docker on an EC2 instance

Se você não usa ECS e roda o container direto numa EC2, o “parar, excluir e criar” é um script na instância, e o workflow o dispara pelo AWS Systems Manager Run Command, sem abrir SSH. Os passos do build, o ECR e o OIDC são os mesmos; só mudam os dois últimos passos do workflow.If you do not use ECS and run the container directly on an EC2 instance, “stop, delete and create” is a script on the instance, and the workflow triggers it through AWS Systems Manager Run Command, with no SSH open. The build, ECR and OIDC steps are the same; only the last two workflow steps change.

Preparar a instância, uma vez por contaPreparing the instance, once per account

  1. A instância precisa de um instance profile com a política gerenciada AmazonSSMManagedInstanceCore (para o SSM Agent) e permissão de leitura no ECR (por exemplo AmazonEC2ContainerRegistryReadOnly). Em EC2 → Instances → Actions → Security → Modify IAM role.The instance needs an instance profile with the managed policy AmazonSSMManagedInstanceCore (for the SSM Agent) and read permission on ECR (for example AmazonEC2ContainerRegistryReadOnly). Under EC2 → Instances → Actions → Security → Modify IAM role.
  2. Confirme em Systems Manager → Fleet Manager que a instância aparece como gerenciada. Docker e AWS CLI instalados nela.Confirm under Systems Manager → Fleet Manager that the instance shows as managed. Docker and the AWS CLI installed on it.
  3. Salve o script abaixo em /opt/meu-app/deploy.sh (chmod +x).Save the script below at /opt/meu-app/deploy.sh (chmod +x).
  4. Na role de deploy (OIDC), troque as permissões do ECS por ssm:SendCommand (nos ARNs do documento AWS-RunShellScript e da instância) e ssm:GetCommandInvocation. Crie a variável EC2_INSTANCE_ID em cada environment.On the deploy role (OIDC), replace the ECS permissions with ssm:SendCommand (on the ARNs of the AWS-RunShellScript document and the instance) and ssm:GetCommandInvocation. Create the EC2_INSTANCE_ID variable in each environment.
#!/usr/bin/env bash
# /opt/meu-app/deploy.sh <image>
set -euo pipefail
IMAGE="$1"
REGISTRY="${IMAGE%%/*}"
REGION="$(echo "$REGISTRY" | cut -d. -f4)"

aws ecr get-login-password --region "$REGION" \
  | docker login --username AWS --password-stdin "$REGISTRY"

docker pull "$IMAGE"          # download first: shortens the downtime
docker stop app || true       # stop the running container
docker rm app || true         # delete it
docker run -d --name app --restart unless-stopped -p 80:3000 "$IMAGE"

No workflow, remova os passos “Render” e “Deploy to Amazon ECS” e acrescente este:In the workflow, remove the “Render” and “Deploy to Amazon ECS” steps and add this one:

- name: Replace the container on the instance
  env:
    IMAGE: ${{ steps.build-image.outputs.image }}
    INSTANCE_ID: ${{ vars.EC2_INSTANCE_ID }}
  run: |
    COMMAND_ID=$(aws ssm send-command \
      --document-name AWS-RunShellScript \
      --instance-ids "$INSTANCE_ID" \
      --parameters commands="bash /opt/meu-app/deploy.sh $IMAGE" \
      --query Command.CommandId --output text)
    aws ssm wait command-executed \
      --command-id "$COMMAND_ID" --instance-id "$INSTANCE_ID"
Aqui há sempre uma janela sem container (entre o docker stop e o docker run) e nenhum rollback automático: se a versão nova não subir, você precisa reexecutar o deploy de um commit anterior. É o que o ECS resolve para você. Segredos: leia-os do Secrets Manager no próprio script, com a role da instância; não os passe pelo workflow.Here there is always a window with no container (between docker stop and docker run) and no automatic rollback: if the new version does not start, you must redeploy an earlier commit. This is what ECS solves for you. Secrets: read them from Secrets Manager in the script itself, with the instance role; do not pass them through the workflow.

Voltar atrás e problemas comunsRolling back and common problems

Voltar para uma versão anteriorGoing back to an earlier version

  • Automático. Com o circuit breaker e rollback ativos, uma versão que não sobe é desfeita pelo ECS.Automatic. With the circuit breaker and rollback on, a version that does not start is undone by ECS.
  • Manual. Reverta o commit na branch (git revert) e faça o push, ou use Re-run jobs numa execução antiga que deu certo. Como as tags são imutáveis e únicas por commit, a imagem antiga ainda está no ECR e o workflow a reaproveita.Manual. Revert the commit on the branch (git revert) and push, or use Re-run jobs on an old successful run. Since tags are immutable and unique per commit, the old image is still in ECR and the workflow reuses it.

Problemas comunsCommon problems

  • “tag invalid: The image tag ... already exists” no push. O repositório tem tags imutáveis e a tag já existe. A checagem do workflow evita isso; se aparecer, confira se ecr:DescribeImages está na política (sem ela a checagem falha e o workflow tenta construir de novo).“tag invalid: The image tag ... already exists” on push. The repository has immutable tags and the tag already exists. The workflow check avoids it; if it appears, check that ecr:DescribeImages is in the policy (without it the check fails and the workflow tries to build again).
  • A task nova não sobe: CannotPullContainerError. A task execution role não pode baixar do ECR, ou a task está numa sub-rede privada sem caminho até o ECR (NAT ou VPC endpoints). Confira também se a imagem existe com aquela tag.The new task does not start: CannotPullContainerError. The task execution role cannot pull from ECR, or the task is in a private subnet with no path to ECR (NAT or VPC endpoints). Also check that the image exists with that tag.
  • O deploy fica parado e o serviço registra “unable to stop or start tasks”. Os percentuais do serviço não deixam o scheduler iniciar nem parar nenhuma task (por exemplo 100/100 com 1 task). Ajuste minimumHealthyPercent ou maximumPercent.The deploy stalls and the service logs “unable to stop or start tasks”. The service percentages do not let the scheduler start or stop any task (for example 100/100 with 1 task). Adjust minimumHealthyPercent or maximumPercent.
  • A aplicação em dev usa a URL de prod (ou o contrário). Confira as variáveis do environment e o ARN em AWS_ROLE_ARN: o ID da conta no ARN decide o destino. ARNs trocados entre os dois environments é o erro mais caro desta configuração.The application in dev uses the prod URL (or the reverse). Check the environment variables and the ARN in AWS_ROLE_ARN: the account ID in the ARN decides the destination. Swapped ARNs between the two environments is the costliest mistake in this setup.
  • Mudei uma variável e o deploy continua com o valor antigo. Reexecutar o mesmo commit reaproveita a imagem. Faça um commit novo (pode ser vazio: git commit --allow-empty).I changed a variable and the deploy still has the old value. Re-running the same commit reuses the image. Make a new commit (it can be empty: git commit --allow-empty).
  • O segredo mudou e a app não viu. O ECS lê o segredo quando o container inicia. Faça um novo deploy ou “Force new deployment” no serviço.The secret changed and the app did not see it. ECS reads the secret when the container starts. Run a new deploy or “Force new deployment” on the service.
