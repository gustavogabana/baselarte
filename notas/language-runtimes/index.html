Configuração: a regra que vale nas trêsConfiguration: the rule that holds in all three

Antes de cada pilha, a ideia que mais confunde iniciantes: nenhuma linguagem lê o arquivo .env sozinha. O .env é só um arquivo de texto com CHAVE=valor. Quem o transforma em configuração é uma biblioteca ou uma opção que você liga de propósito. O que todas as linguagens leem sozinhas são as variáveis de ambiente do processo, ou seja, o que o sistema operacional entrega ao programa quando ele inicia.Before each stack, the idea that confuses beginners the most: no language reads the .env file by itself. A .env is just a text file with KEY=value. What turns it into configuration is a library or an option you switch on on purpose. What every language reads by itself are the process's environment variables, that is, what the operating system hands to the program when it starts.

A escada acima é a regra comum, e eu a medi nas três (a tabela de cada linguagem mostra os números). Em todas, uma variável de ambiente vence o .env, e o .env vence o valor padrão do código. Isso é intencional: no seu computador você usa o .env; no servidor ou no Docker, o ambiente entra por fora e substitui, sem tocar no código. É a ideia do fator III do The Twelve-Factor App: configuração que muda entre ambientes mora no ambiente, não no código.The ladder above is the common rule, and I measured it in all three (each language's table shows the numbers). In every one, an environment variable beats the .env, and the .env beats the default in the code. That is intentional: on your computer you use the .env; on a server or in Docker the environment comes in from outside and overrides it, without touching the code. It is the idea of factor III of The Twelve-Factor App: configuration that changes between environments lives in the environment, not in the code.

  • Variável de ambiente só vale para o processo que a recebe. export GREETING=oi afeta aquele terminal e o que ele iniciar depois; outro terminal, o IDE e o Docker não enxergam. É a causa número um de “defini a variável e o programa não vê”. Para testar, prefixe o comando: GREETING=oi node src/server.ts.An environment variable only applies to the process that receives it. export GREETING=oi affects that terminal and what it starts afterwards; another terminal, the IDE and Docker do not see it. It is the number one cause of “I set the variable and the program does not see it”. To test, prefix the command: GREETING=oi node src/server.ts.
  • Tudo é texto. PORT=8080 chega como a string "8080". Cada pilha converte de um jeito (Spring converte pelo tipo do campo, o pydantic pela anotação, no TypeScript você usa o zod). Converta e valide uma vez, na partida: se faltar algo, o app deve nem subir.Everything is text. PORT=8080 arrives as the string "8080". Each stack converts in its own way (Spring converts by the field type, pydantic by the annotation, in TypeScript you use zod). Convert and validate once, at startup: if something is missing, the app should not even start.
  • Nunca versione o .env real. Coloque .env no .gitignore e no .dockerignore, e versione um .env.example sem segredos. Um segredo que entrou no Git continua no histórico mesmo depois de apagado.Never commit the real .env. Put .env in .gitignore and .dockerignore, and commit a .env.example with no secrets. A secret that got into Git stays in the history even after it is deleted.
  • Não devolva segredos nas respostas nem nos logs. O endpoint /config do laboratório responde só dbPasswordSet: true/false, nunca o valor.Do not return secrets in responses or logs. The lab's /config endpoint only answers dbPasswordSet: true/false, never the value.

Maven: o que ele fazMaven: what it does

O Maven é a ferramenta de build do Java. Ele lê o pom.xml (Project Object Model), baixa do Maven Central as bibliotecas que você declarou (e as que elas precisam), compila, roda os testes e empacota o resultado. As bibliotecas ficam num repositório local global, ~/.m2/repository, compartilhado por todos os projetos. Cada biblioteca é identificada por três coordenadas: groupId:artifactId:version.Maven is Java's build tool. It reads the pom.xml (Project Object Model), downloads from Maven Central the libraries you declared (and the ones they need), compiles, runs the tests and packages the result. Libraries live in a global local repository, ~/.m2/repository, shared by all projects. Each library is identified by three coordinates: groupId:artifactId:version.

Spring Boot: como funcionaSpring Boot: how it works

O Spring é um contêiner de objetos. Você escreve classes e o Spring as cria e as liga umas às outras (injeção de dependência): no código abaixo, o construtor de Hello pede um Settings e um Environment, e o Spring entrega os dois, sem nenhum new. O Spring Boot acrescenta a conveniência: a autoconfiguração olha o que está no classpath e configura sozinha. Pusemos o starter web, então ele sobe um Tomcat embutido na porta 8080 e registra o JSON; pusemos o actuator, então ele expõe /actuator/health. A anotação @SpringBootApplication liga tudo isso, e o main só chama SpringApplication.run.Spring is an object container. You write classes and Spring creates them and wires them together (dependency injection): in the code below, the Hello constructor asks for a Settings and an Environment, and Spring supplies both, with no new. Spring Boot adds the convenience: auto-configuration looks at what is on the classpath and configures by itself. We added the web starter, so it starts an embedded Tomcat on port 8080 and registers JSON; we added the actuator, so it exposes /actuator/health. The @SpringBootApplication annotation switches all that on, and main just calls SpringApplication.run.

package demo;

import java.util.Map;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.boot.context.properties.EnableConfigurationProperties;
import org.springframework.core.env.Environment;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@SpringBootApplication
@EnableConfigurationProperties(App.Settings.class)
public class App {

  public static void main(String[] args) {
    SpringApplication.run(App.class, args);
  }

  // app.greeting  <-  APP_GREETING (variável de ambiente) ou app.greeting (.properties)
  @ConfigurationProperties(prefix = "app")
  public record Settings(String greeting, String dbPassword) {}

  @RestController
  static class Hello {
    private final Settings settings;
    private final Environment env;

    Hello(Settings settings, Environment env) {
      this.settings = settings;
      this.env = env;
    }

    @GetMapping("/config")
    Map<String, Object> config() {
      return Map.of(
          "greeting", settings.greeting(),
          "profiles", env.getActiveProfiles(),
          "dbPasswordSet", settings.dbPassword() != null && !settings.dbPassword().isBlank());
    }
  }
}
  • @ConfigurationProperties(prefix = "app") liga o grupo de propriedades app.* ao record Settings, já convertido para o tipo certo. É o jeito recomendado de ler configuração, em vez de espalhar @Value.@ConfigurationProperties(prefix = "app") binds the app.* group of properties to the Settings record, already converted to the right type. It is the recommended way to read configuration, instead of scattering @Value.
  • O actuator dá observabilidade pronta. Com management.endpoint.health.probes.enabled=true ele publica /actuator/health/liveness e /readiness, que testei: {"status":"UP"}. Só expus o health; expor tudo (*) revela detalhes internos.The actuator gives ready-made observability. With management.endpoint.health.probes.enabled=true it publishes /actuator/health/liveness and /readiness, which I tested: {"status":"UP"}. I exposed only health; exposing everything (*) reveals internal details.
  • Documentação: a referência do Spring Boot (conceitos), o Spring Initializr (gera um projeto com as dependências que você marcar) e o apêndice de propriedades (todas as chaves possíveis).Documentation: the Spring Boot reference (concepts), the Spring Initializr (generates a project with the dependencies you tick) and the properties appendix (every possible key).

Configuração: do .env ao .properties, e os perfisConfiguration: from .env to .properties, and profiles

O Spring lê a configuração de um arquivo, o src/main/resources/application.properties (ou application.yml), que vai para dentro do jar. É um arquivo de chave=valor com nomes em minúsculas separados por ponto (app.greeting). Já o .env usa MAIÚSCULAS com sublinhado (APP_GREETING). As duas formas se encontram assim:Spring reads configuration from a file, src/main/resources/application.properties (or application.yml), which goes inside the jar. It is a key=value file with lowercase names separated by dots (app.greeting). A .env uses UPPERCASE with underscores (APP_GREETING). The two forms meet like this:

spring.application.name=hello
server.port=${PORT:8080}

# valores padrão; qualquer um pode ser trocado por variável de ambiente
app.greeting=olá do application.properties
app.db-password=

management.endpoints.web.exposure.include=health
management.endpoint.health.probes.enabled=true

# lê o arquivo .env (se existir) como se fosse um .properties
spring.config.import=optional:file:.env[.properties]
  1. Variável de ambiente → propriedade, automático. O Spring converte o nome: troca _ por . e ignora maiúsculas, então APP_GREETING vira app.greeting e APP_DB_PASSWORD vira app.db-password. Medi: APP_DB_PASSWORD=x e APP_DBPASSWORD=x ligaram o campo dbPassword. A referência descreve a regra em “Binding From Environment Variables”.Environment variable → property, automatic. Spring converts the name: it turns _ into . and ignores case, so APP_GREETING becomes app.greeting and APP_DB_PASSWORD becomes app.db-password. I measured: APP_DB_PASSWORD=x and APP_DBPASSWORD=x both set the dbPassword field. The reference describes the rule under “Binding From Environment Variables”.
  2. Placeholder: ${VARIAVEL:padrão}. Um valor do .properties pode citar outra propriedade ou variável. É o que a linha server.port=${PORT:8080} faz: usa PORT se existir, senão 8080. É assim que você faz o .properties “ler” uma variável com nome livre.Placeholder: ${VARIABLE:default}. A .properties value can cite another property or variable. That is what the line server.port=${PORT:8080} does: it uses PORT if it exists, otherwise 8080. This is how you make the .properties “read” a variable with a free name.
  3. O .env só entra se você mandar: a última linha, spring.config.import=optional:file:.env[.properties], diz ao Spring para ler o arquivo .env como se fosse um .properties. O optional: evita erro quando o arquivo não existe (no servidor, por exemplo), e o caminho é relativo a onde você roda o comando.The .env only comes in if you tell it to: the last line, spring.config.import=optional:file:.env[.properties], tells Spring to read the .env file as if it were a .properties. The optional: prevents an error when the file does not exist (on a server, say), and the path is relative to where you run the command.

Perfis: dev, prod e o que sãoProfiles: dev, prod and what they are

Um perfil (profile) é um nome de ambiente que escolhe quais arquivos de configuração entram. O arquivo base, application.properties, vale sempre. Se o perfil dev está ativo, o Spring também lê application-dev.properties e os valores dele sobrepõem os do base. Nada mais: um perfil não é uma opção mágica do Java, é só a convenção de nome application-{perfil}.properties.A profile is an environment name that picks which configuration files come in. The base file, application.properties, always applies. If the dev profile is active, Spring also reads application-dev.properties and its values override the base ones. That is all: a profile is not a Java magic option, just the naming convention application-{profile}.properties.

Testei o ./mvnw spring-boot:run -Dspring-boot.run.profiles=dev (a resposta veio do arquivo do perfil dev) e a ativação por variável de ambiente, nas duas formas com o jar. Se nenhum perfil for ativado, o Spring usa o perfil default, e o log avisa: No active profile set, falling back to 1 default profile: "default". Dois cuidados: (1) use perfis para o que muda de verdade entre ambientes (nível de log, endereço do banco); segredo não vai em arquivo de perfil dentro do jar, e sim em variável de ambiente; (2) um jar que contém application-dev.properties e application-prod.properties é o mesmo jar nos dois ambientes, e quem escolhe é o perfil ativo na hora de rodar. Também existe o formato de um arquivo só com várias seções (#--- no .properties, --- no YAML) com spring.config.activate.on-profile.I tested ./mvnw spring-boot:run -Dspring-boot.run.profiles=dev (the response came from the dev profile file) and activation by environment variable, in both forms with the jar. If no profile is activated, Spring uses the default profile, and the log says so: No active profile set, falling back to 1 default profile: "default". Two cautions: (1) use profiles for what really changes between environments (log level, database address); a secret does not go in a profile file inside the jar, it goes in an environment variable; (2) a jar that contains application-dev.properties and application-prod.properties is the same jar in both environments, and the profile active at run time chooses. There is also a single-file format with several sections (#--- in .properties, --- in YAML) with spring.config.activate.on-profile.

No Docker, o build em duas etapas separa o JDK pesado (que tem o Maven) do JRE que roda o jar. O --mount=type=cache guarda o ~/.m2 entre builds; sem ele, cada mudança no código baixaria tudo de novo.In Docker, the two-stage build separates the heavy JDK (which has Maven) from the JRE that runs the jar. Armadilhas que valem nas trêsTraps that hold in all three

  • Escute em 0.0.0.0, não em localhost. Dentro do contêiner, 127.0.0.1 é só o próprio contêiner. O fastapi dev falhou por isso; o Spring, o fastapi run e o listen(…, "0.0.0.0") do Node funcionaram.Listen on 0.0.0.0, not localhost. Inside the container, 127.0.0.1 is only the container itself. fastapi dev failed because of that; Spring, fastapi run and Node's listen(…, "0.0.0.0") worked.
  • EXPOSE não publica porta. Quem abre a porta para o seu computador é o -p host:contêiner (ou ports: no Compose). O EXPOSE é só documentação.EXPOSE does not publish a port. What opens the port to your computer is -p host:container (or ports: in Compose). EXPOSE is only documentation.
  • docker run --env-file não é um parser de shell. Com GREETING="com aspas" o valor chegou ao app com as aspas ("com aspas"), e DB_PASSWORD=x # comentario chegou como x # comentario. O env_file do Compose, ao contrário, tirou as aspas e o comentário (conferi com docker compose config). Escreva o .env sem aspas e sem comentário na mesma linha, e ele serve aos dois.docker run --env-file is not a shell parser. With GREETING="com aspas" the value reached the app with the quotes ("com aspas"), and DB_PASSWORD=x # comentario arrived as x # comentario. Compose's env_file, by contrast, stripped the quotes and the comment (I checked with docker compose config). Write the .env with no quotes and no comment on the same line, and it works for both.
  • .dockerignore evita três desastres: copiar o seu .env (segredos na imagem), copiar a .venv ou o node_modules do seu computador (outro sistema, outro caminho) e invalidar o cache de camadas a cada mudança..dockerignore avoids three disasters: copying your .env (secrets in the image), copying your computer's .venv or node_modules (another system, another path) and invalidating the layer cache on every change.
  • Copie o manifesto antes do código. Os três Dockerfiles copiam pom.xml, pyproject.toml/uv.lock ou package*.json primeiro e instalam as dependências; só então copiam o código. Mudar uma linha de código não refaz o download das bibliotecas.Copy the manifest before the code. The three Dockerfiles copy pom.xml, pyproject.toml/uv.lock or package*.json first and install the dependencies; only then do they copy the code. Changing one line of code does not redo the library download.
  • Rode como usuário comum (USER 10001 ou USER node) e deixe segredos só nas variáveis em tempo de execução, nunca em ENV do Dockerfile nem em ARG, que ficam no histórico da imagem.Run as a regular user (USER 10001 or USER node) and keep secrets only in run-time variables, never in a Dockerfile ENV or ARG, which stay in the image history.
