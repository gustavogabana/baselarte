Study guide

Terraform, the 80/20.

The part of Terraform you will use every day, explained step by step and then applied to AWS: remote state, VPC, EC2, IAM and S3.

O que é e o 20% que importaWhat it is and the 20% that matters

Terraform é uma ferramenta de infraestrutura como código (IaC): em vez de clicar no console da nuvem, você descreve em arquivos de texto o que quer que exista (redes, servidores, buckets, permissões) e o Terraform descobre o que precisa criar, alterar ou apagar para a realidade ficar igual à descrição. A linguagem é a HCL, e o trabalho é feito por providers (plugins) que falam com a API de cada serviço: AWS, Azure, Google Cloud, Cloudflare, GitHub, Kubernetes e milhares de outros.Terraform is an infrastructure as code (IaC) tool: instead of clicking in the cloud console, you describe in text files what should exist (networks, servers, buckets, permissions) and Terraform works out what to create, change or delete so reality matches the description. The language is HCL, and the work is done by providers (plugins) that talk to each service’s API: AWS, Azure, Google Cloud, Cloudflare, GitHub, Kubernetes and thousands more.

A ideia central é ser declarativo: você diz o destino (“quero 2 subnets e 1 bucket”), não os passos. É como a planta de uma casa: o Terraform compara a planta com a obra e só executa a diferença. Rodar de novo sem mudar nada não faz nada (idempotência).The core idea is being declarative: you state the destination (“I want 2 subnets and 1 bucket”), not the steps. It is like a house blueprint: Terraform compares the blueprint with the building and only carries out the difference. Running it again with no changes does nothing (idempotence).

A linguagem HCLThe HCL language

HCL (HashiCorp Configuration Language) tem só duas peças: blocos e argumentos. Um bloco tem um tipo, zero ou mais rótulos e um corpo entre chaves; o corpo tem argumentos (nome = valor) e outros blocos.HCL (HashiCorp Configuration Language) has only two pieces: blocks and arguments. A block has a type, zero or more labels and a body in braces; the body holds arguments (name = value) and other blocks.

  }

Estado, backend e driftState, backend and drift

O estado é um arquivo JSON que mapeia cada bloco do código ao objeto real (por exemplo, aws_s3_bucket.logs ↔ o bucket acme-logs-prod) e guarda os atributos conhecidos. Sem ele o Terraform não sabe o que já criou. Três regras de ouro:The state is a JSON file mapping each code block to the real object (for example, aws_s3_bucket.logs ↔ the bucket acme-logs-prod) and storing the known attributes. Without it Terraform does not know what it already created. Three golden rules:

  1. Nunca edite à mão nem coloque no Git: ele pode conter senhas e chaves em texto puro.Never edit it by hand and never commit it: it may hold passwords and keys in plain text.
  2. Em equipe, use backend remoto com trava (S3, GCS, Azure Blob, HCP Terraform) para ninguém aplicar ao mesmo tempo.In a team, use a remote backend with locking (S3, GCS, Azure Blob, HCP Terraform) so nobody applies at the same time.
  3. Mude o estado só pelos comandos e blocos oficiais (terraform state, moved, import, removed).Change state only through the official commands and blocks (terraform state, moved, import, removed).
terraform state list                       # tudo que o estado conhece
terraform state show aws_s3_bucket.logs    # os atributos de um recurso
terraform state mv A B                     # renomeia no estado (prefira o bloco moved)
terraform state rm aws_s3_bucket.logs      # "esquece" sem apagar na nuvem (prefira removed)
terraform force-unlock LOCK_ID             # só se um apply morreu e deixou a trava

Refatorar e adotar sem destruirRefactor and adopt without destroying

# 1) Renomeou um recurso no código? Diga ao Terraform que é o MESMO objeto:
moved {
  from = aws_s3_bucket.logs
  to   = aws_s3_bucket.access_logs
}

# 2) Já existe na nuvem e foi criado no console? Adote no estado (Terraform >= 1.5):
import {
  to = aws_s3_bucket.legacy
  id = "bucket-criado-no-console"
}
# terraform plan -generate-config-out=generated.tf  escreve o código por você

# 3) Quer parar de gerenciar sem apagar o objeto? (Terraform >= 1.7)
removed {
  from = aws_s3_bucket.legacy
  lifecycle {
    destroy = false
  }
}
Renomear um recurso no código sem um bloco moved faz o Terraform planejar “destruir o antigo e criar o novo”. É o acidente mais comum de refatoração. Sempre leia o plan depois de renomear.Renaming a resource in code without a moved block makes Terraform plan “destroy the old, create the new”. It is the most common refactoring accident. Always read the plan after renaming.

DriftDrift

Drift é quando alguém muda a nuvem pelo console e o código fica desatualizado. O plan normal já mostra a diferença (o Terraform tenta desfazer a mudança manual). Use plan -refresh-only para só atualizar o estado com o que existe, ou aplique o código para corrigir a nuvem. Em times, o remédio é simples: permissões de escrita no console só para emergências.Drift is when someone changes the cloud in the console and the code gets out of date. A normal plan already shows the difference (Terraform tries to undo the manual change). Use plan -refresh-only to merely update state with what exists, or apply the code to fix the cloud. For teams the cure is simple: console write access only for emergencies.

Variáveis, locals e outputsVariables, locals and outputs

Três blocos separam o que muda do como é feito: variable (entrada de fora), locals (valor calculado dentro) e output (saída). Todo módulo, inclusive o diretório raiz, é uma função: entra variável, sai output.Three blocks separate what changes from how it is done: variable (input from outside), locals (computed value inside) and output (result). Every module, including the root directory, is a function: variables go in, outputs come out.

  description = "Nome do ambiente"
  type        = string
  default     = "dev"

    error_message = "environment deve ser dev, staging ou prod."
  }
}

  1. o default da variávelthe variable’s default
  2. variáveis de ambiente TF_VAR_nomeenvironment variables TF_VAR_name
  3. terraform.tfvars e terraform.tfvars.jsonterraform.tfvars and terraform.tfvars.json
  4. *.auto.tfvars (em ordem alfabética)*.auto.tfvars (in alphabetical order)

export TF_VAR_db_password="$(aws secretsmanager get-secret-value --secret-id app/db --query SecretString --output text)"
sensitive = true só esconde o valor na tela. Ele continua em texto puro no state. Por isso: backend remoto cifrado e com acesso restrito, e preferir não ter o segredo no Terraform. Exemplos: o RDS pode gerar e guardar a senha no Secrets Manager (manage_master_user_password = true); versões recentes do Terraform também têm valores efêmeros e atributos write-only que não vão para o state (veja a documentação da sua versão).sensitive = true only hides the value on screen. It stays in plain text in the state. Hence: an encrypted, access-restricted remote backend, and preferably not having the secret in Terraform at all. For example, RDS can generate and store the password in Secrets Manager (manage_master_user_password = true); recent Terraform versions also have ephemeral values and write-only attributes that never reach the state (see your version’s documentation).

Dependências, repetição e lifecycleDependencies, repetition and lifecycle

Dependências e o grafoDependencies and the graph

Cada vez que um recurso referencia outro (vpc_id = aws_vpc.main.id) o Terraform cria uma aresta no grafo: o referenciado nasce primeiro e morre por último. O que não depende entre si roda em paralelo (padrão: 10 ao mesmo tempo). Você quase nunca precisa de depends_on; ele serve só para dependências que o Terraform não enxerga (por exemplo, uma política IAM que precisa existir antes de uma aplicação funcionar).Each time a resource references another (vpc_id = aws_vpc.main.id) Terraform adds an edge to the graph: the referenced one is born first and dies last. Things that do not depend on each other run in parallel (default: 10 at a time). You almost never need depends_on; it is only for dependencies Terraform cannot see (for example, an IAM policy that must exist before an application works).

Módulos e ambientesModules and environments

Um módulo é uma pasta com arquivos .tf usada por outro código via bloco module. O diretório onde você roda terraform apply é o módulo raiz; os que ele chama são módulos filhos. Variáveis são as entradas e outputs, as saídas. Módulos vêm de uma pasta local, do Terraform Registry, do Git ou de um bucket.A module is a folder of .tf files used by other code through a module block. The directory where you run terraform apply is the root module; the ones it calls are child modules. Variables are the inputs and outputs the results. Modules come from a local folder, the Terraform Registry, Git or a bucket.

AWS: estado remoto no S3AWS: remote state on S3

O estado em equipe vai para um bucket S3. Desde o Terraform 1.10 o backend S3 tem trava nativa (use_lockfile = true): ele grava um arquivo .tflock ao lado do estado, sem precisar de DynamoDB (o bloqueio por DynamoDB ainda existe, mas está obsoleto). Existe um ovo-e-galinha: o bucket precisa existir antes do Terraform que o usa. A solução mais simples é criá-lo uma vez à mão (ou com um pequeno projeto de “bootstrap” de estado local).In a team, state goes into an S3 bucket. Since Terraform 1.10 the S3 backend has native locking (use_lockfile = true): it writes a .tflock file next to the state, with no DynamoDB needed (DynamoDB locking still exists but is deprecated). There is a chicken-and-egg problem: the bucket must exist before the Terraform that uses it. The simplest fix is to create it once by hand (or with a tiny local-state “bootstrap” project).

# Bootstrap (uma vez por conta). Troque nome e região; S3 exige nome GLOBALMENTE único.
BUCKET=acme-tfstate-123456789012
REGION=sa-east-1

aws s3api create-bucket --bucket $BUCKET --region $REGION \
  --create-bucket-configuration LocationConstraint=$REGION   # (em us-east-1 omita esta linha)
aws s3api put-bucket-versioning --bucket $BUCKET \
  --versioning-configuration Status=Enabled
aws s3api put-public-access-block --bucket $BUCKET \
  --public-access-block-configuration BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
# backend.tf  (o bloco backend NÃO aceita variáveis)
terraform {
  backend "s3" {
    bucket       = "acme-tfstate-123456789012"
    key          = "loja/dev/terraform.tfstate"   # um "key" por projeto e ambiente
    region       = "sa-east-1"
    encrypt      = true
    use_lockfile = true                           # trava nativa (Terraform >= 1.10)
  }
}
terraform init                    # detecta o backend novo e oferece migrar o estado local
terraform init -migrate-state     # (ou explicitamente)
terraform init -backend-config="key=loja/prod/terraform.tfstate"   # muda o key sem editar o código
