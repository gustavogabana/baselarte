Study guide

Postgres, the 80/20 for developers.

Relational databases from the ground up, Postgres-focused: schemas, connecting, roles and passwords, access security, indexes, CTEs, full-text search, backups and caching — with a Docker lab you can run today.

O que é um banco relacional e um schemaWhat a relational database and a schema are

Um banco relacional guarda dados em tabelas: linhas (registros) e colunas (campos), com relações entre tabelas por chaves. É "relacional" no sentido matemático de relação (um conjunto de tuplas), não porque as tabelas se relacionam entre si — embora também façam isso. O gerenciador que guarda, organiza e responde consultas sobre esses dados é um SGBD (sistema de gerenciamento de banco de dados; em inglês, RDBMS).A relational database stores data in tables: rows (records) and columns (fields), with relations between tables through keys. It is "relational" in the mathematical sense of a relation (a set of tuples), not because tables relate to one another — though they also do that. The manager that stores, organizes and answers queries over that data is a DBMS (database management system).

O que é um schema, de fatoWhat a schema actually is

Um schema é um namespace dentro de um database: uma forma de organizar tabelas (por exemplo, vendas.pedidos e rh.funcionarios no mesmo database) sem precisar de um database separado para cada área. É diferente do uso da palavra "schema" em outros bancos (no MySQL, "schema" costuma ser sinônimo de "database" inteiro).A schema is a namespace inside a database: a way to organize tables (for example, vendas.pedidos and rh.funcionarios in the same database) without needing a separate database for each area. This differs from how the word "schema" is used in other databases (in MySQL, "schema" is usually a synonym for a whole "database").

CREATE SCHEMA vendas;
CREATE TABLE vendas.pedidos (id bigint, total numeric(10,2));

SET search_path TO vendas, public;   -- define a ordem de busca; agora "pedidos" sozinho já encontra vendas.pedidos
SELECT * FROM pedidos;               -- funciona sem o prefixo "vendas."

Como conectarHow to connect

Conectar ao Postgres sempre passa pelos mesmos seis dados: quem você é, com qual senha, em qual máquina, em qual porta, e em qual database. Toda ferramenta — psql, uma lib de app, um painel gráfico — pede exatamente isso, às vezes como uma connection string só.Connecting to Postgres always goes through the same six pieces of data: who you are, with which password, on which machine, on which port, and which database. Every tool — psql, an app library, a graphical panel — asks for exactly that, sometimes as a single connection string.

Pelo psqlThrough psql

Usuários e senhas: as três camadasUsers and passwords: the three layers

Esta é a maior fonte de confusão para quem está começando, porque a palavra "usuário" significa três coisas diferentes que não têm relação automática entre si. Desembaraçar isso resolve a maioria dos "funciona na minha máquina, não funciona no servidor".This is the biggest source of confusion for beginners, because the word "user" means three different things with no automatic relation between them. Untangling this solves most "works on my machine, not on the server" problems.

Segurança de acesso: pg_hba, TLS e privilégio mínimoAccess security: pg_hba, TLS and least privilege

Quem pode se conectar, de onde, e como ela precisa provar quem é — tudo isso é decidido por um arquivo: pg_hba.conf (host-based authentication). É o "firewall de identidade" do Postgres, separado do firewall de rede (nftables/ufw) e separado das permissões SQL (GRANT).Who may connect, from where, and how they must prove who they are — all of that is decided by one file: pg_hba.conf (host-based authentication). It is Postgres's "identity firewall", separate from the network firewall (nftables/ufw) and separate from SQL permissions (GRANT).

Regras são lidas de cima para baixo e a primeira que combinar vence. trust (sem senha) só faz sentido para local, numa máquina de estudo só sua — nunca em algo acessível pela rede. After editing: sudo systemctl reload postgresql (reloads without dropping connections).

Privilégio mínimoLeast privilege

A aplicação nunca deveria conectar como super-usuária. O padrão sensato: uma role por aplicação, com só as permissões que ela usa.The application should never connect as a superuser. The sensible default: one role per application, with only the permissions it uses.

CREATE ROLE app_readonly NOLOGIN;
GRANT CONNECT ON DATABASE loja TO app_readonly;
GRANT USAGE ON SCHEMA public TO app_readonly;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO app_readonly;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO app_readonly;  -- vale para tabelas FUTURAS também

CREATE ROLE app_web LOGIN PASSWORD 'outra-senha-forte' IN ROLE app_readonly;
GRANT INSERT, UPDATE, DELETE ON pedidos, itens_pedido TO app_web;   -- só nessas tabelas

Pooling de conexõesConnection pooling

Cada conexão Postgres custa memória (um processo por conexão). Para apps com muitas conexões curtas (serverless, muitas réplicas), um pooler como PgBouncer ou Supavisor fica entre a aplicação e o Postgres, reaproveitando um número menor de conexões reais — o lado de segurança é que o pooler também costuma ser o lugar certo para autenticar e limitar por aplicação.Every Postgres connection costs memory (one process per connection). For apps with many short-lived connections (serverless, many replicas), a pooler like PgBouncer or Supavisor sits between the application and Postgres, reusing a smaller number of real connections — the security angle is that the pooler is also usually the right place to authenticate and limit per application.

CTEs e window functions (o "pivô")CTEs and window functions (the "pivot")

CTEs (Common Table Expressions, o bloco WITH) dão nome a uma subconsulta para usá-la como se fosse uma tabela, tornando consultas grandes legíveis. Window functions (funções de janela) fazem cálculos "através" de um grupo de linhas sem colapsá-las numa só — é a ferramenta certa para o que costuma ser pedido como "pivô" (comparar cada linha com um agregado do seu grupo).CTEs (Common Table Expressions, the WITH block) name a subquery so it can be used as if it were a table, making large queries readable. Window functions compute "across" a group of rows without collapsing them into one — the right tool for what is usually asked for as a "pivot" (comparing each row against an aggregate of its group).

CTE simplesA simple CTE

WITH pedidos_pagos AS (
  SELECT cliente_id, total FROM pedidos WHERE status = 'pago'
)
SELECT c.nome, sum(p.total) AS total_gasto
FROM clientes c
JOIN pedidos_pagos p ON p.cliente_id = c.id
GROUP BY c.nome
ORDER BY total_gasto DESC;

CTE recursiva: percorrer uma árvoreRecursive CTE: walking a tree

WITH RECURSIVE subordinados AS (
  SELECT id, nome, gerente_id FROM funcionarios WHERE id = 1        -- âncora: o chefe
  UNION ALL
  SELECT f.id, f.nome, f.gerente_id
  FROM funcionarios f
  JOIN subordinados s ON f.gerente_id = s.id                         -- passo recursivo
)
SELECT * FROM subordinados;

Resultado esperado: todos os subordinados diretos e indiretos do funcionário 1, por quantos níveis existirem — sem precisar saber a profundidade do organograma de antemão.Expected result: every direct and indirect subordinate of employee 1, through however many levels exist — with no need to know the org chart's depth beforehand.

Window functions: o "pivô" do PostgresWindow functions: Postgres's "pivot"

Bancos como o SQL Server têm um comando PIVOT; o Postgres resolve o mesmo problema com FILTER (agregação condicional) ou funções de janela com OVER.Databases like SQL Server have a PIVOT command; Postgres solves the same problem with FILTER (conditional aggregation) or window functions with OVER.

-- "pivô" clássico: uma coluna por status, por mês
SELECT
  date_trunc('month', criado_em) AS mes,
  count(*) FILTER (WHERE status = 'pago')      AS pagos,
  count(*) FILTER (WHERE status = 'cancelado') AS cancelados
FROM pedidos
GROUP BY mes
ORDER BY mes;

-- window function: o total do cliente ao lado de CADA pedido, sem agrupar
SELECT
  id, cliente_id, total,
  sum(total) OVER (PARTITION BY cliente_id) AS total_do_cliente,
  rank()     OVER (PARTITION BY cliente_id ORDER BY total DESC) AS posicao
FROM pedidos;

Resultado esperado: a segunda consulta mantém uma linha por pedido (diferente de um GROUP BY, que colapsaria), com total_do_cliente repetindo a soma do grupo em cada linha e posicao ranqueando os pedidos de cada cliente do maior para o menor.Expected result: the second query keeps one row per order (unlike a GROUP BY, which would collapse them), with total_do_cliente repeating the group's sum on every row and posicao ranking each customer's orders from largest to smallest.

Index: ler sem escanear tudoIndexes: reading without scanning everything

Um índice é como o sumário de um livro: uma estrutura à parte que aponta direto para onde cada valor está, em vez de o Postgres ler a tabela inteira (sequential scan) para achar o que você pediu. Custa espaço em disco e um pouco de velocidade a mais em cada escrita; em compensação, consultas que filtram ou ordenam por aquela coluna ficam ordens de magnitude mais rápidas.An index is like a book's index: a separate structure that points straight to where each value is, instead of Postgres reading the whole table (a sequential scan) to find what you asked for. It costs disk space and a little extra time on every write; in exchange, queries that filter or sort by that column get orders of magnitude faster.

Resultado esperado: o plano muda de Seq Scan (lê a tabela inteira) para Index Scan ou Bitmap Index Scan, e o Execution Time cai — em tabelas pequenas a diferença é pequena, mas cresce junto com a tabela. EXPLAIN ANALYZE executa a consulta de verdade; para só ver o plano sem rodar, use EXPLAIN sozinho.Expected result: the plan changes from Seq Scan (reads the whole table) to Index Scan or Bitmap Index Scan, and Execution Time drops — on small tables the difference is small, but it grows with the table. EXPLAIN ANALYZE actually runs the query; to see just the plan without running it, use EXPLAIN alone.

Índice não é de graça: cada INSERT/UPDATE precisa atualizar todos os índices da tabela também. Não crie um índice "só por garantia" em toda coluna — crie para as consultas que você de fato tem (olhe o WHERE, o JOIN e o ORDER BY das consultas lentas).Indexes are not free: every INSERT/UPDATE has to update all of the table's indexes too. Do not create an index "just in case" on every column — create them for the queries you actually have (look at the WHERE, the JOIN and the ORDER BY of your slow queries).

CREATE TABLE sessoes (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),    -- nativo desde o Postgres 13
  usuario_id bigint NOT NULL,
  criada_em timestamptz NOT NULL DEFAULT now()
);
UUID v4 (totalmente aleatório) espalha as escritas pelo índice de forma ruim para o cache e o disco. UUID v7 (ordenado no tempo, como um "serial disfarçado") existe para resolver isso — e o ULID é uma alternativa fora do padrão UUID com a mesma ideia. Prefira v7/ULID quando precisar das vantagens do UUID sem perder a localidade de um ID crescente.UUID v4 (fully random) spreads writes across the index in a way that is bad for caching and disk. UUID v7 (time-ordered, like a "disguised serial") exists to fix that — and ULID is a non-UUID-standard alternative with the same idea. Prefer v7/ULID when you need UUID's advantages without losing an increasing ID's locality.

Full-text search no lugar de LIKEFull-text search instead of LIKE

LIKE '%palavra%' funciona, mas não usa índice de forma eficiente (o % no início impede o B-tree de "pular" direto ao lugar certo) e não entende idioma nenhum — busca "corre" não acha "correu". Para busca de texto de verdade, o Postgres tem busca textual embutida.LIKE '%word%' works, but does not use an index efficiently (the leading % stops a B-tree from "jumping" straight to the right place) and understands no language at all — searching "run" will not find "ran". For real text search, Postgres has built-in full-text search.

tsvector e tsquerytsvector and tsquery

ALTER TABLE produtos ADD COLUMN busca tsvector
  GENERATED ALWAYS AS (to_tsvector('portuguese', nome || ' ' || descricao)) STORED;

CREATE INDEX idx_produtos_busca ON produtos USING gin (busca);

SELECT nome FROM produtos
WHERE busca @@ to_tsquery('portuguese', 'camisa & azul')     -- E
   OR busca @@ to_tsquery('portuguese', 'camisa | blusa');   -- OU

SELECT nome, ts_rank(busca, to_tsquery('portuguese', 'camisa')) AS relevancia
FROM produtos
WHERE busca @@ to_tsquery('portuguese', 'camisa')
ORDER BY relevancia DESC;

Resultado esperado: buscar "camisa" encontra também "camisas" (o to_tsvector reduz palavras à raiz — stemming) e o ts_rank ordena pela relevância, algo que LIKE nunca faz.Expected result: searching "shirt" also finds "shirts" (to_tsvector reduces words to their root — stemming) and ts_rank sorts by relevance, something LIKE never does.

Quando o full-text search é demais: pg_trgmWhen full-text search is overkill: pg_trgm

Para "busca parecida" (tolerar erros de digitação, autocompletar) sem a complexidade de idioma do full-text, a extensão pg_trgm indexa trigramas (grupos de 3 letras) e acelera ILIKE/similarity().For "fuzzy search" (tolerating typos, autocomplete) without full-text's language complexity, the pg_trgm extension indexes trigrams (groups of 3 letters) and speeds up ILIKE/similarity().

CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_produtos_nome_trgm ON produtos USING gin (nome gin_trgm_ops);

SELECT nome FROM produtos WHERE nome ILIKE '%camisa%';         -- agora usa o índice
SELECT nome, similarity(nome, 'camiza azul') AS parecido
FROM produtos ORDER BY parecido DESC LIMIT 5;                  -- tolera o erro de digitação

Quem tem acesso ao quêWho has access to what

"Quem tem acesso a quê" no Postgres se decide em camadas: a role precisa existir, precisa de permissão no database, no schema, e por fim na tabela (ou até na linha). GRANT concede, REVOKE retira.Who has access to what, in Postgres, is decided in layers: the role must exist, and needs permission on the database, on the schema, and finally on the table (or even on the row). GRANT gives, REVOKE takes away.

GRANT CONNECT ON DATABASE loja TO ana;
GRANT USAGE ON SCHEMA vendas TO ana;
GRANT SELECT, INSERT ON vendas.pedidos TO ana;
GRANT SELECT (nome, email) ON clientes TO suporte;        -- só essas colunas
REVOKE INSERT ON vendas.pedidos FROM ana;

-- o que uma role pode fazer:
SELECT grantee, table_name, privilege_type
FROM information_schema.role_table_grants
WHERE grantee = 'ana';

Row-Level Security (RLS): permissão por linhaRow-Level Security (RLS): permission per row

Quando até colunas não bastam — por exemplo, cada cliente só pode ver seus próprios pedidos — o RLS aplica um filtro automático em toda consulta daquela role, sem precisar confiar que todo WHERE da aplicação está correto.When even columns are not enough — for example, each customer may only see their own orders — RLS applies an automatic filter to every query from that role, without having to trust that every WHERE in the application is correct.

ALTER TABLE pedidos ENABLE ROW LEVEL SECURITY;

CREATE POLICY pedidos_do_proprio_cliente ON pedidos
  USING (cliente_id = current_setting('app.cliente_id')::bigint);

-- a aplicação define quem está logado antes de consultar:
SET app.cliente_id = '42';
SELECT * FROM pedidos;   -- só retorna pedidos do cliente 42, mesmo sem WHERE
RLS é uma segunda camada de defesa, não uma desculpa para pular a checagem na aplicação — mas é exatamente o tipo de coisa que evita um vazamento quando um WHERE é esquecido em algum lugar do código.RLS is a second layer of defence, not an excuse to skip the check in the application — but it is exactly the kind of thing that prevents a leak when a WHERE is forgotten somewhere in the code.

Backups e a regra 3-2-1Backups and the 3-2-1 rule

Um backup só vale alguma coisa se você já tiver restaurado ele com sucesso pelo menos uma vez. O Postgres tem três ferramentas principais, e por cima delas vale uma regra que não é específica de banco de dados: a 3-2-1.A backup is only worth something once you have restored it successfully at least once. Postgres has three main tools, and on top of them sits a rule that is not database-specific at all: the 3-2-1 rule.

Point-in-time recovery (PITR), em uma frasePoint-in-time recovery (PITR), in one sentence

Cache: o 80/20 para quem programaCaching: the 80/20 for developers

Cache é "guardar uma resposta pronta para não refazer o trabalho". É provavelmente a técnica isolada que mais acelera sistemas reais — e também a que mais causa bugs sutis, porque introduz uma segunda fonte de verdade que pode ficar desatualizada.A cache is "keeping a ready-made answer so you do not redo the work". It is probably the single technique that speeds up real systems the most — and also the one that causes the most subtle bugs, because it introduces a second source of truth that can go stale.

O problema N+1: o "cache que você nem precisava"The N+1 problem: the "cache you did not even need"

-- N+1: 1 consulta para os pedidos + N consultas, uma por pedido, para o cliente
SELECT * FROM pedidos LIMIT 20;                     -- 1
SELECT * FROM clientes WHERE id = 1;                -- repetida 20x por um ORM "ingênuo"

-- resolvido com UM join, sem precisar de cache nenhum
SELECT p.*, c.nome FROM pedidos p JOIN clientes c ON c.id = p.cliente_id LIMIT 20;

Boa parte do "preciso de cache" na prática é, na verdade, uma consulta ruim. Laboratório com DockerLab with Docker

Um Postgres local em segundos, para treinar tudo desta nota sem instalar nada no sistema.A local Postgres in seconds, to practise everything in this note without installing anything on your system.

mkdir lab-postgres && cd lab-postgres
cat > docker-compose.yml <<'EOF'
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: ana
      POSTGRES_PASSWORD: s3nha-forte-de-verdade
      POSTGRES_DB: loja
    ports:
      - "127.0.0.1:5432:5432"
    volumes:
      - dados:/var/lib/postgresql/data
volumes:
  dados:
EOF
docker compose up -d
docker compose exec db psql -U ana -d loja -c "SELECT version();"

Resultado esperado: a última linha imprime a versão do Postgres — se aparecer, o container subiu, aceitou a senha definida e criou o database loja.Expected result: the last line prints the Postgres version — if it shows up, the container came up, accepted the configured password, and created the loja database.

psql "postgresql://ana:s3nha-forte-de-verdade@localhost:5432/loja"   # do seu HOST, direto
docker compose exec db pg_dump -U ana loja > backup.sql              # pratique o backup da seção anterior
docker compose down                                                   # para os containers, mantém o volume
docker compose down -v                                                # remove TAMBÉM o volume (apaga os dados)
Diferenças entre este laboratório e um banco real (gerenciado ou em produção): aqui os dados vivem num volume Docker no seu disco — ele sobrevive a um docker compose down, mas some com -v, com uma reinstalação do Docker, ou se você trocar de máquina; um serviço gerenciado como o RDS tem o disco (EBS) e os backups automáticos independentes do processo. A rede também é a mesma do Docker explicada na nota de segurança: 127.0.0.1:5432:5432 deixa a porta só no seu host; sem o 127.0.0.1, ficaria acessível por qualquer coisa que alcance a sua máquina. E não há TLS nem pg_hba.conf customizado aqui — a imagem oficial já libera senha de qualquer host dentro do container por padrão, o que é aceitável só porque é um laboratório local.Differences between this lab and a real database (managed or in production): here the data lives in a Docker volume on your disk — it survives a docker compose down, but disappears with -v, with a Docker reinstall, or if you switch machines; a managed service like RDS has the disk (EBS) and automated backups independent of the process. The network is also the same Docker setup explained in the security note: 127.0.0.1:5432:5432 keeps the port local to your host only; without the 127.0.0.1, it would be reachable by anything that can reach your machine. And there is no TLS or custom pg_hba.conf here — the official image already allows password auth from any host inside the container by default, which is acceptable only because this is a local lab.

Para algo mais perto de produção, veja a nota de AWS (RDS) ou suba um Postgres numa VM de verdade e aplique o pg_hba.conf e o TLS desta nota de propósito.For something closer to production, see the AWS note (RDS) or spin up Postgres on a real VM and apply this note's pg_hba.conf and TLS on purpose.
