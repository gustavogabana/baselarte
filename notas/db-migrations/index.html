O que é uma migrationWhat a migration is

Uma migration é um arquivo versionado que descreve uma mudança no esquema do banco: criar uma tabela, adicionar uma coluna, criar um índice, renomear algo, mover dados. Os arquivos ficam no repositório, ao lado do código, e são aplicados em ordem por uma ferramenta que lembra, dentro do próprio banco, quais já rodaram.A migration is a versioned file that describes one change to the database schema: create a table, add a column, create an index, rename something, move data. The files live in the repository next to the code and are applied in order by a tool that remembers, inside the database itself, which ones have already run.

Pense no Git, só que para o banco: cada migration é um commit do esquema. O estado atual do banco é a soma de todas as migrations aplicadas, da primeira até a última. Qualquer banco (o seu notebook, o CI, staging, produção) que rodar a mesma sequência chega ao mesmo esquema.Think of Git, but for the database: each migration is a commit of the schema. The current state of the database is the sum of every applied migration, from the first to the last. Any database (your laptop, CI, staging, production) that runs the same sequence ends up with the same schema.

Qual problema resolveWhat problem it solves

Sem migrations, o esquema muda "na mão": alguém roda um ALTER TABLE no banco de produção, outro esquece de rodar no staging, o colega novo não sabe quais comandos rodar para montar o banco local. O resultado tem nome: drift, quando bancos que deveriam ser iguais ficam diferentes e ninguém sabe exatamente como.Without migrations, the schema changes "by hand": someone runs an ALTER TABLE on the production database, someone else forgets to run it on staging, the new colleague does not know which commands to run to build the local database. The result has a name: drift, when databases that should be identical end up different and nobody knows exactly how.

Duas filosofias: SQL escrito ou esquema declarativoTwo philosophies: hand-written SQL or a declarative schema

Todas as ferramentas acabam executando SQL, mas diferem em quem escreve esse SQL:Every tool ends up running SQL, but they differ in who writes that SQL:

  • Versionada por SQL (Flyway, Liquibase): você escreve o ALTER TABLE. Controle total, nenhuma mágica, mas é você quem mantém o código das entidades e o SQL em sincronia.SQL-versioned (Flyway, Liquibase): you write the ALTER TABLE. Full control, no magic, but you keep the entity code and the SQL in sync.
  • Gerada a partir do modelo (Prisma, Alembic com autogenerate, TypeORM, Django): você muda o modelo (o schema.prisma ou as classes do SQLAlchemy), a ferramenta compara com o banco e gera o SQL da diferença. Rápido, mas o SQL gerado precisa ser lido antes do commit: renomear uma coluna pode virar "apagar e criar", perdendo dados.Generated from the model (Prisma, Alembic with autogenerate, TypeORM, Django): you change the model (the schema.prisma or the SQLAlchemy classes), the tool diffs it against the database and generates the SQL for the difference. Fast, but the generated SQL must be read before committing: renaming a column can turn into "drop and create", losing data.
Nas duas filosofias o artefato que vai para produção é o mesmo: um arquivo de migration imutável, com SQL concreto. O modelo declarativo é só uma forma mais confortável de produzir esse arquivo.In both philosophies the artifact that reaches production is the same: an immutable migration file with concrete SQL. The declarative model is just a more comfortable way of producing that file.

A regra de ouro de qualquer ferramenta: migration aplicada em qualquer ambiente compartilhado é imutável. Errou? Escreva uma migration nova que corrige. Como o banco precisa estarWhat the database must look like

Migrations cuidam do que fica dentro do banco (tabelas, índices, constraints, dados de referência). O que está em volta normalmente vem antes, por infraestrutura (Docker Compose, Terraform, o painel do provedor):Migrations take care of what lives inside the database (tables, indexes, constraints, reference data). What is around it usually comes first, from infrastructure (Docker Compose, Terraform, the provider's console):

  • O servidor e o database existem (CREATE DATABASE app). Flyway e Alembic não criam o database; o prisma migrate dev cria em desenvolvimento, mas em produção você não deve depender disso.The server and the database exist (CREATE DATABASE app). Flyway and Alembic do not create the database; prisma migrate dev does in development, but in production you should not rely on it.
  • Um usuário com permissão de DDL (criar e alterar tabelas) para rodar as migrations. Em produção, o ideal é separar: um usuário de migration (dono das tabelas) e um usuário da aplicação só com SELECT/INSERT/UPDATE/DELETE.A user with DDL permission (create and alter tables) to run the migrations. In production, ideally separate them: a migration user (owner of the tables) and an application user with only SELECT/INSERT/UPDATE/DELETE.
  • O schema vazio (sem tabelas) num projeto novo. A ferramenta cria a tabela de histórico sozinha na primeira execução.An empty schema (no tables) in a new project. The tool creates its history table on its own on the first run.
  • Extensões como pgcrypto ou postgis podem ir numa migration (CREATE EXTENSION IF NOT EXISTS) se o usuário tiver permissão; em bancos gerenciados às vezes só o admin pode, aí ficam na infraestrutura.Extensions such as pgcrypto or postgis can go in a migration (CREATE EXTENSION IF NOT EXISTS) if the user is allowed; on managed databases sometimes only the admin can, so they stay in the infrastructure.

services:

A primeira migration tem todas as tabelas?Does the first migration have every table?

A primeira migration contém tudo o que existe no momento em que você a cria, e nada além. Num projeto realmente novo, isso costuma ser pouco: users e talvez mais uma ou duas tabelas. Você não precisa (nem deve) desenhar o banco inteiro do futuro no V1.The first migration contains everything that exists at the moment you create it, and nothing more. In a truly new project, that is usually little: users and maybe one or two more tables. You do not need to (and should not) design the whole future database in V1.

Daí em diante, cada migration é um delta: só a mudança daquela tarefa. Feature de pedidos? V2__create_orders.sql. Precisa do telefone do usuário? V3__add_users_phone.sql. Nunca volte ao V1 para "encaixar" a coluna nova, nem num projeto que ainda não está em produção, assim que alguém além de você já rodou aquele arquivo.From then on, each migration is a delta: only the change for that task. Orders feature? V2__create_orders.sql. Need the user's phone? V3__add_users_phone.sql. Never go back to V1 to "fit in" the new column, even in a project not yet in production, as soon as anyone other than you has run that file.

Banco que já existe: baselineAn existing database: baseline

Se o projeto já tem um banco em produção criado na mão (ou com ddl-auto=update, create_all(), synchronize: true), você não pode rodar um V1 com CREATE TABLE users: a tabela já existe e vai dar erro. O caminho é o baseline:If the project already has a production database created by hand (or with ddl-auto=update, create_all(), synchronize: true), you cannot run a V1 with CREATE TABLE users: the table exists and it will fail. The way out is a baseline:

  1. Gere o SQL do esquema atual (pg_dump --schema-only ou o diff da ferramenta) e salve como a primeira migration.Generate the SQL of the current schema (pg_dump --schema-only or the tool's diff) and save it as the first migration.
  2. Nos bancos que já têm essas tabelas, marque essa migration como aplicada sem executá-la.On databases that already have those tables, mark that migration as applied without running it.
  3. Bancos novos (dev, CI) rodam o baseline normalmente e chegam ao mesmo esquema.New databases (dev, CI) run the baseline normally and reach the same schema.
FerramentaToolMarcar o baseline como aplicadoMark the baseline as applied
Flywayflyway baseline ouor spring.flyway.baseline-on-migrate=true (versão do baseline: baseline-version)(baseline version: baseline-version)
Prismanpx prisma migrate resolve --applied 0_init

Desligue a geração automática de esquema assim que adotar migrations: spring.jpa.hibernate.ddl-auto=validate (ou none), nada de Base.metadata.create_all() no startup do FastAPI, synchronize: false no TypeORM. Duas fontes de verdade para o esquema é exatamente o drift que as migrations vieram resolver.Turn off automatic schema generation as soon as you adopt migrations: spring.jpa.hibernate.ddl-auto=validate (or none), no Base.metadata.create_all() at FastAPI startup, synchronize: false in TypeORM. Two sources of truth for the schema is exactly the drift migrations came to solve.

Java + Spring: FlywayJava + Spring: Flyway

O Flyway é a escolha mais comum em Spring Boot. Você escreve SQL puro, e o Spring Boot roda o Flyway sozinho no startup, antes do Hibernate/JPA subir.Flyway is the most common choice in Spring Boot. You write plain SQL, and Spring Boot runs Flyway on its own at startup, before Hibernate/JPA comes up.

1. Dependências1. Dependencies

<!-- pom.xml -->
<!-- Spring Boot 4: the dedicated starter. Spring Boot 3: org.flywaydb:flyway-core instead. -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-flyway</artifactId>
</dependency>
<!-- Since Flyway 10, each database has its own module -->
<dependency>
  <groupId>org.flywaydb</groupId>
  <artifactId>flyway-database-postgresql</artifactId>
</dependency>
<dependency>
  <groupId>org.postgresql</groupId>
  <artifactId>postgresql</artifactId>
  <scope>runtime</scope>
</dependency>

2. Configuração2. Configuration

# src/main/resources/application.yml
spring:
  datasource:
    url: ${DATABASE_URL:jdbc:postgresql://localhost:5432/app}
    username: ${DB_USER:app}

    hibernate:
      ddl-auto: validate        # Hibernate only CHECKS the schema; Flyway is the one who changes it

3. A primeira migration e as seguintes3. The first migration and the next ones

O nome do arquivo é a configuração: V + versão + dois underscores + descrição + .sql.The file name is the configuration: V + version + two underscores + description + .sql.

src/main/resources/db/migration/
├── V1__create_users.sql
├── V2__create_orders.sql
├── V3__add_users_phone.sql
└── R__orders_summary_view.sql      # repeatable: re-runs whenever its content changes
-- V1__create_users.sql  (the first one: only what exists today)
CREATE TABLE users (
  id          bigserial    PRIMARY KEY,
  email       varchar(255) NOT NULL UNIQUE,
  name        varchar(120) NOT NULL,
  created_at  timestamptz  NOT NULL DEFAULT now()
);

-- V2__create_orders.sql  (a delta: the orders feature)
CREATE TABLE orders (
  id          bigserial    PRIMARY KEY,
  user_id     bigint       NOT NULL REFERENCES users(id),
  total_cents integer      NOT NULL CHECK (total_cents >= 0),
  created_at  timestamptz  NOT NULL DEFAULT now()
);
CREATE INDEX idx_orders_user_id ON orders(user_id);

-- V3__add_users_phone.sql  (another delta: nullable, so existing rows stay valid)
ALTER TABLE users ADD COLUMN phone varchar(30);
// The entity must match the schema; with ddl-auto=validate the app refuses to start if it does not
@Entity
@Table(name = "users")
public class User {
  @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id;
  @Column(nullable = false, unique = true) private String email;
  @Column(nullable = false) private String name;
  private String phone;                                   // added in V3
  @Column(name = "created_at", insertable = false, updatable = false) private OffsetDateTime createdAt;
}

4. Rodar e inspecionar4. Run and inspect

./mvnw spring-boot:run          # applies pending migrations at startup, then starts the app

# Outside the app (CI, a deploy step), with the Flyway CLI or the Docker image:
flyway -url=jdbc:postgresql://localhost:5432/app -user=app -password=dev \
       -locations=filesystem:src/main/resources/db/migration info      # what is applied / pending
flyway ... migrate        # apply pending
flyway ... validate       # do the files match the history? (checksums)
flyway ... repair         # fix the history after a failed migration (never to hide an edited file)
O Flyway Community não tem undo (os scripts U1__... são da edição paga). Na prática isso é bom: em produção, desfazer quase sempre é uma migration nova para frente (roll forward), não um DROP às pressas.Flyway Community has no undo (the U1__... scripts are a paid feature). In practice that is fine: in production, undoing is almost always a new forward migration (roll forward), not a rushed DROP.

TypeScript: PrismaTypeScript: Prisma

No Prisma, a fonte da verdade é o arquivo schema.prisma. Você altera o modelo, e o prisma migrate dev gera uma pasta com o SQL da diferença. É o modelo "declarativo": você descreve o destino, a ferramenta escreve o caminho.In Prisma, the source of truth is the schema.prisma file. You change the model, and prisma migrate dev generates a folder with the SQL for the difference. It is the "declarative" model: you describe the destination, the tool writes the route.

1. Instalar e iniciar1. Install and initialise

npm install -D prisma
npm install @prisma/client @prisma/adapter-pg dotenv
npx prisma init --datasource-provider postgresql     # creates prisma/schema.prisma, prisma.config.ts and .env
echo 'DATABASE_URL="postgresql://app:dev@localhost:5432/app"' > .env
// prisma.config.ts  (Prisma 7: the connection URL lives here; in Prisma 6 it was url = env(...) in the schema)

export default defineConfig({
  schema: 'prisma/schema.prisma',
  migrations: { path: 'prisma/migrations' },
  datasource: { url: env('DATABASE_URL') },
});

2. O modelo e a primeira migration2. The model and the first migration

// prisma/schema.prisma

  provider = "prisma-client"

Use --create-only, replace the SQL with ALTER TABLE ... RENAME COLUMN and only then apply. migrate dev may also ask to reset the database when it detects drift: fine on your laptop, never in production.

E TypeORM ou Sequelize?What about TypeORM or Sequelize?

Mesmo conceito, outros nomes. No TypeORM: synchronize: false, typeorm migration:generate src/migrations/AddPhone -d src/data-source.ts gera uma classe com up()/down() a partir das entidades, e migration:run aplica (histórico na tabela migrations). No Sequelize, o sequelize-cli cria arquivos com up/down escritos à mão e guarda o histórico em SequelizeMeta.Same concept, different names. In Sequelize, sequelize-cli creates files with hand-written up/down and keeps the history in SequelizeMeta.

Python + FastAPI: AlembicPython + FastAPI: Alembic

O FastAPI não tem ORM próprio; o par mais comum é SQLAlchemy (o ORM) + Alembic (as migrations, do mesmo autor). O Alembic gera migrations em Python comparando seus modelos com o banco (--autogenerate), e você revisa.FastAPI has no ORM of its own; the most common pair is SQLAlchemy (the ORM) + Alembic (the migrations, by the same author). Alembic generates Python migrations by diffing your models against the database (--autogenerate), and you review them.

1. Instalar e iniciar1. Install and initialise

uv add fastapi sqlalchemy alembic "psycopg[binary]" pydantic-settings
uv run alembic init migrations       # creates alembic.ini and migrations/ (env.py, versions/)
# app/db.py
from datetime import datetime
from sqlalchemy import BigInteger, String, func
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column

class Base(DeclarativeBase):
    pass

class User(Base):
    __tablename__ = "users"
    id: Mapped[int] = mapped_column(BigInteger, primary_key=True)
    email: Mapped[str] = mapped_column(String(255), unique=True)
    name: Mapped[str] = mapped_column(String(120))
    created_at: Mapped[datetime] = mapped_column(server_default=func.now())
# migrations/env.py (the two lines that matter)
from app.db import Base
from app.settings import settings          # pydantic-settings, reads DATABASE_URL from env/.env

config.set_main_option("sqlalchemy.url", settings.database_url)  # e.g. postgresql+psycopg://app:dev@localhost/app
target_metadata = Base.metadata            # what autogenerate compares against

2. A primeira revisão2. The first revision

uv run alembic revision --autogenerate -m "create users"
# writes migrations/versions/3f1a9c2b7d10_create_users.py
uv run alembic upgrade head          # apply everything up to the latest revision
# migrations/versions/3f1a9c2b7d10_create_users.py
from alembic import op
import sqlalchemy as sa

revision = "3f1a9c2b7d10"
down_revision = None                 # None = this is the first one (the root of the chain)

def upgrade() -> None:
    op.create_table(
        "users",
        sa.Column("id", sa.BigInteger(), primary_key=True),
        sa.Column("email", sa.String(255), nullable=False, unique=True),
        sa.Column("name", sa.String(120), nullable=False),
        sa.Column("created_at", sa.DateTime(), server_default=sa.func.now(), nullable=False),
    )

def downgrade() -> None:
    op.drop_table("users")

3. As próximas: a corrente de revisões3. The next ones: the chain of revisions

Cada revisão nova aponta para a anterior com down_revision. É isso, e não o nome do arquivo, que define a ordem.Each new revision points to the previous one with down_revision. That, not the file name, defines the order.

# add `phone: Mapped[str | None] = mapped_column(String(30))` to User, then:
uv run alembic revision --autogenerate -m "add users phone"
#   revision = "8b2e44c0a5f1"
#   down_revision = "3f1a9c2b7d10"      <- the chain
#   def upgrade(): op.add_column("users", sa.Column("phone", sa.String(30), nullable=True))
uv run alembic upgrade head

uv run alembic current               # which revision this database is at
uv run alembic history               # the whole chain
uv run alembic downgrade -1          # undo the last one (dev); in production prefer roll forward
uv run alembic check                 # fails if the models have changes with no migration (great in CI)
O autogenerate não enxerga tudo: renomeações viram "apagar + criar", e mudanças de tipo, constraints sem nome e alguns defaults podem passar batido. Sempre abra o arquivo gerado. E tire o Base.metadata.create_all() do startup da aplicação: quem cria tabela agora é o Alembic.Autogenerate does not see everything: renames become "drop + create", and type changes, unnamed constraints and some defaults may slip by. Always open the generated file. And remove Base.metadata.create_all() from the application startup: Alembic creates the tables now.

Conflitos em equipeConflicts in a team

O conflito clássico: duas pessoas criam migrations ao mesmo tempo, em branches diferentes, a partir do mesmo ponto. Cada branch funciona sozinha; o problema aparece no merge.The classic conflict: two people create migrations at the same time, on different branches, from the same starting point. Each branch works alone; the problem shows up at merge time.

Regras que evitam a maior parte dos conflitosRules that avoid most conflicts

  • Nunca edite uma migration que já saiu da sua máquina. Corrija com outra migration.Never edit a migration that has left your machine. Fix it with another migration.
  • Uma mudança de esquema por migration, pequena e com nome descritivo. Migrations gigantes conflitam mais e são mais difíceis de revisar.One schema change per migration, small and descriptively named. Huge migrations conflict more and are harder to review.
  • Rebase antes do merge e rode as migrations de novo localmente (de um banco limpo) para ver a sequência final.Rebase before merging and run the migrations again locally (from a clean database) to see the final sequence.
  • O CI aplica todas as migrations num banco vazio a cada PR (e roda flyway validate, prisma migrate status ou alembic check). Se a sequência não monta do zero, o PR não entra.CI applies every migration to an empty database on each PR (and runs flyway validate, prisma migrate status or alembic check). If the sequence does not build from scratch, the PR does not merge.
  • Ninguém altera o banco compartilhado na mão. Um ALTER manual em staging é drift garantido no próximo deploy.Nobody changes the shared database by hand. A manual ALTER on staging is guaranteed drift on the next deploy.

Em produçãoIn production

Quando rodarWhen to run

Duas opções comuns: (a) a aplicação roda as migrations no startup (padrão do Spring Boot com Flyway), ou (b) um passo separado do deploy roda migrate antes de subir a versão nova (um job no pipeline, um init container no Kubernetes, uma task one-off no ECS). Com várias réplicas, (b) é mais previsível: uma execução só, logs separados, e se falhar o deploy para antes de trocar o código.Two common options: (a) the application runs the migrations at startup (the Spring Boot default with Flyway), or (b) a separate deploy step runs migrate before rolling out the new version (a pipeline job, a Kubernetes init container, a one-off ECS task). With several replicas, (b) is more predictable: a single run, separate logs, and if it fails the deploy stops before swapping the code.

Mudanças sem downtime: expandir e contrairZero-downtime changes: expand and contract

Durante um deploy, a versão antiga e a nova do código rodam ao mesmo tempo contra o mesmo banco. Então toda migration precisa ser compatível com as duas. Renomear name para full_name num passo só quebra a versão antiga. O jeito seguro é dividir em etapas:During a deploy, the old and new versions of the code run at the same time against the same database. So every migration must be compatible with both. Renaming name to full_name in one step breaks the old version. The safe way is to split it into stages:
