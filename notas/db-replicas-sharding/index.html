O problema e a escadaThe problem and the ladder

Um banco em um servidor só cresce até o limite da máquina: CPU, memória, disco, conexões. Depois disso há duas perguntas diferentes, e elas têm respostas diferentes. Leitura demais? Réplicas copiam os dados para outras máquinas que só respondem consultas. Escrita demais, ou dados demais para um disco? Só dividir os dados entre servidores (sharding) resolve, porque toda escrita de uma linha ainda passa por um único primário.A database on one server grows until the machine's limit: CPU, memory, disk, connections. Past that there are two different questions with different answers. Too many reads? Replicas copy the data to other machines that only answer queries. Too many writes, or too much data for one disk? Only splitting the data across servers (sharding) solves it, because every write to a row still goes through a single primary.

1. Primário, WAL e réplicas1. Primary, WAL and replicas

Todo banco relacional grava as mudanças primeiro em um log (no Postgres, o WAL, write-ahead log) e só depois nos arquivos de dados. A streaming replication do Postgres aproveita isso: o primário envia o WAL a um standby assim que ele é gerado, sem esperar o segmento de 16 MB encher, e o standby reaplica as mudanças. Em modo assíncrono ele costuma ficar menos de um segundo atrás.Every relational database writes changes first to a log (in Postgres, the WAL, write-ahead log) and only then to the data files. Postgres streaming replication builds on that: the primary sends the WAL to a standby as soon as it is generated, without waiting for the 16 MB segment to fill, and the standby replays the changes. In asynchronous mode it is usually under a second behind.

Montar na mão (Postgres)Setting it up by hand (Postgres)

É o que o laboratório da seção 6 faz, e é o que o RDS faz por você. No primário, um usuário de replicação, uma linha no pg_hba.conf e max_wal_senders suficiente. No standby, um backup base, um arquivo standby.signal vazio e o primary_conninfo. A opção -R do pg_basebackup grava os dois últimos.This is what the section 6 lab does, and what RDS does for you. On the primary, a replication user, a line in pg_hba.conf and enough max_wal_senders. On the standby, a base backup, an empty standby.signal file and primary_conninfo. The -R option of pg_basebackup writes the last two.

# primário: pg_hba.conf
host  replication  replicator  192.168.1.100/32  scram-sha-256

# standby: backup base + standby.signal + primary_conninfo (e um slot de replicação)
pg_basebackup -h 192.168.1.50 -U replicator -D /var/lib/postgresql/data \
  -R -X stream -C -S replica1

# monitorar, no primário
SELECT application_name, state, sync_state,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS replay_lag_bytes
FROM pg_stat_replication;

# promover o standby a primário (failover)
SELECT pg_promote();
Slot de replicação enche o disco. Um slot impede o primário de reciclar o WAL que o standby ainda precisa. Se o standby some, o WAL acumula em pg_wal até lotar o disco. Limite com max_slot_wal_keep_size, como no laboratório, e alarme o tamanho do WAL retido.A replication slot can fill the disk. A slot stops the primary from recycling WAL the standby still needs. If the standby disappears, WAL piles up in pg_wal until the disk is full. Cap it with max_slot_wal_keep_size, as in the lab, and alarm on the retained WAL size.

Assíncrona ou síncronaAsynchronous or synchronous

O padrão é assíncrono: o COMMIT não espera o standby, então uma queda do primário pode perder as últimas transações confirmadas. No modo síncrono (synchronous_standby_names não vazio) o commit espera, e synchronous_commit escolhe até onde:The default is asynchronous: COMMIT does not wait for the standby, so a primary crash can lose the last committed transactions. In synchronous mode (synchronous_standby_names non-empty) the commit waits, and synchronous_commit chooses how far:

There is also quorum: ANY 2 (s1, s2, s3) waits for any two.

2. Lidar com réplicas: lag, consistência, conflitos2. Living with replicas: lag, consistency, conflicts

Adicionar a réplica é a parte fácil. O difícil é que ela sempre está um pouco no passado, e o app precisa ser desenhado para isso.Adding the replica is the easy part. The hard part is that it is always a little in the past, and the app must be designed for that.

Medir o lagMeasuring lag

  • Em bytes, no primário: pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) em pg_stat_replication. Se a distância até sent_lsn é grande, o primário está carregado; entre sent e replay, é rede ou réplica lenta.In bytes, on the primary: pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) from pg_stat_replication. A large gap up to sent_lsn means a loaded primary; between sent and replay, network or a slow replica.
  • Em tempo, na réplica: now() - pg_last_xact_replay_timestamp(). Cuidado: num primário parado esse valor cresce mesmo com a réplica em dia. É o mesmo cálculo da métrica ReplicaLag do RDS, que por isso pode mostrar até 5 minutos de lag sem transações.In time, on the replica: now() - pg_last_xact_replay_timestamp(). Careful: on an idle primary this value grows even with the replica caught up. It is the same calculation as RDS's ReplicaLag metric, which is why it can show up to 5 minutes of lag with no transactions.

As causas típicas de lag, segundo a AWS: escrita muito concorrente ou lotes grandes no primário; consultas pesadas ou lentas na própria réplica, que disputam recurso com a reaplicação; e transações enormes ou DDL, porque a ordem dos commits é preservada.Typical lag causes, per AWS: highly concurrent writes or big batches on the primary; heavy or slow queries on the replica itself, competing with replay; and huge transactions or DDL, because commit order is preserved.

Conflitos: a réplica cancela consultasConflicts: the replica cancels queries

O primário não enxerga as consultas da réplica. Quando a reaplicação do WAL entra em conflito com uma consulta que está rodando na réplica (por exemplo, o VACUUM do primário removeu linhas que a consulta ainda via, ou um DROP TABLE pegou um lock exclusivo), a réplica espera ou cancela a consulta. Os controles:The primary cannot see the replica's queries. When WAL replay conflicts with a query running on the replica (for example, the primary's VACUUM removed rows the query still saw, or a DROP TABLE took an exclusive lock), the replica waits or cancels the query. The pg_stat_database_conflicts view, on the replica, shows cancellations by reason.

Uma topologia típicaA typical topology

  • Endpoints do Aurora: o cluster endpoint sempre aponta para o writer (muda sozinho no failover); o reader endpoint balanceia conexões entre os readers (não balanceia consultas: para espalhar cada consulta, abra uma conexão por consulta); o custom endpoint agrupa um subconjunto de instâncias (por exemplo, readers maiores para relatórios); o instance endpoint serve para diagnóstico. Se o cluster só tem o writer, o reader endpoint aponta para ele.Aurora endpoints: the cluster endpoint always points to the writer (it changes by itself on failover); the reader endpoint balances connections among the readers (it does not balance queries: to spread each query, open a connection per query); the custom endpoint groups a subset of instances (for example, larger readers for reports); the instance endpoint is for diagnosis. If the cluster has only the writer, the reader endpoint points to it.
  • RDS Proxy: mantém um pool de conexões e as multiplexa (todas as operações de uma transação usam uma conexão do banco), o que protege o banco de rajadas, e reconecta a um standby no failover preservando as conexões do app. Para Aurora e Multi-AZ DB cluster você pode criar endpoints somente leitura (TargetRole = READ_ONLY), que reagem a um reader que cai sem esperar o cache de DNS. Já para uma instância RDS com réplicas, o proxy só se associa ao writer, não a uma réplica de leitura.RDS Proxy: keeps a connection pool and multiplexes it (all operations of a transaction use one database connection), which protects the database from bursts, and reconnects to a standby on failover while preserving app connections. For Aurora and Multi-AZ DB clusters you can create read-only endpoints (TargetRole = READ_ONLY), which react to a reader dying without waiting for the DNS cache. For an RDS instance with replicas, however, the proxy only associates with the writer, not a read replica.
  • Sem autoscaling de réplica no RDS: o RDS não adiciona nem remove réplicas conforme a demanda; você cria e apaga à mão. Se apagar o primário sem apagar as réplicas na mesma Região, cada réplica é promovida a instância independente.No replica autoscaling on RDS: RDS does not add or remove replicas as demand changes; you create and delete them by hand. If you delete the primary without deleting its replicas in the same Region, each replica is promoted to a standalone instance.
  • Lag e failover: no Multi-AZ DB cluster com PostgreSQL, o tempo de failover depende do menor lag entre os dois readers, porque o escolhido precisa aplicar o que falta antes de virar writer. Por isso a AWS recomenda alarmar o lag.Lag and failover: in a Multi-AZ DB cluster with PostgreSQL, failover time depends on the lowest lag of the two readers, because the chosen one must apply what is missing before becoming writer. That is why AWS recommends alarming on lag.

4. Sharding: dividir os dados entre servidores4. Sharding: splitting data across servers

No sharding cada servidor (shard) guarda um pedaço das linhas, e cada shard é o primário dos seus dados, com as suas próprias réplicas. A escrita escala porque deixa de passar por um único nó. O preço é que o banco deixa de ser “um banco”: o que era trivial (um join, uma transação, um COUNT) vira problema distribuído.In sharding each server (shard) holds a slice of the rows, and each shard is the primary of its own data, with its own replicas. Writes scale because they no longer go through a single node. The price is that the database stops being “one database”: what was trivial (a join, a transaction, a COUNT) becomes a distributed problem.

Particionar não é fazer shardPartitioning is not sharding

O Postgres tem particionamento declarativo (range, list e hash), que divide uma tabela em pedaços dentro do mesmo servidor. Ele ajuda com poda de partições (partition pruning), com manutenção (apagar uma partição antiga é quase instantâneo) e com localidade de cache, mas CPU, memória e disco continuam sendo de uma máquina só. A documentação sugere considerar particionar quando a tabela passa da memória do servidor. Sharding é o passo seguinte: os pedaços ficam em máquinas diferentes.Postgres has declarative partitioning (range, list and hash), which splits a table into pieces inside the same server. It helps with partition pruning, with maintenance (dropping an old partition is nearly instant) and with cache locality, but CPU, memory and disk still belong to one machine. The docs suggest considering partitioning when the table exceeds the server's memory. Sharding is the next step: the pieces live on different machines.

Duas restrições que importam: uma chave primária ou UNIQUE numa tabela particionada precisa incluir todas as colunas da chave de partição, e partições demais aumentam o tempo de planejamento.Two restrictions that matter: a primary key or UNIQUE on a partitioned table must include all the partition key columns, and too many partitions increase planning time.

Escolher a chave de shardChoosing the shard key

É a decisão mais difícil de desfazer. Uma boa chave: (1) aparece em quase toda consulta, para que ela caia em um shard só; (2) distribui bem, sem shards quentes; (3) mantém junto o que é consultado junto. Em SaaS multi-tenant, tenant_id costuma ser a escolha natural.It is the hardest decision to undo. A good key: (1) appears in almost every query, so it lands on a single shard; (2) distributes evenly, with no hot shards; (3) keeps together what is queried together. In multi-tenant SaaS, tenant_id is usually the natural choice.

It is the case where reading from the replica hurts most. The drawing below is what the section 6 lab implements.

  1. POST /orders. O router sabe que isto é escrita e abre conexão com o primário.POST /orders. The router knows this is a write and opens a connection to the primary.
  2. INSERT ... RETURNING id. O primário grava no WAL e confirma o commit. Assíncrono: não espera a réplica.INSERT ... RETURNING id. The primary writes to the WAL and acknowledges the commit. Asynchronous: it does not wait for the replica.

If false, or if the replica is down, the API reads from the primary (served_by: primary (...)). The replay position only advances, so the check has no race condition.

O que esse desenho não resolve. (1) O token precisa viajar: cabeçalho, cookie ou sessão; se o cliente o perde, volta ao split ingênuo. (2) Se a réplica fica muito atrás, quase todas as leituras vão ao primário: o lag vira carga no primário. Alarme o lag. (1) The token has to travel: header, cookie or session; if the client loses it, you are back to the naive split. (2) If the replica falls far behind, nearly every read goes to the primary: lag becomes load on the primary. Alarm on lag. (3) Between requests from different users, a read may still be stale; the token is not needed for that and the strategy is to accept it.

app/app.pyapp/app.py

import hashlib
import json
import os
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

import psycopg

PRIMARY = os.environ["PRIMARY_DSN"]
REPLICA = os.environ["REPLICA_DSN"]
SHARDS = os.environ["SHARD_DSNS"].split(",")
BUCKETS = 64  # logical shards: fixed forever; only the bucket -> server map changes


def connect(dsn):
    return psycopg.connect(dsn, autocommit=True, connect_timeout=2)


# ---- read/write split with read-your-writes --------------------------------
def create_order(tenant, customer, total):
    with connect(PRIMARY) as db:
        order_id = db.execute(
            "INSERT INTO orders (tenant_id, customer, total) VALUES (%s, %s, %s) RETURNING id",
            (tenant, customer, total),
        ).fetchone()[0]
        # taken AFTER the commit, so it is >= the commit's position in the WAL
        lsn = db.execute("SELECT pg_current_wal_lsn()::text").fetchone()[0]
    return {"id": str(order_id), "min_lsn": lsn, "served_by": "primary"}


def read_order(order_id, min_lsn):
    reason = "no token"
    try:
        with connect(REPLICA) as db:
            fresh = min_lsn is None or db.execute(
                "SELECT pg_last_wal_replay_lsn() >= %s::pg_lsn", (min_lsn,)
            ).fetchone()[0]
            if fresh:
                row = db.execute(
                    "SELECT id, customer, total FROM orders WHERE id = %s", (order_id,)
                ).fetchone()
                return row, "replica"
            reason = "replica behind the token"
    except psycopg.OperationalError:
        reason = "replica unreachable"
    with connect(PRIMARY) as db:
        row = db.execute("SELECT id, customer, total FROM orders WHERE id = %s", (order_id,)).fetchone()
    return row, f"primary ({reason})"


def lag():
    with connect(PRIMARY) as db:
        return db.execute(
            "SELECT application_name, state, sync_state, "
            "pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)::bigint AS replay_lag_bytes "
            "FROM pg_stat_replication"
        ).fetchall()


# ---- sharding by tenant -----------------------------------------------------
def bucket_of(tenant):
    return int.from_bytes(hashlib.sha256(tenant.encode()).digest()[:8], "big") % BUCKETS


def shard_of(tenant):
    return bucket_of(tenant) * len(SHARDS) // BUCKETS  # buckets 0..31 -> shard 0, 32..63 -> shard 1


def shard_create(tenant, customer, total):
    with connect(SHARDS[shard_of(tenant)]) as db:
        order_id = db.execute(
            "INSERT INTO orders (tenant_id, customer, total) VALUES (%s, %s, %s) RETURNING id",
            (tenant, customer, total),
        ).fetchone()[0]
    return {"id": str(order_id), "tenant": tenant, "bucket": bucket_of(tenant), "shard": shard_of(tenant)}


def shard_list(tenant):
    with connect(SHARDS[shard_of(tenant)]) as db:  # single-shard query: tenant_id is in the WHERE
        rows = db.execute(
            "SELECT customer, total FROM orders WHERE tenant_id = %s ORDER BY created_at DESC", (tenant,)
        ).fetchall()
    return {"tenant": tenant, "shard": shard_of(tenant), "orders": [[c, str(t)] for c, t in rows]}


def shard_stats():
    out = []  # scatter-gather: touches every shard
    for i, dsn in enumerate(SHARDS):
        with connect(dsn) as db:
            n, s = db.execute("SELECT count(*), coalesce(sum(total), 0) FROM orders").fetchone()
        out.append({"shard": i, "orders": n, "revenue": str(s)})
    return {"shards": out, "total_orders": sum(x["orders"] for x in out)}


class Handler(BaseHTTPRequestHandler):
    def reply(self, status, body, headers=()):
        data = json.dumps(body).encode()
        self.send_response(status)
        self.send_header("Content-Type", "application/json")
        for k, v in headers:
            self.send_header(k, v)
        self.end_headers()
        self.wfile.write(data)

    def body(self):
        return json.loads(self.rfile.read(int(self.headers.get("Content-Length", 0))) or "{}")

    def do_POST(self):
        parts = self.path.strip("/").split("/")
        data = self.body()
        if parts == ["orders"]:
            out = create_order(data.get("tenant", "acme"), data["customer"], data["total"])
            return self.reply(201, out, [("X-Min-LSN", out["min_lsn"])])
        if len(parts) == 3 and parts[0] == "t" and parts[2] == "orders":
            return self.reply(201, shard_create(parts[1], data["customer"], data["total"]))
        self.reply(404, {"error": "not found"})

    def do_GET(self):
        parts = self.path.strip("/").split("/")
        if len(parts) == 2 and parts[0] == "orders":
            row, served_by = read_order(parts[1], self.headers.get("X-Min-LSN"))
            if row is None:
                return self.reply(404, {"error": "order not found", "served_by": served_by})
            return self.reply(200, {"id": str(row[0]), "customer": row[1], "total": str(row[2]), "served_by": served_by})
        if parts == ["lag"]:
            return self.reply(200, [dict(zip(("replica", "state", "sync", "replay_lag_bytes"), r)) for r in lag()])
        if len(parts) == 3 and parts[0] == "t" and parts[2] == "orders":
            return self.reply(200, shard_list(parts[1]))
        if parts == ["stats"]:
            return self.reply(200, shard_stats())
        self.reply(404, {"error": "not found"})


ThreadingHTTPServer(("0.0.0.0", 8080), Handler).serve_forever()

post() { curl -s -D /tmp/h -X POST $api/orders -d "{\"customer\":\"$1\",\"total\":$2}"; }

echo "== 1. write goes to the primary and returns a token (WAL position)"
out=$(post ana 49.90); echo "$out"
id=$(echo "$out" | sed 's/.*"id": "\([^"]*\)".*/\1/'); lsn=$(grep -i x-min-lsn /tmp/h | tr -d '\r' | cut -d' ' -f2)
sleep 1
echo "== 2. read with the token: replica has already replayed it"
curl -s -H "X-Min-LSN: $lsn" $api/orders/$id; echo

echo "== 3. freeze replay on the replica (simulates lag)"
sql "SELECT pg_wal_replay_pause()" >/dev/null
out=$(post bruno 120.00); echo "$out"
id=$(echo "$out" | sed 's/.*"id": "\([^"]*\)".*/\1/'); lsn=$(grep -i x-min-lsn /tmp/h | tr -d '\r' | cut -d' ' -f2)
echo "-- read WITHOUT token (naive split): stale read"
curl -s $api/orders/$id; echo
echo "-- read WITH token: falls back to the primary"
curl -s -H "X-Min-LSN: $lsn" $api/orders/$id; echo
echo "-- lag as seen by the primary"
curl -s $api/lag; echo

echo "== 4. resume replay: the same read goes back to the replica"
sql "SELECT pg_wal_replay_resume()" >/dev/null; sleep 1
curl -s -H "X-Min-LSN: $lsn" $api/orders/$id; echo

echo "== 5. replica down: reads survive on the primary"
docker compose stop -t 1 replica >/dev/null 2>&1
curl -s -H "X-Min-LSN: $lsn" $api/orders/$id; echo
docker compose start replica >/dev/null 2>&1

Also note that acme and umbrella landed in the same bucket (32), which is normal with 64 buckets: the bucket is a unit of movement, not of isolation.

Este laboratório não faz resharding. Ele mostra o roteamento (bucket para shard) e a consulta em todos os shards, mas não move dados. Mover um bucket de verdade exige copiar as linhas, sincronizar as escritas feitas durante a cópia (por exemplo, com replicação lógica), trocar o mapa de forma atômica e só então apagar a origem. Também não há réplicas por shard nem tolerância a falha de shard.This lab does not reshard. It shows the routing (bucket to shard) and the query across all shards, but it does not move data. Really moving a bucket requires copying the rows, syncing the writes made during the copy (for example, with logical replication), switching the map atomically and only then deleting the source. There are also no per-shard replicas or shard-failure tolerance.

ChecklistChecklist

  • Meça antes: qual é o gargalo? CPU, IO, conexões, leitura, escrita?Measure first: what is the bottleneck? CPU, IO, connections, reads, writes?

  • Transação que escreve (ou usa FOR UPDATE) inteira no primário.A transaction that writes (or uses FOR UPDATE) entirely on the primary.
