Study guide

Kubernetes, from zero to production.

What Kubernetes is, the problem it solves, the configuration files and their security options, small hands-on labs with Docker on your machine, and how to run it securely on AWS.

O que é o Kubernetes e que problema ele resolveWhat Kubernetes is and the problem it solves

Kubernetes (K8s: o 8 são as letras entre K e s) é um sistema open source, criado no Google e hoje mantido pela CNCF, que roda e cuida de contêineres em várias máquinas como se fossem uma só. O nome vem do grego e significa “timoneiro”: quem conduz o navio. Pense num maestro: cada músico (contêiner) sabe tocar o seu trecho, mas alguém precisa dizer quem toca, quando, e substituir quem faltar.Kubernetes (K8s: the 8 stands for the letters between K and s) is an open source system, created at Google and now maintained by the CNCF, that runs and looks after containers across many machines as if they were one. The name is Greek for “helmsman”: the one who steers the ship. Think of a conductor: each musician (container) knows their part, but someone has to say who plays, when, and replace whoever is missing.

Pré-requisito: saber o que é um contêiner. Uma imagem é o pacote pronto (programa + bibliotecas); um contêiner é essa imagem em execução, isolada do resto da máquina. O Docker constrói e roda contêineres em uma máquina. O Kubernetes entra quando são muitos contêineres em muitas máquinas.Prerequisite: knowing what a container is. An image is the ready-made package (program + libraries); a container is that image running, isolated from the rest of the machine. Docker builds and runs containers on one machine. Kubernetes enters when there are many containers on many machines.

O problemaThe problem

Rodar um contêiner com docker run é fácil. Operar dezenas deles em produção traz perguntas que o Docker sozinho não responde:Running one container with docker run is easy. Operating dozens in production raises questions Docker alone does not answer:

  • O contêiner caiu às 3h da manhã. Quem sobe de novo?The container died at 3 a.m. Who starts it again?
  • A máquina inteira morreu. Quem move os contêineres para outra?The whole machine died. Who moves the containers to another one?
  • Chegou mais tráfego. Como ter 10 cópias em vez de 2, e dividir os acessos entre elas?More traffic arrived. How do you get 10 copies instead of 2, and split the requests among them?
  • Versão nova. Como trocar sem derrubar o site, e voltar atrás se der errado?New version. How do you swap without downtime, and go back if it fails?
  • Configuração e segredos. Como entregar senhas e variáveis sem colocá-las na imagem?Configuration and secrets. How do you deliver passwords and variables without baking them into the image?
  • Quem pode fazer o quê? E quem pode falar com quem dentro do sistema?Who may do what? And who may talk to whom inside the system?

A ideia central: declarativoThe core idea: declarative

Você não manda “suba o contêiner A na máquina 2”. Você escreve um arquivo YAML dizendo como quer que fique (“3 cópias do app A, na versão 1.27”) e o Kubernetes trabalha sem parar para que a realidade fique igual ao arquivo. É a mesma ideia do Terraform, só que para aplicações em execução.You do not say “start container A on machine 2”. You write a YAML file saying how you want things to be (“3 copies of app A, version 1.27”) and Kubernetes works non-stop to make reality match the file. It is the same idea as Terraform, but for running applications.

Quando usar, e quando não. Kubernetes vale quando você tem vários serviços, precisa de alta disponibilidade e de deploys frequentes. Para um site simples ou um único app, uma VM, o ECS/Fargate ou um PaaS custam muito menos esforço. K8s tem curva de aprendizado e custo operacional reais.When to use it, and when not. Kubernetes pays off when you have several services, need high availability and deploy often. For a simple site or a single app, a VM, ECS/Fargate or a PaaS take far less effort. K8s has a real learning curve and operating cost.

Como funciona por dentroHow it works inside

Um cluster é um conjunto de máquinas (chamadas nós). Um grupo delas, o control plane, decide; as outras, os workers, executam. Você só conversa com o control plane, pelo kubectl (a linha de comando) que chama o API server.A cluster is a set of machines (called nodes). Some of them, the control plane, decide; the others, the workers, execute. You only talk to the control plane, through kubectl (the command line) calling the API server.

O laço de reconciliaçãoThe reconciliation loop

Tudo no Kubernetes segue o mesmo padrão: cada controller olha o estado desejado (o que você escreveu) e o estado atual (o que existe) e age sobre a diferença, para sempre. Por isso um Pod apagado volta, e por isso você nunca “inicia” coisas à mão.Everything in Kubernetes follows the same pattern: each controller looks at the desired state (what you wrote) and the current state (what exists) and acts on the difference, forever. That is why a deleted Pod comes back, and why you never “start” things by hand.

Em nuvem gerenciada (EKS, GKE, AKS) o control plane é da empresa de nuvem: você cuida só dos workers e do que roda neles. É o caminho recomendado para produção.On a managed cloud (EKS, GKE, AKS) the control plane belongs to the cloud provider: you only look after the workers and what runs on them. This is the recommended path for production.

Os arquivos de configuraçãoThe configuration files

Você trabalha com manifestos: arquivos YAML, um ou vários objetos por arquivo (separados por ---), que vão no Git como código. O comando é sempre kubectl apply -f arquivo.yaml.You work with manifests: YAML files, one or several objects per file (separated by ---), kept in Git as code. Anatomia: quatro campos em todo objetoAnatomy: four fields in every object

apiVersion: apps/v1        # which API group/version defines this kind

metadata:                  # identity
  name: web                #   unique name inside the namespace
  namespace: default       #   optional; defaults to "default"

Segurança nos arquivosSecurity in the files

O Kubernetes vem aberto por padrão: um Pod roda como root se você não disser o contrário, fala com qualquer outro Pod, e recebe um token para falar com o API server. A boa notícia: quase toda proteção é uma linha de YAML. Pense em camadas:Kubernetes is open by default: a Pod runs as root unless you say otherwise, talks to any other Pod, and gets a token to talk to the API server. The good news: almost every protection is one line of YAML. Think in layers:

Camada 4 e 3: o securityContext e o PodLayers 4 and 3: the securityContext and the Pod

spec:
  serviceAccountName: web
  automountServiceAccountToken: false   # the app does not call the K8s API: give it no token
  securityContext:                      # Pod level
    runAsNonRoot: true                  # refuses to start if the image wants root
    runAsUser: 101
    seccompProfile:
      type: RuntimeDefault              # blocks dangerous system calls
  containers:
    - name: web
      image: nginxinc/nginx-unprivileged:1.27   # fixed tag (better: @sha256:digest)
      securityContext:                  # container level
        allowPrivilegeEscalation: false # no setuid tricks to become root
        readOnlyRootFilesystem: true    # attacker cannot write or drop tools
        capabilities:
          drop: ["ALL"]                 # no special Linux powers
      resources:
        requests: { cpu: 50m, memory: 64Mi }
        limits:   { cpu: 200m, memory: 128Mi }   # a crypto-miner or a leak cannot eat the node

Camada 2: o namespace diz o que é permitido (Pod Security)Layer 2: the namespace says what is allowed (Pod Security)

O Pod Security Admission vem ligado no cluster e é controlado por rótulos no Namespace. Há três perfis: privileged (sem limites), baseline (bloqueia o pior) e restricted (as boas práticas acima, obrigatórias). Três modos: enforce (recusa), audit (registra) e warn (avisa o usuário). Ele substituiu o antigo PodSecurityPolicy, removido no Kubernetes 1.25.Pod Security Admission is built into the cluster and controlled by labels on the Namespace. There are three profiles: privileged (no limits), baseline (blocks the worst) and restricted (the best practices above, mandatory). Three modes: enforce (rejects), audit (logs) and warn (warns the user). It replaced the old PodSecurityPolicy, removed in Kubernetes 1.25.

apiVersion: v1
kind: Namespace
metadata:
  name: secure
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: latest

Camada 2: RBAC, o mínimo de permissãoLayer 2: RBAC, least privilege

RBAC liga quem (ServiceAccount, usuário, grupo) a o que pode fazer (verbos sobre recursos). Um Role vale em um namespace; um ClusterRole no cluster todo. Regras de ouro: nada de cluster-admin para apps, nada de verbs: ["*"], e secrets só para quem realmente precisa.RBAC ties who (ServiceAccount, user, group) to what they may do (verbs on resources). A Role applies in one namespace; a ClusterRole cluster-wide. Golden rules: no cluster-admin for apps, no verbs: ["*"], and secrets only for those who truly need them.

kind: Role
metadata: { name: pod-reader, namespace: secure }
rules:
  - apiGroups: [""]               # "" = the core API group
    resources: ["pods"]
    verbs: ["get", "list", "watch"]   # read only
---
kind: RoleBinding                 # ties the Role to a subject
metadata: { name: pod-reader, namespace: secure }
subjects:
  - { kind: ServiceAccount, name: pod-reader, namespace: secure }
roleRef: { kind: Role, name: pod-reader, apiGroup: rbac.authorization.k8s.io }

Camada 2: NetworkPolicy, o firewall internoLayer 2: NetworkPolicy, the internal firewall

Sem nenhuma política, todo Pod fala com todo Pod, de qualquer namespace. Um invasor que entra em um Pod passeia pelo cluster inteiro. O padrão seguro é negar tudo e liberar só o necessário. (O plugin de rede precisa suportar NetworkPolicy; o do EKS, o Calico e o Cilium suportam.)With no policy, every Pod talks to every Pod, from any namespace. An intruder who gets into one Pod roams the whole cluster. The safe default is to deny everything and allow only what is needed. (The network plugin must support NetworkPolicy; EKS's, Calico and Cilium do.)

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny, namespace: secure }
spec:
  podSelector: {}                   # {} = every Pod in the namespace
  policyTypes: ["Ingress"]          # no ingress rules listed = nothing may enter
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-client-to-web, namespace: secure }
spec:
  podSelector: { matchLabels: { app: web } }   # applies to the web Pods
  policyTypes: ["Ingress"]
  ingress:
    - from:
        - podSelector: { matchLabels: { role: client } }
      ports:
        - port: 8080

Secrets: o que o base64 não fazSecrets: what base64 does not do

Um Secret guarda o valor em base64, que é só codificação, não criptografia: echo czNjcjN0 | base64 -d devolve a senha. Quem pode ler o Secret via API (ou ler o etcd) lê a senha. O que realmente protege: RBAC apertado, criptografia do etcd em repouso, e nunca versionar o YAML com o valor.A Secret stores the value in base64, which is just encoding, not encryption: echo czNjcjN0 | base64 -d returns the password. Whoever can read the Secret via the API (or read etcd) reads the password. What really protects it: tight RBAC, etcd encryption at rest, and never committing the YAML with the value.
  • Monte como arquivo (volumeMounts com readOnly: true) em vez de variável de ambiente: variáveis aparecem em dumps de erro, em /proc e em logs de depuração.Mount as a file (volumeMounts with readOnly: true) instead of an environment variable: variables show up in crash dumps, in /proc and in debug logs.
  • Em produção, mantenha o segredo fora do cluster (AWS Secrets Manager, Vault) e sincronize com o External Secrets Operator ou o Secrets Store CSI Driver. No Git, use Sealed Secrets ou SOPS (o valor vai cifrado).In production, keep the secret outside the cluster (AWS Secrets Manager, Vault) and sync it with the External Secrets Operator or the Secrets Store CSI Driver. In Git, use Sealed Secrets or SOPS (the value goes encrypted).
  • Rotacione: um segredo que muda é um segredo que, se vazar, expira.Rotate: a secret that changes is one that, if leaked, expires.

Camada 1: o cluster em siLayer 1: the cluster itself

  • API server não exposto à internet (ou restrito por IP), autenticação por identidade da nuvem, nada de usuário com senha estática.API server not exposed to the internet (or restricted by IP), authentication through cloud identity, no static-password users.
  • Logs de auditoria ligados: quem fez o quê, quando.Audit logs on: who did what, when.

metadata:
  name: web
automountServiceAccountToken: false
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  labels:

        app: web

Bônus: fechar também a saída (egress)Bonus: also close the outbound side (egress)

Negar a saída impede um Pod comprometido de “ligar para casa” (exfiltrar dados, baixar ferramentas). Mas ao negar tudo você também bloqueia o DNS, e nada mais resolve nomes (o erro é bad address 'web'). Por isso liberamos o DNS e depois cada destino necessário:Denying outbound traffic stops a compromised Pod from “phoning home” (exfiltrating data, downloading tools). But denying everything also blocks DNS, and nothing resolves names any more (the error is bad address 'web'). So we allow DNS first and then each needed destination:

# egress.yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny-egress, namespace: secure }
spec:
  podSelector: {}
  policyTypes: ["Egress"]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-dns, namespace: secure }
spec:
  podSelector: {}
  policyTypes: ["Egress"]
  egress:
    - to:
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: kube-system }
          podSelector:
            matchLabels: { k8s-app: kube-dns }
      ports:
        - { port: 53, protocol: UDP }
        - { port: 53, protocol: TCP }
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: client-egress-to-web, namespace: secure }
spec:
  podSelector: { matchLabels: { role: client } }
  policyTypes: ["Egress"]
  egress:
    - to:
        - podSelector: { matchLabels: { app: web } }
      ports:
        - port: 8080
kubectl apply -f egress.yaml
kubectl exec -n secure client -- wget -qO- -T 3 http://web | head -2          # still works
kubectl exec -n secure client -- wget -qO- -T 3 http://example.com | head -2  # blocked

Colocar em produção com segurança na AWS (EKS)Running it in production, securely, on AWS (EKS)

O serviço gerenciado da AWS é o EKS (Elastic Kubernetes Service): a AWS opera o control plane (alta disponibilidade em várias zonas, atualizações, backup do etcd) e você cuida dos nós e dos apps. O modelo de responsabilidade compartilhada vale aqui: a AWS protege o control plane; a configuração do seu cluster e dos seus Pods é com você.AWS's managed service is EKS (Elastic Kubernetes Service): AWS runs the control plane (multi-zone high availability, upgrades, etcd backups) and you look after the nodes and the apps. The shared-responsibility model applies: AWS protects the control plane; your cluster's and Pods' configuration is on you.

Custo. O EKS cobra pelo control plane por hora (cerca de US$ 0,10/h, uns US$ 73 por mês, consulte a tabela de preços atual), mais os nós EC2, o NAT gateway e o ALB. Crie o cluster de estudo, pratique e apague no mesmo dia (eksctl delete cluster). Defina um alerta de orçamento (AWS Budgets) antes de começar.Cost. EKS charges for the control plane by the hour (about US$ 0.10/h, roughly US$ 73 a month, check the current price list), plus the EC2 nodes, the NAT gateway and the ALB. Create the study cluster, practise and delete it the same day (eksctl delete cluster). Set a budget alert (AWS Budgets) before you begin.

Os comentários mostram o que cada linha protege:The shortest way to learn is eksctl, which reads a file and creates the VPC, control plane and nodes. # cluster.yaml
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig
metadata:
  name: demo
  region: us-east-1
  version: "1.35"                      # use a version currently in standard support

accessConfig:
  authenticationMode: API              # access via IAM "access entries"; no legacy aws-auth ConfigMap

vpc:
  clusterEndpoints:
    privateAccess: true
    publicAccess: true                 # best for production: false + VPN/bastion
  publicAccessCIDRs: ["203.0.113.10/32"]   # replace with YOUR IP: only it can reach the API server

secretsEncryption:
  keyARN: arn:aws:kms:us-east-1:111122223333:key/REPLACE-ME   # your own KMS key for Secrets

cloudWatch:
  clusterLogging:
    enableTypes: ["api", "audit", "authenticator", "controllerManager", "scheduler"]

iam:
  withOIDC: true                       # lets Pods assume IAM roles (IRSA)

addons:
  - name: vpc-cni
    configurationValues: '{"enableNetworkPolicy": "true"}'   # NetworkPolicy enforcement
  - name: eks-pod-identity-agent       # IAM roles for Pods (Pod Identity)

managedNodeGroups:
  - name: ng-private
    instanceType: t3.medium
    desiredCapacity: 2
    minSize: 2
    maxSize: 4
    privateNetworking: true            # nodes in private subnets, no public IP
    volumeEncrypted: true              # encrypted disks
eksctl create cluster -f cluster.yaml                       # ~15-20 minutes
aws eks update-kubeconfig --name demo --region us-east-1    # writes your kubeconfig (short-lived tokens via IAM)
kubectl get nodes
O kubectl do EKS não usa senha: o kubeconfig chama aws eks get-token e o acesso segue as suas credenciais da AWS (SSO, de preferência). Quem entra no cluster é decidido por access entries do IAM, com políticas como AmazonEKSViewPolicy; evite dar cluster-admin a todo mundo.EKS's kubectl uses no password: the kubeconfig calls aws eks get-token and access follows your AWS credentials (SSO, ideally). Who gets into the cluster is decided by IAM access entries, with policies such as AmazonEKSViewPolicy; avoid giving cluster-admin to everyone.

aws ecr create-repository --repository-name web \
  --image-scanning-configuration scanOnPush=true \

aws ecr get-login-password --region us-east-1 | docker login --username AWS --password-stdin 111122223333.dkr.ecr.us-east-1.amazonaws.com

Tags imutáveis impedem que a 1.0.0 seja sobrescrita; o scan na publicação aponta CVEs conhecidas. No manifesto, referencie a imagem pelo digest (web@sha256:…). Em CI, o próprio pipeline faz o push, com OIDC (veja a nota GitHub to AWS with OIDC), sem chave guardada.Immutable tags stop 1.0.0 from being overwritten; scan-on-push flags known CVEs. In the manifest, reference the image by digest (web@sha256:…). In CI, the pipeline itself does the push, with OIDC (see the GitHub to AWS with OIDC note), with no stored key.

Passo 3: o app com identidade própria na AWSStep 3: the app with its own AWS identity

Um Pod que precisa ler um bucket S3 ou um segredo não deve usar as credenciais do nó (que serviriam a todos os Pods) nem chaves fixas. Crie uma IAM role só com o que ele precisa e ligue-a à ServiceAccount:A Pod that must read an S3 bucket or a secret should not use the node's credentials (which would serve every Pod) nor static keys. Create an IAM role with only what it needs and tie it to the ServiceAccount:

# IRSA: the ServiceAccount carries the role to assume
apiVersion: v1
kind: ServiceAccount
metadata:
  name: web
  namespace: prod
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::111122223333:role/web-s3-read
automountServiceAccountToken: true     # IRSA needs the projected token; set false only for Pods with no AWS access

A alternativa mais nova, o EKS Pod Identity, dispensa a anotação: aws eks create-pod-identity-association --cluster-name demo --namespace prod --service-account web --role-arn …. Nos dois casos a role aceita só aquela ServiceAccount daquele namespace.The newer alternative, EKS Pod Identity, drops the annotation: aws eks create-pod-identity-association --cluster-name demo --namespace prod --service-account web --role-arn …. In both cases the role accepts only that ServiceAccount in that namespace.

Passo 4: expor com HTTPSStep 4: expose it with HTTPS

Instale o AWS Load Balancer Controller (Helm). Ele transforma um Ingress em um ALB. Certificado no ACM, HTTPS e, se quiser, WAF:Install the AWS Load Balancer Controller (Helm). It turns an Ingress into an ALB. Certificate in ACM, HTTPS and, if you want, WAF:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
  namespace: prod
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTPS":443}]'
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:us-east-1:111122223333:certificate/REPLACE-ME
    alb.ingress.kubernetes.io/ssl-policy: ELBSecurityPolicy-TLS13-1-2-2021-06
    # alb.ingress.kubernetes.io/wafv2-acl-arn: arn:aws:wafv2:...   # optional WAF
spec:
  ingressClassName: alb
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service: { name: web, port: { number: 80 } }

Mantenha os Services como ClusterIP e as subnets dos nós privadas: só o ALB fica na internet. Aponte seu domínio para o ALB (Route 53 ou Cloudflare).Keep Services as ClusterIP and the node subnets private: only the ALB faces the internet. Point your domain at the ALB (Route 53 or Cloudflare).

Passo 5: entregar com pipelineStep 5: deliver through a pipeline

O ideal é GitOps: o Git é a fonte da verdade e uma ferramenta dentro do cluster (Argo CD ou Flux) aplica o que está lá. Ninguém precisa de kubectl com permissão de escrita em produção, e todo deploy vira um commit auditável.The ideal is GitOps: Git is the source of truth and a tool inside the cluster (Argo CD or Flux) applies what is there. Nobody needs write-enabled kubectl in production, and every deploy becomes an auditable commit.

O erro mais comum em produção não é um ataque sofisticado: é um painel, um API server ou um Service LoadBalancer exposto sem querer, e um Pod root com token de ServiceAccount poderoso.
