Study guide

Cybersecurity for developers, where to start.

The map of the field, the concepts that matter, a five-stage study path, portfolio projects and where to learn, written for people who already program.

Antes de começar: o mapaBefore you start: the map

Cibersegurança parece um território único, mas é um conjunto de ofícios com perguntas diferentes: como eu quebro isto? (red team), como eu percebo que quebraram? (blue team) e como eu construo de um jeito que seja difícil de quebrar? (segurança de aplicações). Quem já programa começa com uma vantagem real: entende como o software é montado, onde as suposições escondem falhas e como um deploy funciona. Esta nota é o ponto de entrada da série de segurança do site: o mapa, os conceitos, uma trilha de estudo, projetos para o portfólio e onde aprender.Cybersecurity looks like one territory, but it is a set of crafts that ask different questions: how do I break this? (red team), how do I notice someone broke it? (blue team) and how do I build it so it is hard to break? (application security). Anyone who already programs starts with a real advantage: you understand how software is assembled, where assumptions hide flaws and how a deploy works. This note is the entry point to the site's security series: the map, the concepts, a study path, portfolio projects and where to learn.

Como um dev deve escolherHow a developer should choose

Comece por AppSec: é onde o que você já sabe rende mais rápido, a nota de aplicações web seguras já cobre a base e o mercado sempre precisa de quem fale as duas línguas, a do código e a da segurança. Em paralelo, faça a trilha ofensiva em laboratório para entender o atacante, e a defensiva para entender o que ele deixa nos logs. Depois de uns seis meses você saberá se prefere quebrar (red), investigar (blue) ou construir (AppSec/cloud). Ninguém acerta de primeira, e as bases são as mesmas.Start with AppSec: it is where what you already know pays off fastest, the secure web apps note already covers the base and the market always needs people who speak both languages, code and security. In parallel, do the offensive path in a lab to understand the attacker, and the defensive one to understand what the attacker leaves in the logs. After about six months you will know whether you prefer to break (red), investigate (blue) or build (AppSec/cloud). Nobody gets it right the first time, and the foundations are the same.

Projeto 1: auditar e endurecer o seu próprio appProject 1: audit and harden your own app

Pegue um projeto seu (qualquer um) e rode três varreduras: segredos, dependências e padrões de código inseguro. Priorize o que achar por gravidade, corrija o que for crítico e registre cada correção num commit com a explicação do risco. Em seguida revise cabeçalhos e cookies com o checklist da nota de aplicações web seguras.Take one of your projects (any of them) and run three scans: secrets, dependencies and insecure code patterns. Prioritise what you find by severity, fix what is critical and record each fix in a commit that explains the risk. Then review headers and cookies with the checklist in the secure web apps note.

# dentro da pasta do seu projeto: três varreduras, nenhuma sai da sua máquina
docker run --rm -v "$PWD:/repo" zricethezav/gitleaks:latest detect --source /repo --redact
# ^ segredos no código e no histórico do Git
docker run --rm -v "$PWD:/src" aquasec/trivy:latest fs /src
# ^ dependências com CVE, Dockerfile e IaC mal configurados
docker run --rm -v "$PWD:/src" semgrep/semgrep semgrep scan --config auto --metrics=off /src
# ^ padrões de código inseguro (injeção, criptografia fraca, XSS)

Resultado esperado: uma lista de achados, quase sempre com falsos positivos. Aprender a separá-los é metade do ofício: para cada item, escreva "real" ou "falso positivo, porque…". Se o gitleaks achar um segredo real, revogue-o primeiro e só depois limpe o histórico: um segredo que já foi para o Git deve ser tratado como vazado.Expected result: a list of findings, almost always with false positives. Learning to tell them apart is half the craft: for each item write "real" or "false positive, because…". If gitleaks finds a real secret, revoke it first and only then clean the history: a secret that reached Git must be treated as leaked.

Projeto 2: o mesmo, a cada pushProject 2: the same, on every push

Transforme as varreduras do projeto 1 num workflow do GitHub Actions. O objetivo é que um segredo ou uma dependência com CVE crítico quebre o build antes de chegar à produção. Ative também o Dependabot e o secret scanning do repositório (Settings → Code security).Turn the scans from project 1 into a GitHub Actions workflow. The goal is that a secret or a dependency with a critical CVE breaks the build before it reaches production. Also turn on Dependabot and the repository's secret scanning (Settings → Code security).

# .github/workflows/security.yml (esqueleto; fixe versões e SHAs dos actions que você usar)
name: security
on: [push, pull_request]
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }   # gitleaks lê o histórico inteiro
      - name: segredos
        run: docker run --rm -v "$PWD:/repo" zricethezav/gitleaks:latest detect --source /repo --redact
      - name: dependências e arquivos de configuração
        run: docker run --rm -v "$PWD:/src" aquasec/trivy:latest fs --exit-code 1 --severity HIGH,CRITICAL /src

Resultado esperado: um push com um arquivo .env falso (use um valor inventado) deixa o job vermelho. Teste isso de propósito, em um branch, para ter certeza de que o pipeline realmente barra. Veja também a nota de OIDC: o pipeline não deve ter chaves de nuvem fixas.Expected result: a push with a fake .env file (use an invented value) turns the job red. Test it on purpose, on a branch, to be sure the pipeline really blocks. See also the OIDC note: the pipeline must not hold static cloud keys.

Projeto 3: um mini SOC domésticoProject 3: a home mini-SOC

Aqui o lado blue se encontra com o laboratório da nota de red team. Primeiro, o jeito mais simples: gere tráfego de ataque (um scan com o nmap e uma SQL injection no DVWA), capture com o tcpdump e peça ao Suricata, um IDS de código aberto, que leia a captura.Here the blue side meets the lab from the red team note. First, the simplest way: generate attack traffic (an nmap scan and a SQL injection on DVWA), capture it with tcpdump and ask Suricata, an open-source IDS, to read the capture.

# 1. capture tráfego do laboratório (o mesmo da nota de segurança e redes)
sudo tcpdump -i any -n -w lab.pcap port 80 or port 8081 -c 2000
# 2. rode um ataque conhecido contra o DVWA: um scan com nmap e uma SQL injection
# 3. leia a captura com o Suricata e as regras Emerging Threats (gratuitas)
mkdir -p suricata-out && sudo suricata-update          # baixa o conjunto de regras
suricata -r lab.pcap -l suricata-out
cat suricata-out/fast.log                              # os alertas, uma linha cada

Resultado esperado: o fast.log lista alertas como o do scan de portas e de tentativas de injeção. Anote quais ataques foram vistos e quais passaram em silêncio: os que passaram são o seu trabalho de detecção. Depois suba o Wazuh (SIEM e agente de host) seguindo o guia oficial de implantação com Docker e instale o agente na máquina que hospeda o laboratório; compare o que cada ferramenta enxerga.Expected result: fast.log lists alerts such as the port scan and the injection attempts. Note which attacks were seen and which slipped past silently: the ones that slipped past are your detection work. Then bring up Wazuh (SIEM and host agent) following the official Docker deployment guide and install the agent on the machine hosting the lab; compare what each tool sees.

Projeto 5: uma regra de detecção em SigmaProject 5: a detection rule in Sigma

Sigma é um formato aberto e neutro de regras de detecção: você escreve uma vez e converte para o SIEM que usar. A regra abaixo traduz em código a defesa da nota de red team: um processo de servidor web não deveria gerar um shell filho. Teste rodando o exercício do shell reverso do laboratório e conferindo se a regra, convertida, dispara no seu Wazuh ou Elastic.Sigma is an open, vendor-neutral format for detection rules: you write it once and convert it for whichever SIEM you use. The rule below turns the defence from the red team note into code: a web server process should not spawn a child shell. Test it by running the reverse shell exercise from the lab and checking that the converted rule fires in your Wazuh or Elastic.

# web-shell.yml: um servidor web não deveria abrir um shell (o padrão da nota de red team)
title: Web server spawning a shell
id: 1dca4040-3843-4463-a982-c8a755bbeddc
status: experimental
description: A web server process starting a shell, a common sign of a reverse shell
logsource:
  category: process_creation
  product: linux
detection:
  selection:
    ParentImage|endswith: ['/nginx', '/apache2', '/httpd', '/php-fpm']
    Image|endswith: ['/bash', '/sh', '/dash']
  condition: selection
falsepositives:
  - Deploy scripts started by the web server
level: high

Resultado esperado: um arquivo YAML versionado, um teste que o dispara e uma nota sobre falsos positivos. O repositório SigmaHQ/sigma tem milhares de regras para você ler e o atomic-red-team (Red Canary) tem testes de técnicas do ATT&CK para provar cada regra: é o purple team em casa.Expected result: a versioned YAML file, a test that triggers it and a note on false positives. The SigmaHQ/sigma repository has thousands of rules to read and atomic-red-team (Red Canary) has ATT&CK technique tests to prove each rule: purple team at home.

Projetos 4, 6, 7 e 8, em poucas linhasProjects 4, 6, 7 and 8, in a few lines

Ética e lei: o que separa estudo de crimeEthics and law: what separates study from crime

A diferença entre um pentester e um criminoso não é a técnica, é a autorização. Antes de testar qualquer coisa, responda por escrito às três perguntas abaixo. Se alguma resposta for "não sei", não teste.The difference between a pentester and a criminal is not the technique, it is authorisation. Before testing anything, answer the three questions below in writing. If any answer is "I don't know", don't test.

  • É meu? Máquina, rede, conta de nuvem e aplicação que você administra e pode quebrar sem prejudicar ninguém.Is it mine? A machine, network, cloud account and application you run and can break without harming anyone.
  • Tenho autorização por escrito? Contrato de pentest, regras de um CTF, política de um programa de bug bounty ou a licença da plataforma de treino.Do I have written authorisation? A pentest contract, the rules of a CTF, a bug bounty programme's policy or the training platform's terms.
  • Qual é o escopo? Quais alvos, quais técnicas e quais horários estão permitidos. Fora do escopo é fora da autorização, mesmo no mesmo domínio.What is the scope? Which targets, techniques and hours are allowed. Outside the scope is outside the authorisation, even on the same domain.

No Brasil, a Lei 12.737/2012 criou o crime de invasão de dispositivo informático (art. 154-A do Código Penal), e a LGPD (Lei 13.709/2018) regula o tratamento de dados pessoais, o que importa se um teste expõe dados reais. Se achar uma falha em um sistema que não é seu, pare, não explore além do mínimo para confirmar, não baixe dados e reporte pelo canal oficial de divulgação (muitas empresas têm um security.txt ou um VDP). Isto é uma orientação geral, não consultoria jurídica.In Brazil, Law 12,737/2012 created the crime of invading a computing device (art. 154-A of the Penal Code), and the LGPD (Law 13,709/2018) regulates the processing of personal data, which matters if a test exposes real data. If you find a flaw in a system that is not yours, stop, do not exploit beyond the minimum needed to confirm, do not download data and report through the official disclosure channel (many companies have a security.txt or a VDP). This is general guidance, not legal advice.

Hábito que vale ouro: mantenha um diário de laboratório com data, alvo, objetivo e resultado de cada exercício. Em uma entrevista, em um relatório ou numa dúvida sobre autorização, esse registro mostra que você trabalha como profissional.A habit worth gold: keep a lab journal with the date, target, goal and result of every exercise. In an interview, in a report or in a doubt about authorisation, that record shows you work like a professional.

Qual a diferença entre ameaça, vulnerabilidade e risco?What is the difference between threat, vulnerability and risk?Ameaça é quem ou o que pode causar dano; vulnerabilidade é a fraqueza que permite; risco é a probabilidade vezes o impacto.Threat is who or what can cause harm; vulnerability is the weakness that allows it; risk is probability times impact.
Para que serve a modelagem de ameaças e quando fazê-la?What is threat modelling for and when should you do it?Achar falhas de projeto antes do código, percorrendo cada fluxo de dados com perguntas como as do STRIDE; quanto mais cedo, mais barato.Finding design flaws before the code, walking each data flow with questions like STRIDE's; the earlier, the cheaper.
Qual a relação entre CVE, CWE e CVSS?How do CVE, CWE and CVSS relate?CVE identifica uma vulnerabilidade específica, CWE a classe de fraqueza por trás dela e CVSS a gravidade de 0 a 10.CVE identifies one specific vulnerability, CWE the class of weakness behind it and CVSS the 0-to-10 severity.
O que diferencia red team, blue team e purple team?What distinguishes red, blue and purple team?Red ataca com autorização, blue detecta e responde, purple faz os dois trabalharem juntos: roda a técnica e confere se o alerta dispara.Red attacks with authorisation, blue detects and responds, purple makes the two work together: runs the technique and checks whether the alert fires.
Por que um dev deve começar por AppSec?Why should a developer start with AppSec?Porque reaproveita o que já sabe (código, testes, CI) e porque cada falha corrigida no projeto evita trabalho de red e de blue depois.Because it reuses what you already know (code, tests, CI) and because each flaw fixed in the design saves red and blue work later.
