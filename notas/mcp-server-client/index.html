O que é o MCP e que problema resolveWhat MCP is and the problem it solves

Um modelo de linguagem sozinho só gera texto. Para fazer coisas (consultar um banco, abrir uma issue, criar uma tarefa) alguém precisa ligar o modelo ao sistema. Sem padrão, cada aplicação de IA escreve uma integração própria para cada sistema: N aplicações × M sistemas. O Model Context Protocol (MCP) é um padrão aberto que corta isso: você escreve um servidor MCP para o seu sistema e qualquer aplicação de IA que fale MCP consegue usá-lo. A documentação oficial usa a analogia da porta USB-C: um conector único em vez de um cabo para cada aparelho.A language model alone only produces text. To do things (query a database, open an issue, create a task) someone has to connect the model to the system. Without a standard, every AI application writes its own integration for every system: N applications × M systems. The Model Context Protocol (MCP) is an open standard that cuts this down: you write one MCP server for your system and any AI application that speaks MCP can use it. The official documentation uses the USB-C analogy: one connector instead of a cable for every device.

MCP é uma camada agêntica sobre a sua APIMCP is an agentic layer over your API

Você já tem uma API. O MCP não a substitui: ele é outra fachada para a mesma lógica, pensada para quem não conhece a API de antemão, ou seja, um modelo. Compare os dois consumidores:You already have an API. MCP does not replace it: it is another facade over the same logic, designed for a caller that does not know the API beforehand, namely a model. Passo 1: extrair o núcleo da APIStep 1: extract the API core

O todos.js recebe, sem mudar, a configuração do banco que estava no server.js, e as quatro operações com suas validações. Um detalhe de projeto: os erros de regra carregam um status (400, 404), exatamente o que o onRequest do server.js já sabe transformar em resposta HTTP. A API continua igual para quem a usa; a camada MCP vai ignorar o número e usar só a mensagem.todos.js receives, unchanged, the database configuration that was in server.js, and the four operations with their validations. A design detail: rule errors carry a status (400, 404), exactly what server.js's onRequest already knows how to turn into an HTTP response. The API stays the same for its users; the MCP layer will ignore the number and use only the message.

'use strict';

const fs = require('node:fs');
const { Pool } = require('pg');

const pool = new Pool({
  host: process.env.DB_HOST,
  port: Number(process.env.DB_PORT || 5432),
  database: process.env.DB_NAME || 'todos',
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  ssl: process.env.DB_SSL === 'off'
    ? false
    : { ca: fs.readFileSync(process.env.DB_CA_FILE || '/app/rds-global-bundle.pem', 'utf8') },
  max: 5,
  connectionTimeoutMillis: 5000,
});

// Without this listener, a dropped idle connection (database restart) crashes the process.
pool.on('error', (err) => console.error('idle database client error:', err.message));

const COLUMNS = 'id, title, done, created_at';

// An error that carries the HTTP status the API should answer with.
// The MCP layer ignores the number and passes the message to the model.
const fail = (status, message) => Object.assign(new Error(message), { status });

async function migrate() {
  await pool.query(`CREATE TABLE IF NOT EXISTS todos (
    id         integer     GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title      text        NOT NULL,
    done       boolean     NOT NULL DEFAULT false,
    created_at timestamptz NOT NULL DEFAULT now()
  )`);
}

async function list() {
  const { rows } = await pool.query(`SELECT ${COLUMNS} FROM todos ORDER BY id`);
  return rows;
}

async function create(title) {
  if (typeof title !== 'string' || !title.trim() || title.length > 200) throw fail(400, 'title: 1 to 200 characters');
  const { rows } = await pool.query(`INSERT INTO todos (title) VALUES ($1) RETURNING ${COLUMNS}`, [title.trim()]);
  return rows[0];
}

async function setDone(id, done) {
  if (typeof done !== 'boolean') throw fail(400, 'done: boolean');
  const { rows } = await pool.query(`UPDATE todos SET done = $1 WHERE id = $2 RETURNING ${COLUMNS}`, [done, id]);
  if (!rows[0]) throw fail(404, 'not found');
  return rows[0];
}

async function remove(id) {
  const { rowCount } = await pool.query('DELETE FROM todos WHERE id = $1', [id]);
  if (!rowCount) throw fail(404, 'not found');
}

const close = () => pool.end();

module.exports = { migrate, list, create, setDone, remove, close };

No server.js, o handle() encolhe: só lê a requisição, chama o núcleo e escreve a resposta. O resto do arquivo (send, readJson, TLS, parada limpa) fica como estava; main() passa a chamar todos.migrate() e todos.close().In server.js, handle() shrinks: it only reads the request, calls the core and writes the response. The rest of the file (send, readJson, TLS, graceful shutdown) stays as it was; main() now calls todos.migrate() and todos.close().

async function handle(req, res) {
  const url = new URL(req.url, 'http://localhost');
  const m = url.pathname.match(/^\/todos(?:\/(\d+))?$/);

  if (url.pathname === '/health' && req.method === 'GET') return send(res, 200, { ok: true });

  if (m && !m[1] && req.method === 'GET') return send(res, 200, await todos.list());
  if (m && !m[1] && req.method === 'POST') {
    const { title } = await readJson(req);
    return send(res, 201, await todos.create(title));
  }
  if (m && m[1] && req.method === 'PATCH') {
    const { done } = await readJson(req);
    return send(res, 200, await todos.setDone(Number(m[1]), done));
  }
  if (m && m[1] && req.method === 'DELETE') {
    await todos.remove(Number(m[1]));
    return send(res, 204);
  }
  return send(res, 404, { error: 'not found' });
}

Há uma linha nova no núcleo: pool.on('error', ...). Sem ela, quando o Postgres reinicia ou a rede derruba uma conexão ociosa do pool, o pg emite um evento error sem ouvinte e o processo inteiro cai (reproduzi isso parando o banco com o servidor rodando). A correção vale para a API também.There is one new line in the core: pool.on('error', ...). Without it, when Postgres restarts or the network drops an idle pooled connection, pg emits an error event with no listener and the whole process crashes (I reproduced this by stopping the database while the server ran). The fix applies to the API too.

Passo 2: o servidor MCPStep 2: the MCP server

O servidor é uma função createServer() que cria um McpServer e registra as ferramentas. Ela fica num arquivo separado dos transportes, para o mesmo servidor ser servido por stdio e por HTTP. Repare que o arquivo importa o mesmo todos.js da API:The server is a createServer() function that creates an McpServer and registers the tools. It lives in a file separate from the transports, so the same server can be served over stdio and over HTTP. Note that the file imports the same todos.js as the API:

import { McpServer } from '@modelcontextprotocol/server';
import * as z from 'zod/v4';
import todos from './todos.js'; // the same module server.js uses

const todoShape = z.object({
  id: z.number(),
  title: z.string(),
  done: z.boolean(),
  created_at: z.string(),
});
const toDto = (t) => ({ ...t, created_at: t.created_at.toISOString() });
const text = (value) => ({ content: [{ type: 'text', text: typeof value === 'string' ? value : JSON.stringify(value) }] });

// A rule error (400/404) becomes a result the model can read and fix.
// Anything else (database down, bug) is logged for you and hidden from the model:
// the SDK would otherwise send err.message (host names, SQL) back as the result.
async function run(fn) {
  try { return await fn(); }
  catch (err) {
    if (err.status) return { isError: true, ...text(err.status === 404 ? `${err.message}: call list_todos to see the valid ids` : err.message) };
    console.error('tool failed:', err);
    return { isError: true, ...text('internal error: the operation failed') };
  }
}

// One instance per call: serveStdio and the HTTP handler both ask for a fresh one.
export function createServer() {
  const server = new McpServer({ name: 'todo', version: '1.0.0' });

  server.registerTool('list_todos', {
    title: 'List to-dos',
    description: 'List every to-do with its id, title and whether it is done. Call this first to find an id.',
    outputSchema: z.object({ todos: z.array(todoShape) }),
    annotations: { readOnlyHint: true },
  }, () => run(async () => {
    const output = { todos: (await todos.list()).map(toDto) };
    return { ...text(output), structuredContent: output };
  }));

  server.registerTool('add_todo', {
    title: 'Add a to-do',
    description: 'Create a new to-do (not done yet). Returns the created item with its id.',
    inputSchema: z.object({ title: z.string().min(1).max(200).describe('What needs to be done') }),
    annotations: { readOnlyHint: false, destructiveHint: false },
  }, ({ title }) => run(async () => text(toDto(await todos.create(title)))));

  server.registerTool('set_todo_done', {
    title: 'Mark a to-do done or not done',
    description: 'Set the done flag of one to-do. Use list_todos first if you do not know the id.',
    inputSchema: z.object({
      id: z.number().int().positive().describe('The to-do id'),
      done: z.boolean().describe('true to complete it, false to reopen it'),
    }),
    annotations: { readOnlyHint: false, destructiveHint: false, idempotentHint: true },
  }, ({ id, done }) => run(async () => text(toDto(await todos.setDone(id, done)))));

  server.registerTool('delete_todo', {
    title: 'Delete a to-do',
    description: 'Permanently delete one to-do. This cannot be undone.',
    inputSchema: z.object({ id: z.number().int().positive().describe('The to-do id') }),
    annotations: { readOnlyHint: false, destructiveHint: true, idempotentHint: true },
  }, ({ id }) => run(async () => { await todos.remove(id); return text(`Deleted to-do ${id}`); }));

  return server;
}

Erro do modelo × erro do sistemaModel error × system error

A função run() separa dois casos. Falha de regra (título vazio, id inexistente) é culpa da chamada: vira um resultado com isError: true e uma mensagem clara, e o modelo corrige. Falha do sistema (banco fora do ar, bug) o modelo não conserta, e há uma armadilha: o SDK captura qualquer exceção lançada pelo handler e a devolve como isError: true com o texto original. Eu medi: com o banco parado, a resposta trazia connect ECONNREFUSED 127.0.0.1:5433, ou seja, endereço interno entregue ao modelo (e a quem controlar o texto que ele lê). Por isso o run() registra o erro completo em stderr, para você, e devolve só internal error: the operation failed. Já os argumentos que reprovam no esquema Zod nem chegam ao seu código: o SDK mesmo devolve o isError: true, como mostra a atividade 2.The run() function separates two cases. A rule failure (empty title, unknown id) is the call's fault: it becomes a result with isError: true and a clear message, and the model corrects it. A system failure (database down, bug) the model cannot fix, and there is a trap: the SDK catches any exception the handler throws and returns it as isError: true with the original text. I measured it: with the database stopped, the reply carried connect ECONNREFUSED 127.0.0.1:5433, an internal address handed to the model (and to whoever controls the text it reads). So run() logs the full error to stderr, for you, and returns only internal error: the operation failed. Arguments that fail the Zod schema never reach your code: the SDK itself returns the isError: true, as activity 2 shows.

Como desenhar boas ferramentasHow to design good tools

  1. Pense em intenções, não em endpoints. A API tem PATCH /todos/:id com {done}; o agente ganha set_todo_done(id, done), um nome que descreve o que se quer. Poucas ferramentas bem nomeadas valem mais do que um espelho de cada rota.Think in intents, not endpoints. The API has PATCH /todos/:id with {done}; the agent gets set_todo_done(id, done), a name that describes what is wanted. A few well-named tools beat a mirror of every route.
  2. Descreva como se escrevesse para um colega novo: o que faz, quando usar, em que ordem, o que devolve. Marque as consequências (“não pode ser desfeito”).Describe as if writing to a new colleague: what it does, when to use it, in which order, what it returns. Flag consequences (“cannot be undone”).
  3. Devolva pouco e legível. Tudo que a ferramenta devolve ocupa o contexto do modelo. Pagine, limite, e não despeje a linha inteira do banco quando três campos bastam.Return little and readable. Everything the tool returns takes up the model's context. Paginate, cap, and do not dump the whole database row when three fields will do.
  4. Erros que ensinam. “not found” é pouco; “to-do 9999 não existe; chame list_todos para ver os ids” deixa o modelo se recuperar.Errors that teach. “not found” is thin; “to-do 9999 does not exist; call list_todos to see the ids” lets the model recover.
  5. Não exponha o que não precisa. Nada de ferramenta “rodar SQL” ou “fazer qualquer requisição”: cada ferramenta é uma permissão que você concede a um chamador que pode ser enganado (veja segurança).Do not expose what you do not need. No “run SQL” or “make any request” tool: each tool is a permission you grant to a caller that can be tricked (see security).

if (!TOKEN) throw new Error('MCP_TOKEN is required');

await todos.migrate();

function authorized(req) {
  const given = Buffer.from((req.headers.authorization || '').replace(/^Bearer /, ''));
  const wanted = Buffer.from(TOKEN);
  return given.length === wanted.length && timingSafeEqual(given, wanted);
}

createHttpServer((req, res) => {
  if (!validateHost(req, res) || !validateOrigin(req, res)) return;
  if (!authorized(req)) {
    res.writeHead(401, { 'www-authenticate': 'Bearer' }).end();
    return;
  }
  void mcp(req, res);
}).listen(PORT, '127.0.0.1', () => console.error(`todo MCP server on http://127.0.0.1:${PORT}/mcp`));
  • createMcpHandler(createServer) atende um pedido por vez, sem estado: a fábrica roda a cada requisição e nada é lembrado entre elas. Por isso funciona atrás de um balanceador e com várias réplicas, e por isso as ferramentas precisam ser registradas dentro da fábrica.createMcpHandler(createServer) serves one request at a time, statelessly: the factory runs on every request and nothing is remembered between them. That is why it works behind a load balancer and with several replicas, and why tools must be registered inside the factory.
  • O handler não valida Host, Origin nem token. Você mesmo põe as guardas na frente. Em um servidor ligado a 127.0.0.1, a checagem de Host é a defesa contra DNS rebinding (uma página maliciosa que faz o próprio domínio apontar para 127.0.0.1 e fala com o seu servidor local pelo navegador). O exemplo devolve 403 para Origin estranha e 401 sem token.The handler validates neither Host, Origin nor token. You put the guards in front yourself. On a server bound to 127.0.0.1, the Host check is the defence against DNS rebinding (a malicious page that makes its own domain point at 127.0.0.1 and talks to your local server through the browser). The example answers 403 for a foreign Origin and 401 without a token.
  • O token fixo (MCP_TOKEN) e a comparação em tempo constante (timingSafeEqual) servem ao laboratório. Em produção a especificação manda usar OAuth 2.1, com o servidor MCP como resource server; o SDK tem requireBearerAuth e o passo authInfo para isso (veja as fontes).The fixed token (MCP_TOKEN) and the constant-time comparison (timingSafeEqual) are for the lab. In production the specification says to use OAuth 2.1, with the MCP server as a resource server; the SDK has requireBearerAuth and the authInfo step for it (see the sources).
  • Para expor além do localhost, troque os guardas de localhost* pelos equivalentes com a lista de hosts e origens permitidos (hostHeaderValidation, originValidation), termine TLS no proxy e ligue em 0.0.0.0 só atrás dele.To expose beyond localhost, swap the localhost* guards for the equivalents that take your allowed hosts and origins (hostHeaderValidation, originValidation), terminate TLS at the proxy and bind 0.0.0.0 only behind it.

Passo 5: consumir com um agente (Claude + MCP)Step 5: consuming it with an agent (Claude + MCP)

Um agente é o cliente do passo anterior com um modelo no meio. O modelo nunca executa nada: ele devolve um bloco tool_use (“quero chamar add_todo com estes argumentos”); o seu código chama o servidor MCP e devolve um tool_result; o modelo lê e decide se chama outra ferramenta ou responde. Repete até a resposta vir em texto.An agent is the client from the previous step with a model in the middle. The model never executes anything: it returns a tool_use block (“I want to call add_todo with these arguments”); your code calls the MCP server and returns a tool_result; the model reads it and decides whether to call another tool or answer. This repeats until the reply comes as text.

import Anthropic from '@anthropic-ai/sdk';
import { Client } from '@modelcontextprotocol/client';
import { StdioClientTransport } from '@modelcontextprotocol/client/stdio';
import { createInterface } from 'node:readline/promises';

const MODEL = 'claude-sonnet-5-5';
const MAX_TURNS = 8; // a hard stop so a confused model cannot loop forever

const mcp = new Client({ name: 'todo-agent', version: '1.0.0' });
await mcp.connect(new StdioClientTransport({ command: process.execPath, args: ['mcp.mjs'], env: { ...process.env } }));

// 1. Discover: the tool list comes from the server, nothing is hard-coded here.
const { tools } = await mcp.listTools();
const destructive = new Set(tools.filter((t) => t.annotations?.destructiveHint).map((t) => t.name));
const claudeTools = tools.map((t) => ({ name: t.name, description: t.description, input_schema: t.inputSchema }));

const anthropic = new Anthropic(); // reads ANTHROPIC_API_KEY
const messages = [{ role: 'user', content: process.argv[2] }];
const rl = createInterface({ input: process.stdin, output: process.stderr });

for (let turn = 0; turn < MAX_TURNS; turn++) {
  const response = await anthropic.messages.create({ model: MODEL, max_tokens: 1024, tools: claudeTools, messages });
  messages.push({ role: 'assistant', content: response.content });

  if (response.stop_reason !== 'tool_use') {
    console.log(response.content.filter((b) => b.type === 'text').map((b) => b.text).join('\n'));
    break;
  }

  // 2. Act: run every tool the model asked for and answer with tool_result blocks.
  const results = [];
  for (const call of response.content.filter((b) => b.type === 'tool_use')) {
    console.error(`-> ${call.name}(${JSON.stringify(call.input)})`);
    let result;
    if (destructive.has(call.name) && (await rl.question(`   allow ${call.name}? [y/N] `)).toLowerCase() !== 'y') {
      result = { isError: true, content: [{ type: 'text', text: 'The user denied this action.' }] };
    } else {
      result = await mcp.callTool({ name: call.name, arguments: call.input });
    }
    results.push({
      type: 'tool_result',
      tool_use_id: call.id,
      is_error: result.isError === true,
      content: result.content.filter((c) => c.type === 'text'),
    });
  }
  messages.push({ role: 'user', content: results });
}

rl.close();
await mcp.close();
  1. Descobrir. As ferramentas vêm do listTools() e são repassadas ao Claude no formato da API de mensagens (name, description, input_schema). Nada está escrito à mão no agente: se você adicionar uma ferramenta ao servidor, o agente a enxerga na próxima execução.Discover. The tools come from listTools() and are handed to Claude in the Messages API format (name, description, input_schema). Nothing is hand-written in the agent: if you add a tool to the server, the agent sees it on the next run.
  2. Agir. Para cada tool_use o agente chama callTool e devolve um tool_result com o mesmo tool_use_id e is_error. A mensagem do assistente, com os blocos tool_use, precisa ir de volta no histórico antes dos resultados.Act. For each tool_use the agent calls callTool and returns a tool_result with the same tool_use_id and is_error. The assistant message, with the tool_use blocks, has to go back into the history before the results.
  3. Pedir confirmação do que é destrutivo. O servidor marcou delete_todo com destructiveHint; o cliente é quem decide o que fazer com a dica. Aqui o agente pergunta [y/N] e, se negado, devolve um erro que o modelo entende (“the user denied this action”) em vez de executar.Ask before anything destructive. The server marked delete_todo with destructiveHint; the client decides what to do with the hint. Here the agent asks [y/N] and, if denied, returns an error the model understands (“the user denied this action”) instead of executing.
  4. Limite de voltas. MAX_TURNS impede que um modelo confuso (ou um servidor que sempre devolve erro) gire para sempre gastando tokens.Turn limit. MAX_TURNS stops a confused model (or a server that always returns an error) from spinning forever burning tokens.
