O que é o LinuxWhat Linux is

Linux é, em sentido estrito, só o kernel (o núcleo): o programa que fala com o hardware e reparte CPU, memória, disco e rede entre os outros programas. Tudo o que você usa no terminal (shell, ls, grep, ssh) são programas comuns que pedem coisas ao kernel. A combinação kernel + ferramentas + gerenciador de pacotes é uma distribuição (Ubuntu, Debian, Fedora, Arch).Strictly speaking, Linux is just the kernel: the program that talks to the hardware and shares CPU, memory, disk and network among the other programs. Everything you use in the terminal (shell, ls, grep, ssh) is an ordinary program that asks the kernel for things. Kernel + tools + package manager is a distribution (Ubuntu, Debian, Fedora, Arch).

Dois princípios explicam quase tudo nesta nota: “tudo é arquivo” (discos, terminais, processos e até a rede aparecem como arquivos ou descritores de arquivo) e “todo programa roda como algum usuário” (as permissões decidem o que ele pode tocar). Aprenda esses dois e o resto vira consequência.Two principles explain almost everything in this note: “everything is a file” (disks, terminals, processes and even the network show up as files or file descriptors) and “every program runs as some user” (permissions decide what it may touch). Learn these two and the rest follows.

Para o kernel, um usuário é só um número: o UID. Nomes como “ana” existem para humanos; o kernel compara números. Cada usuário tem também um GID principal e pode pertencer a outros grupos. Os dados ficam em arquivos de texto em /etc.To the kernel a user is just a number: the UID. Names like “ana” exist for humans; the kernel compares numbers. Each user also has a primary GID and may belong to other groups. The data lives in plain text files in /etc.

O superusuário (root)The superuser (root)

O superusuário é quem tem UID 0, não quem se chama “root”. Para o kernel, UID 0 ignora as checagens de permissão de arquivos e pode, por exemplo, ler qualquer arquivo, matar qualquer processo e abrir portas abaixo de 1024. No Linux moderno esse poder é dividido em capabilities (ex.: CAP_NET_BIND_SERVICE só para abrir portas baixas), mas o root tradicional tem todas. Por isso a regra de ouro é: use root só no instante em que precisar.The superuser is whoever has UID 0, not whoever is named “root”. To the kernel, UID 0 skips file permission checks and can, for example, read any file, kill any process and bind ports below 1024. Modern Linux splits that power into capabilities (e.g. CAP_NET_BIND_SERVICE just for low ports), but the traditional root has them all. Hence the golden rule: use root only at the moment you need it.

Arquivos e permissõesFiles and permissions

Todo arquivo tem um dono (usuário), um grupo e nove bits de permissão: leitura (r), escrita (w) e execução (x) para três públicos: o dono (u), o grupo (g) e todo o resto (o). O kernel escolhe um público, nesta ordem: se você é o dono, vale só a regra do dono; senão, se está no grupo, vale a do grupo; senão, a de outros.Every file has an owner (user), a group and nine permission bits: read (r), write (w) and execute (x) for three audiences: the owner (u), the group (g) and everybody else (o). The kernel picks one audience, in this order: if you are the owner, only the owner rule applies; otherwise, if you are in the group, the group rule; otherwise, the others rule.

Estrutura de arquivosFile structure

O Linux tem uma única árvore de diretórios que começa em / (a raiz). Não existe “C:” ou “D:”: um pendrive ou outro disco é montado em algum diretório (por exemplo /mnt/usb) e seu conteúdo aparece ali. O Filesystem Hierarchy Standard (FHS) define o papel de cada diretório, e man 7 hier resume.Linux has one single tree of directories that starts at / (the root). There is no “C:” or “D:”: a USB stick or another disk is mounted on some directory (for example /mnt/usb) and its content appears there. The Filesystem Hierarchy Standard (FHS) defines each directory’s role, and man 7 hier summarises it.

Montagem, discos e inodesMounting, disks and inodes

Cada arquivo é, por baixo, um inode: um registro com dono, permissões, tamanhos e ponteiros para os blocos de dados. O nome do arquivo vive no diretório, que é só uma tabela “nome → número do inode”. Por isso um arquivo pode ter vários nomes (hard links) e por isso renomear é instantâneo (Kerrisk, cap. 14 e 18).Underneath, each file is an inode: a record with owner, permissions, sizes and pointers to the data blocks. The file’s name lives in the directory, which is just a “name → inode number” table. That is why a file can have several names (hard links) and why renaming is instant (Kerrisk, ch. 14 and 18).

Links simbólicos (e hard links)Symbolic links (and hard links)

Um link simbólico (symlink, ou soft link) é um arquivo especial e minúsculo cujo conteúdo é só um caminho, escrito como texto. Quando um programa abre o link, o kernel lê esse texto e segue para o caminho indicado, como se o programa tivesse aberto o alvo. Parece um “atalho” do Windows, com uma diferença importante: o atalho é entendido só pelo gerenciador de arquivos, enquanto o symlink é entendido pelo sistema inteiro. Para o cat, o nginx ou um script, o link é o alvo.A symbolic link (symlink, or soft link) is a tiny special file whose content is just a path, written as text. When a program opens the link, the kernel reads that text and follows it to the path, as if the program had opened the target. It looks like a Windows “shortcut”, with one important difference: a shortcut is understood only by the file manager, while a symlink is understood by the whole system. To cat, nginx or a script, the link is the target.

Para entender a diferença para o hard link (do fim da seção anterior), lembre que o diretório é uma tabela “nome → inode”. O hard link é uma segunda linha apontando para o mesmo inode. O symlink é um inode novo, do tipo “link”, que guarda o nome de outro arquivo.To see the difference from the hard link (at the end of the previous section), remember that a directory is a “name → inode” table. A hard link is a second row pointing to the same inode. A symlink is a new inode, of type “link”, that stores the name of another file.

Caminho relativo ou absolutoRelative or absolute path

O texto guardado pode ser absoluto (/home/ana/dados) ou relativo (../dados). O relativo é resolvido a partir da pasta onde o link está, não de onde você está no terminal. Resultado prático: se você move a pasta inteira (projeto, backup), links relativos dentro dela continuam certos; links absolutos continuam apontando para o lugar antigo. Já se você move só o link para outra pasta, é o relativo que quebra.The stored text can be absolute (/home/ana/data) or relative (../data). A relative one is resolved from the folder the link lives in, not from where you are in the terminal. Practical result: if you move a whole folder (project, backup), relative links inside it stay correct; absolute links keep pointing at the old place. If you move only the link to another folder, it is the relative one that breaks.

$ ln -s ../hard.txt p/sub/rel          # relativo: "um nível acima de p/sub"
$ ln -s /home/ana/p/hard.txt p/sub/abs # absoluto
$ mv p/sub x/sub                       # mudei a pasta de lugar
$ cat x/sub/rel
cat: x/sub/rel: No such file or directory   # "../hard.txt" agora é x/hard.txt
$ cat x/sub/abs

Regra prática: use relativo para links dentro do mesmo projeto (releases, repositório) e absoluto para apontar para um lugar fixo do sistema (/mnt/hd/Videos, /etc/...).Rule of thumb: use relative for links inside the same project (releases, repository) and absolute to point to a fixed place on the system (/mnt/hd/Videos, /etc/...).

Processos, pais e filhosProcesses, parents and children

Um programa é um arquivo no disco; um processo é esse programa em execução, com seu PID (identificador), seu PPID (PID do pai), um dono (UID), memória própria, diretório atual e descritores de arquivos abertos. Como um processo nasce: fork, exec e waitHow a process is born: fork, exec and wait

Linux cria processos em duas etapas (Kerrisk, cap. 24–27). fork() clona o processo atual: nasce um filho idêntico, com PID novo. Em seguida o filho chama exec(), que troca o programa dentro dele (o PID continua). O pai chama wait() para esperar o filho terminar e ler o código de saída. É exatamente isso que o bash faz quando você digita ls.Linux creates processes in two steps (Kerrisk, ch. 24–27). fork() clones the current process: an identical child is born with a new PID. Then the child calls exec(), which swaps the program inside it (the PID stays). The parent calls wait() to wait for the child to finish and read its exit code. This is exactly what bash does when you type ls.

// fork_exec.c — gcc fork_exec.c -o fork_exec
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    pid_t pid = fork();                       // clona o processo
    if (pid == -1) { perror("fork"); exit(1); }

    if (pid == 0) {                           // aqui roda o FILHO
        execlp("ls", "ls", "-l", (char *)NULL);
        perror("execlp");                     // só chega aqui se o exec falhar
        _exit(127);
    }

    int status;                               // aqui roda o PAI
    waitpid(pid, &status, 0);                 // espera e "colhe" o filho
    printf("pai %d: filho %d saiu com %d\n", getpid(), pid, WEXITSTATUS(status));
    return 0;
}

Um firewall é um porteiro: olha cada pacote e decide deixar passar, descartar ou recusar. No Linux quem filtra é o netfilter, dentro do kernel. Limpar o histórico do terminalClearing the terminal history

O shell guarda os comandos que você digita para poder repeti-los (seta para cima, Ctrl+R). No bash a lista fica na memória durante a sessão e é gravada em ~/.bash_history quando você sai. Por isso uma senha digitada na linha de comando fica gravada em texto puro.The shell keeps the commands you type so you can repeat them (up arrow, Ctrl+R). In bash the list stays in memory during the session and is written to ~/.bash_history when you exit. That is why a password typed on the command line stays stored in plain text.

history | tail -20              # veja os últimos
history -d 482                  # apaga UMA entrada (pelo número)
history -c                      # limpa a lista em MEMÓRIA
history -w                      # grava a memória no arquivo -> junto com -c, zera o arquivo
history -c && history -w        # zerar tudo de uma vez
> ~/.bash_history               # alternativa: esvazia o arquivo direto

Um detalhe que pega muita gente: history -c sozinho limpa só a memória; ao sair, o bash grava de volta o que ainda estiver no arquivo ou o que você digitar depois. Para uma sessão sem rastro, use um dos modos abaixo.A detail that catches many people: history -c alone clears only memory; on exit bash writes back what is still in the file or what you type afterwards. For a session without a trace, use one of the modes below.

O histórico também vaza por outros lugaresHistory also leaks elsewhere

  • Arquivos de histórico de outros programas: ~/.python_history, ~/.lesshst, ~/.viminfo, ~/.mysql_history, ~/.psql_history.Other programs’ history files: ~/.python_history, ~/.lesshst, ~/.viminfo, ~/.mysql_history, ~/.psql_history.
  • Os logs do sistema: o sudo registra cada comando em /var/log/auth.log ou no journal, e isso não é apagado por limpar o histórico do shell.System logs: sudo records each command in /var/log/auth.log or the journal, and that is not erased by clearing the shell history.
  • A lista de processos: argumentos de linha de comando aparecem para outros usuários em ps e em /proc/PID/cmdline enquanto o comando roda.The process list: command-line arguments are visible to other users in ps and /proc/PID/cmdline while the command runs.
  • Ferramentas de histórico sincronizado (como o atuin) guardam cópias fora do arquivo local.Synced-history tools (such as atuin) keep copies outside the local file.
Se uma senha, token ou chave de API foi digitada e gravada, limpar o histórico não basta: considere o segredo vazado e troque-o. Para o futuro, não coloque segredos em argumentos: leia sem eco (read -rs SENHA), use variáveis de ambiente, arquivos com permissão 600 ou o gerenciador de segredos.If a password, token or API key was typed and stored, clearing the history is not enough: treat the secret as leaked and rotate it. For the future, keep secrets out of arguments: read without echo (read -rs SECRET), use environment variables, files with permission 600 or a secrets manager.
Limpar o seu próprio histórico é privacidade e higiene. Apagar rastros em sistemas que não são seus, ou para esconder atividade de quem administra o ambiente, é outra coisa: em empresas o histórico e os logs costumam ser exigência de auditoria.Clearing your own history is privacy and hygiene. Erasing traces on systems that are not yours, or to hide activity from whoever administers the environment, is something else: in companies, history and logs are often an audit requirement.
