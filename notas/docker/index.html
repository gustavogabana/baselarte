O que é Docker: contêiner, imagem e por que usarWhat Docker is: container, image and why use it

Todo mundo já ouviu “na minha máquina funciona”. O Docker resolve isso empacotando o app junto com tudo que ele precisa para rodar (runtime, bibliotecas, arquivos de sistema) numa unidade que se comporta igual no seu notebook, no CI e no servidor. Essa unidade em execução é um contêiner.Everyone has heard “it works on my machine”. Docker fixes that by packaging the app together with everything it needs to run (runtime, libraries, system files) into a unit that behaves the same on your laptop, in CI and on the server. That unit, running, is a container.

Um contêiner não é uma máquina virtual. A VM simula um computador e roda um sistema operacional inteiro por cima. O contêiner é só um processo comum do Linux, isolado por recursos do próprio kernel (namespaces escondem o resto do sistema; cgroups limitam CPU e memória). Por isso sobe em milissegundos e pesa megabytes em vez de gigabytes.A container is not a virtual machine. A VM simulates a computer and runs a whole operating system on top. A container is just an ordinary Linux process, isolated by features of the kernel itself (namespaces hide the rest of the system; cgroups cap CPU and memory). That is why it starts in milliseconds and weighs megabytes instead of gigabytes.

Do Dockerfile ao contêiner: o ciclo de vidaFrom Dockerfile to container: the life cycle

O fluxo é sempre o mesmo: build (Dockerfile → imagem), push/pull (levar a imagem de e para um registry) e run (imagem → contêiner). Uma imagem pode virar muitos contêineres, e apagar um contêiner nunca apaga a imagem.The flow is always the same: build (Dockerfile → image), push/pull (move the image to and from a registry) and run (image → container). One image can become many containers, and deleting a container never deletes the image.

A imagem é feita de camadas, uma por instrução do Dockerfile. O Docker guarda cada camada em cache: se a instrução e tudo acima dela não mudaram, ele reaproveita. Por isso a ordem das linhas importa (veja a seção do Dockerfile). Dois contêineres da mesma imagem compartilham as camadas de leitura e só cada um tem a sua camada gravável, que desaparece junto com o contêiner.The image is made of layers, one per Dockerfile instruction. Docker caches each layer: if the instruction and everything above it did not change, it reuses it. That is why the order of the lines matters (see the Dockerfile section). Two containers from the same image share the read-only layers and each has its own writable layer, which vanishes with the container.

Cache: a ordem das linhas importaCache: line order matters

Repare que o Dockerfile acima copia o go.mod e baixa as dependências antes de copiar o resto do código. Como o código muda a cada commit e as dependências quase nunca, o Docker reaproveita a camada pesada do go mod download e só refaz o COPY . . e o build. A regra geral: o que muda menos vem primeiro. No Node seria COPY package*.json + npm ci antes do COPY . .; no Python, requirements.txt + pip install.Notice that the Dockerfile above copies go.mod and downloads dependencies before copying the rest of the code. Since code changes on every commit and dependencies almost never do, Docker reuses the heavy go mod download layer and only redoes COPY . . and the build. General rule: what changes least comes first. In Node it would be COPY package*.json + npm ci before COPY . .; in Python, requirements.txt + pip install.

Executar o app: PID 1, sinais e um processo por contêinerRunning the app: PID 1, signals and one process per container

  • Um processo principal por contêiner. O contêiner vive enquanto esse processo viver; quando ele sai, o contêiner para. Banco, API e fila ficam em contêineres separados, ligados por rede (veja Compose), não todos dentro de um só com systemd ou supervisord.One main process per container. The container lives as long as that process lives; when it exits, the container stops. Database, API and queue go in separate containers, joined by a network (see Compose), not all inside one with systemd or supervisord.
  • Use a forma exec (CMD ["/server"], com colchetes), não a forma shell (CMD /server). A forma shell executa sh -c "/server": o shell vira o PID 1 e não repassa o SIGTERM ao app, então o docker stop espera 10 s e acaba matando com SIGKILL, sem desligamento limpo.Use the exec form (CMD ["/server"], with brackets), not the shell form (CMD /server). The shell form runs sh -c "/server": the shell becomes PID 1 and does not forward SIGTERM to the app, so docker stop waits 10 s and ends up killing it with SIGKILL, with no clean shutdown.
  • O app deve tratar o SIGTERM (parar de aceitar requisições, terminar as em andamento, fechar conexões). Se ele cria processos filhos, rode com --init (ou init: true no Compose) para um init mínimo recolher os zumbis.The app should handle SIGTERM (stop accepting requests, finish in-flight ones, close connections). If it spawns child processes, run with --init (or init: true in Compose) so a minimal init reaps the zombies.
  • O app deve escutar em 0.0.0.0, não em 127.0.0.1: dentro do contêiner, “localhost” é o próprio contêiner, e a porta publicada chega pela interface de rede dele, não pelo loopback.The app must listen on 0.0.0.0, not 127.0.0.1: inside the container “localhost” is the container itself, and the published port arrives through its network interface, not the loopback.
  • Configuração por variáveis de ambiente (PORT, DB_ADDR), e logs na saída padrão. Assim a mesma imagem serve para dev, teste e produção.Configuration through environment variables (PORT, DB_ADDR) and logs on standard output. That way the same image serves dev, test and production.

Como decidirHow to decide

  • Comece pela variante -slim (Debian) ou -alpine da imagem oficial da sua linguagem (node:22-slim, python:3.13-slim), em vez de partir de ubuntu e instalar o runtime. Já vem configurada, atualizada e menor.Start from the -slim (Debian) or -alpine variant of your language's official image (node:22-slim, python:3.13-slim) instead of starting from ubuntu and installing the runtime. It comes configured, maintained and smaller.
  • Alpine quando o app roda bem em musl (Go, Node, a maioria dos apps Java e Python puros) e você quer uma base pequena. Cuidado com dependências nativas: se algo falhar com erros de biblioteca ou o pip install demorar para compilar, troque para -slim.Alpine when the app runs fine on musl (Go, Node, most Java and pure Python apps) and you want a small base. Mind native dependencies: if something fails with library errors or pip install takes forever compiling, switch to -slim.
  • Ubuntu quando você precisa de pacotes específicos do apt, de compatibilidade máxima ou segue o padrão da empresa. Não é “errado”, só maior; mantenha-o enxuto (exemplo abaixo).Ubuntu when you need specific apt packages, maximum compatibility, or your company standard. It is not “wrong”, just larger; keep it lean (example below).
  • Distroless ou scratch para produção de binários estáticos (Go, Rust) ou apps com runtime mínimo, geralmente como estágio final de um multi-stage.Distroless or scratch for production of static binaries (Go, Rust) or minimal-runtime apps, usually as the final stage of a multi-stage build.
# Ubuntu enxuto: um RUN so, sem recomendados, limpando o cache do apt na mesma camada
FROM ubuntu:24.04
RUN apt-get update \
 && apt-get install -y --no-install-recommends ca-certificates curl \
 && rm -rf /var/lib/apt/lists/* \
 && useradd --system --uid 10001 app
USER app

# Alpine equivalente
FROM alpine:3.22
RUN apk add --no-cache ca-certificates curl \
 && adduser -S -u 10001 app
USER app
Por que “limpar na mesma camada”: uma camada nunca encolhe. Se você instala no RUN A e apaga no RUN B, os arquivos continuam na camada A e a imagem não diminui. Instalar e limpar precisam estar no mesmo RUN.Why “clean in the same layer”: a layer never shrinks. If you install in RUN A and delete in RUN B, the files stay in layer A and the image does not get smaller. Installing and cleaning must happen in the same RUN.

Multi-stage build: levar para produção só o que rodaMulti-stage build: ship only what runs

Compilar um app exige compilador, cabeçalhos, gerenciador de pacotes, código-fonte e, às vezes, chaves de acesso a repositórios privados. Nada disso é necessário para executar o resultado, mas num Dockerfile de um estágio tudo fica na imagem final, pesando e dando ao atacante ferramentas prontas (um compilador, curl, apk). O multi-stage build usa vários FROM no mesmo arquivo: o primeiro estágio constrói, o último recebe só o artefato.Compiling an app needs a compiler, headers, a package manager, source code and sometimes access keys for private repositories. None of that is needed to run the result, but in a single-stage Dockerfile it all stays in the final image, adding weight and handing an attacker ready-made tools (a compiler, curl, apk). A multi-stage build uses several FROM lines in one file: the first stage builds, the last receives only the artifact.

# ---- estagio 1: compila (tem compilador, shell, apk; nada disso vai para o final)
FROM golang:1.25-alpine AS build
WORKDIR /src
COPY go.mod ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o /out/server .

# ---- estagio 2: so o binario, sem shell, sem apt/apk, usuario nao-root
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/server /server
EXPOSE 8080
HEALTHCHECK --interval=10s --timeout=3s --start-period=5s --retries=3 \
  CMD ["/server", "healthcheck"]
ENTRYPOINT ["/server"]
  • AS build dá nome ao primeiro estágio; COPY --from=build traz de lá apenas o binário. Os outros arquivos do estágio 1 são descartados e não entram na imagem final nem nas suas camadas.AS build names the first stage; COPY --from=build brings over only the binary. The other files of stage 1 are discarded and do not enter the final image or its layers.
  • CGO_ENABLED=0 gera um binário estático (não depende de glibc nem musl), o que permite rodar sobre a base mínima distroless/static ou até scratch (imagem vazia). -s -w remove símbolos de depuração e -trimpath tira caminhos da máquina de build.CGO_ENABLED=0 produces a static binary (depends on neither glibc nor musl), which lets it run on the minimal distroless/static base or even scratch (an empty image). -s -w strips debug symbols and -trimpath removes build-machine paths.
  • A tag :nonroot da distroless já define USER 65532: o app não roda como root.The distroless :nonroot tag already sets USER 65532: the app does not run as root.
  • Em linguagens interpretadas o desenho é o mesmo: estágio de build instala dependências de desenvolvimento e gera o bundle (npm run build, pip wheel); o final copia só dist/ ou o virtualenv para uma imagem -slim ou distroless do runtime (gcr.io/distroless/nodejs22-debian12).In interpreted languages the design is the same: the build stage installs development dependencies and produces the bundle (npm run build, pip wheel); the final one copies only dist/ or the virtualenv onto a -slim or distroless runtime image (gcr.io/distroless/nodejs22-debian12).
  • É possível construir só um estágio com docker build --target build ., útil para rodar testes dentro do estágio de build.You can build just one stage with docker build --target build ., handy for running tests inside the build stage.

Reduzir a superfície de ataqueReducing the attack surface

Se alguém conseguir executar código dentro do seu contêiner (uma falha no app, uma dependência comprometida), o estrago depende do que existe lá dentro. Um shell permite navegar e rodar comandos; um curl baixa ferramentas; o root altera o que quiser; capacidades extras permitem mexer na rede. A estratégia é tirar tudo o que o app não usa, em camadas:If someone manages to execute code inside your container (a flaw in the app, a compromised dependency), the damage depends on what exists in there. A shell lets them roam and run commands; curl downloads tools; root can change anything; extra capabilities let them touch the network. Saúde do contêiner: HEALTHCHECKContainer health: HEALTHCHECK

“Contêiner rodando” só diz que o processo existe. Um app pode estar de pé e travado, sem conexão com o banco ou sem memória. The healthcheck is a command Docker runs from time to time inside the container; the exit code decides the state: 0 healthy, 1 unhealthy.

  CMD ["/server", "healthcheck"]

# ou no Compose (sobrepoe o do Dockerfile)

	port := getenv("PORT", "8080")

	// Modo healthcheck: o proprio binario testa /health e sai com 0 ou 1.
	if len(os.Args) > 1 && os.Args[1] == "healthcheck" {
		c := http.Client{Timeout: 2 * time.Second}
		res, err := c.Get("http://127.0.0.1:" + port + "/health")
		if err != nil || res.StatusCode != 200 {
			os.Exit(1)
		}
		return
	}

	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		host, _ := os.Hostname()
		fmt.Fprintf(w, "ola do container %s\n", host)
	})
	http.HandleFunc("/health", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "ok")
	})
	// Prova a comunicacao entre containers: abre TCP para o banco pelo NOME do servico.
	http.HandleFunc("/db", func(w http.ResponseWriter, r *http.Request) {
		addr := getenv("DB_ADDR", "db:5432")
		conn, err := net.DialTimeout("tcp", addr, 2*time.Second)
		if err != nil {
			http.Error(w, "db inacessivel: "+err.Error(), http.StatusBadGateway)
			return
		}
		conn.Close()
		fmt.Fprintf(w, "db alcancavel em %s\n", addr)
	})

	logJSON("start", map[string]any{"port": port})
	log.Fatal(http.ListenAndServe(":"+port, logged(http.DefaultServeMux)))
}

func logged(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if r.URL.Path != "/health" { // o healthcheck roda a cada 10 s; nao polui o log
			logJSON("request", map[string]any{"method": r.Method, "path": r.URL.Path})
		}
		next.ServeHTTP(w, r)
	})
}

func logJSON(msg string, fields map[string]any) {
	fields["msg"], fields["time"] = msg, time.Now().UTC().Format(time.RFC3339)
	b, _ := json.Marshal(fields)
	fmt.Println(string(b))
}
